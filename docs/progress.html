Task 1 — Project scaffolding & config

done
requirements.txt · .env.example · .gitignore · sleuth/config.py · tests/test_config.py

What it does

config.py is the single place the app reads secrets/settings from the environment. A frozen Config dataclass carries voyage_api_key, groq_api_key, groq_model, database_url. load_config() builds it from env vars (via a local .env file, loaded through python-dotenv).

Why it's built this way

Nothing downstream calls os.environ directly — every module (embedder, DB connection, Groq client) takes a Config object instead. One place to look when a value is wrong; tests can build a fake Config directly without touching real env vars.

load_config() checks the three required vars (VOYAGE_API_KEY, GROQ_API_KEY, DATABASE_URL) up front and raises ConfigError naming exactly what's missing — fail fast at startup, not a cryptic 401 three layers deep during a chat request. GROQ_MODEL is optional, defaulting to llama-3.3-70b-versatile, so the model is a one-line config change, never a code change.

Task 2 — Postgres schema, local dev DB & connection helper

done
schema.sql · docker-compose.yml · sleuth/db.py · tests/conftest.py · tests/test_db.py

What it does

schema.sql defines two tables: repos (one row per indexed GitHub repo, tracks status/error/indexed_at) and chunks (one row per code chunk — function/method/class — with its embedding vector(1024), a content_hash for incremental re-index, and a unique index on (repo_id, file_path, symbol_name) so re-indexing upserts instead of duplicating). sleuth/db.py exposes get_connection(database_url), which opens a psycopg connection and registers the pgvector type adapter, and apply_schema(conn), which runs schema.sql idempotently (everything is CREATE ... IF NOT EXISTS).

Why it's built this way

Raw SQL + psycopg, no ORM — the user wants to see and understand every table and query directly rather than have SQLAlchemy generate it. content_hash on each chunk is what makes re-indexing cheap: on a repeat run, chunks whose hash hasn't changed are skipped instead of re-embedded (an API call saved per unchanged function). The HNSW index on embedding is what makes similarity search fast at query time instead of a full table scan.

docker-compose.yml runs the same pgvector/pgvector:pg16 image locally that the schema targets in Supabase, so dev/test behavior matches prod. Host port is 5433, not the default 5432 — a native Postgres 18 install already runs inside WSL on 5432 (unrelated to this project), and it intercepts localhost:5432 before Docker's port mapping ever sees the connection. Remapping the container avoids touching that native install.

One wrinkle: get_connection() registers the vector pgvector type immediately on connect, but a brand-new database doesn't have the vector extension installed until apply_schema() runs CREATE EXTENSION vector — and apply_schema() needs a connection first. Chicken-and-egg on a fresh container. Fixed by bootstrapping the extension once by hand (plain CREATE EXTENSION IF NOT EXISTS vector, no type registration) right after the container comes up; extensions persist in the database afterward, so every later connection's get_connection() finds the type already registered.

Task 3 — Chunk data model & context formatting

done
sleuth/chunking.py · tests/test_chunking.py

What it does

A Chunk dataclass — one piece of code (function, method, class, or leftover module-level statements): file_path, symbol_name (None for module-level), kind, start_line/end_line, code_text. It carries a content_hash property (SHA-256 of code_text). format_chunk_context(chunk, language) wraps that code with a small header (file, symbol, kind, language) — this is the exact text that later gets sent to Voyage for embedding, and reused when building the LLM prompt at answer time.

Why it's built this way

Pure data model, no tree-sitter or DB dependency here — Task 4/5 (parsing + AST walk) produce Chunks, Task 7 (embedding) and the future retrieve/answer.py both consume format_chunk_context(), so the "what does the LLM/embedder actually see" logic lives in exactly one place instead of being duplicated on the ingest and retrieve sides.

content_hash is the incremental-reindex hook: Task 8's store compares this against what's already in the DB and only re-embeds chunks whose hash changed — an unchanged function costs zero API calls on a repeat index.

Task 4 — tree-sitter language registry & parsing

done
sleuth/ingest/__init__.py · sleuth/ingest/parse.py · tests/test_parse.py

What it does

LANGUAGES is a dict mapping file extension (.py, .js, .ts) to a LanguageSpec (a language key like "python" plus its compiled tree-sitter grammar). parse_source(source_bytes, extension) looks up the grammar for that extension, runs a tree-sitter Parser over the raw source bytes, and returns the resulting Tree alongside the LanguageSpec that produced it. Unknown extensions raise UnsupportedFileType instead of parsing.

Why it's built this way

Tree-sitter grammars are compiled ahead-of-time (by the tree_sitter_python/tree_sitter_javascript/tree_sitter_typescript packages) into C parse tables — at runtime we just load the compiled grammar and run its parser over bytes, which is why parse_source itself is a few lines: the heavy lifting already happened at package build time. Returning (Tree, LanguageSpec) together (not just the tree) means Task 5's AST walker gets both the parse tree and the language key in one call — that key becomes the language argument format_chunk_context (Task 3) needs, so callers never have to re-derive language from the extension a second time. A dedicated UnsupportedFileType exception (instead of a raw KeyError) lets the future ingest pipeline (Task 9) catch and skip one unrecognized file type without the whole repo index crashing.

Task 5 — Chunker: walk the AST into Chunks

done
sleuth/ingest/chunk.py · tests/test_chunk.py

What it does

chunk_source(source_bytes, file_path, extension) parses the file (via Task 4's parse_source) then walks the top-level children of the root AST node. Each top-level function becomes a function chunk. Each top-level class is inspected: if it has method-like children, every method becomes its own method chunk named ClassName.method_name and the class itself is not separately chunked; if it has no methods (e.g. an empty class or a dataclass with only fields), the whole class becomes one class chunk. Everything else at module level (imports, constants, bare statements) is collected into a single trailing module chunk with symbol_name=None. Unsupported extensions return an empty list rather than raising.

Why it's built this way

Splitting by class-with-methods vs. class-without avoids storing the same source twice — a method already appears in full inside its own chunk, so re-emitting the enclosing class verbatim would just duplicate it in the embedding index and bloat retrieval with near-identical hits. Python and JS/TS share one _walk_generic walker parameterized by node-type names (function_definition vs function_declaration, etc.) since the shape of "top-level function / class / method" is the same AST pattern across these grammars, just spelled differently — one walk, one set of tests to reason about instead of three parallel implementations. Line numbers come straight off tree-sitter's start_point/end_point (0-indexed, so +1), which is what will let retrieval later cite exact source line ranges back to the user.

Task 5 revisited — query-based chunker (decorators & exports)

done
sleuth/ingest/queries/python.scm · sleuth/ingest/queries/javascript.scm · sleuth/ingest/queries/typescript.scm · sleuth/ingest/query_chunker.py · sleuth/ingest/chunk.py · tests/test_chunk.py

What it does

Replaces the positional _walk_generic walker with tree-sitter queries: a small .scm pattern file per language plus one generic run_query that turns matches into Chunks, unchanged regardless of language. A query says "find every function_definition anywhere in the tree, wherever it's nested" instead of "check if this exact child is a function" — so a decorator or an export keyword changing the node's immediate type no longer breaks detection. Decorated/exported definitions are captured by a second pattern that wraps the whole thing (decorator or export text included in the chunk), with the raw inner node also tagged (@inner.function) purely so run_query can dedupe it against the bare pattern, which independently matches the same inner node, keeping whichever match has the larger span. The same wrap/dedupe shape handles Python's @deco def f() and JS/TS's export function f() / export class C — structurally the same problem. Unsupported extensions (no .scm file) now fall back to a blank-line-block splitter instead of returning [], so nothing silently vanishes. A final pass caps any chunk over 4000 chars, slicing it into name#1, name#2, ... parts.

Why it's built this way

The bug wasn't really "decorators break Python" — it was "wrapping breaks positional matching," and JS/TS's export keyword wraps declarations the exact same way decorators wrap Python definitions. Since almost every real NestJS/Express file uses export class, the old walker was silently misfiling nearly all JS/TS classes into the generic leftover chunk, not just an edge case. Frameworks (FastAPI, NestJS, Django, Celery, Express) never enter the picture at the chunker level: their decorators/exports are just base-language syntax, so one .scm file per language is the only axis that scales — adding framework support later means adding zero code here. Extending to a new language is now "write a 15-30 line query file," not "write a new Python walker function." Class-with-methods still suppresses the whole-class chunk (methods already contain the full source, re-emitting the class would duplicate it in the embedding index) — but the class node still has to be marked "consumed" at the root even when its chunk is suppressed, otherwise it would leak into the leftover module chunk; this was the one non-obvious bug caught while wiring the dedupe logic.

Task 6 — Git clone and file listing

done
sleuth/ingest/clone.py · tests/test_clone.py

What it does

clone_repo(url, dest_dir) shells out to git clone --depth 1 and returns the destination Path; a non-zero exit raises CloneError with git's own stderr as the message. list_source_files(repo_path, extensions) walks the cloned tree with rglob("*"), skips anything under .git, and returns every file whose suffix is in the given extension set.

Why it's built this way

--depth 1 since indexing only needs the current state of the files, not history — a shallow clone is faster and smaller for every repo this will ever point at. Raising CloneError instead of letting subprocess.CalledProcessError bubble up keeps the ingest pipeline's exception surface local to sleuth.ingest, same reasoning as Task 4's UnsupportedFileType — Task 9's orchestration layer only needs to know about exceptions this package defines, not subprocess internals. list_source_files takes the extension set as a parameter rather than hardcoding it so it can be driven off Task 4's LANGUAGES dict later, keeping "which extensions we support" defined in exactly one place.

Task 7 — HTTP retry helper & Voyage embedder

done
sleuth/http_retry.py · sleuth/ingest/embed.py · tests/test_http_retry.py · tests/test_embed.py

What it does

post_with_retry(client, url, retries=1, backoff_seconds=1.0, **kwargs) wraps httpx.AsyncClient.post: on a network error (httpx.TransportError) or a transient status code (429/500/502/503/504), it sleeps backoff_seconds and retries once, then raises via raise_for_status(); any other error status (e.g. 401) raises immediately with no retry. Embedder is an ABC (embed_batch(texts), class attrs model_name, dim). VoyageEmbedder(api_key, batch_size=128, max_concurrency=5) is model_name="voyage-code-3", dim=1024: it splits input texts into batches of batch_size, fires them concurrently under an asyncio.Semaphore(max_concurrency), and for each batch response sorts Voyage's returned data by its index field before extracting embeddings — guaranteeing output vector i corresponds to input text i even though concurrent batches (and possibly the API itself) don't guarantee response order. Scope for this task deliberately narrowed to Voyage only — NimEmbedder and a get_embedder(config) provider switch are deferred until NIM support is actually needed.

Why it's built this way

One shared retry helper instead of duplicating retry logic in the Voyage client, the future Groq client, and the future NIM client — every provider call in the app goes through post_with_retry, so the retry policy (what counts as transient, how many attempts, backoff) is defined once and applied identically everywhere. Retrying blindly on any failure would silently double-charge/double-call on a permanent error like bad auth — the transient-status allowlist is what keeps retries meaningful instead of wasteful.

Batching + bounded concurrency is the main lever on ingest speed: embedding is network-bound, so one request per chunk would be dominated by round-trip latency, while unbounded concurrency risks tripping Voyage's rate limits. The semaphore caps in-flight requests without capping throughput below what's actually needed. The index-sort step exists because this is the one place a silent bug would be catastrophic and undetectable: if a batch's embeddings ever came back reordered relative to their input texts, every chunk in that batch would get permanently mismatched to the wrong vector — no error, no crash, just wrong retrieval results forever. Sorting explicitly by index removes the assumption entirely instead of trusting the API's ordering to hold.

Task 8 — Repo/chunk store (raw SQL CRUD)

done
sleuth/store.py · schema.sql · tests/test_store.py

What it does

create_repo(conn, github_url) inserts a repos row and returns its id. update_repo_status(conn, repo_id, status, error_message=None) and set_repo_embedding_info(conn, repo_id, model, dim) update that row. get_existing_hashes(conn, repo_id) returns {(file_path, symbol_name): content_hash} for every chunk already stored for that repo. upsert_chunks(conn, repo_id, [(Chunk, embedding), ...]) inserts each chunk or, on a conflict against the existing (repo_id, file_path, symbol_name) unique index, overwrites it in place. delete_stale_chunks(conn, repo_id, current_keys) removes any stored chunk whose key isn't in the freshly-parsed set. schema.sql gained embedding_model/embedding_dim columns on repos, added via both CREATE TABLE IF NOT EXISTS (fresh DB) and ALTER TABLE ADD COLUMN IF NOT EXISTS (the already-running dev container from Task 2) — apply_schema() stays idempotent either way.

Why it's built this way

Scope was narrowed from the plan's per-dimension design (separate chunks_1024/chunks_2048 tables, one per embedding provider) down to the single existing chunks table — only Voyage (1024-dim) is wired up right now, so a second table with nothing to put in it is pure speculation; the multi-table split gets added if/when NIM support actually happens. Every function takes a plain connection and never commits internally — the caller (ingest orchestration, Task 9) controls the transaction boundary, so create_repo → upsert_chunks → update_repo_status can all land in one commit, or all roll back together if something mid-run fails, instead of leaving a repo row in a half-indexed state. COALESCE(symbol_name, '') appears in the unique index, the upsert's conflict target, and the delete's match clause — SQL treats NULL != NULL, so without it two module-level chunks (both symbol_name=NULL) in the same file would never conflict/dedupe against each other and every reindex would insert a duplicate leftover-chunk instead of overwriting the one already there.

get_existing_hashes is the incremental-reindex hook content_hash (Task 3) was built for: Task 9's orchestration will diff a fresh parse's hashes against this map and only send changed/new chunks to the embedder — an unchanged function costs zero Voyage calls on a repeat index, not just zero DB writes.

Task 9 — Ingest pipeline orchestration

Files touched

sleuth/ingest/pipeline.py (new), tests/test_pipeline.py (new)

What it does

async def ingest_repo(github_url, conn, config) -> str is the one function that wires every earlier task together into a full clone-to-searchable-repo run. It finds or creates the repos row, marks it indexing, clones the repo into a temp dir, walks every .py/.js/.ts file through the Task 5 chunker, diffs the resulting chunks' content_hash against what's already stored (Task 8's get_existing_hashes) to find only the new/changed ones, embeds just those through Voyage (Task 7), upserts them, deletes any chunk whose key no longer shows up in the fresh parse, and marks the repo ready. A failed clone is caught and lands the repo in status = 'failed' with the git error message instead of raising — the function never throws.

Why it's built this way

The plan's Task 9 assumed the pluggable Voyage/NIM embedder + per-dimension chunk tables that Task 7/8's actual scope narrowed away (see Task 8 above) — so this version drops the get_embedder(config) factory and model-change re-embed path from the plan and calls VoyageEmbedder directly. That piece gets rebuilt if/when NIM support actually lands. The temp clone directory is always cleaned up in a finally, win or lose, so a failed or interrupted index run doesn't leak disk space across repeated attempts. Every step commits as it goes rather than wrapping the whole run in one transaction, so a crash partway through still leaves the DB in a legible state (e.g. indexing with some chunks already upserted) instead of silently rolling everything back with no trace of what happened.

The incremental-reindex behavior is the payoff of Task 3's content_hash and Task 8's get_existing_hashes: re-running ingest_repo against a repo where only one file changed sends exactly the chunks from that file to Voyage — everything else is skipped by hash comparison, confirmed by the test asserting the request count during a reindex only reflects the changed chunk.
