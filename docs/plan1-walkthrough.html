Task 1 — Config

sleuth/config.py

Every other module in SLEUTH needs secrets and settings — API keys, a model name, a database URL. The naive approach is to have each module call os.environ["WHATEVER"] directly wherever it needs a value. Config exists to stop that: one dataclass, built once, passed down as an explicit argument everywhere. No module reaches into the environment on its own.

DEFAULT_GROQ_MODEL = "openai/gpt-oss-120b"
REQUIRED_VARS = ("VOYAGE_API_KEY", "GROQ_API_KEY", "DATABASE_URL")


class ConfigError(Exception):
    pass


@dataclass(frozen=True)
class Config:
    voyage_api_key: str
    groq_api_key: str
    groq_model: str
    database_url: str
    generation_provider: str = "groq"
    nim_api_key: str | None = None
  • @dataclass(frozen=True) — immutable. Once built, a Config can't be mutated by some far-away piece of code; every function that takes it can trust the values didn't change mid-run.
  • REQUIRED_VARS lists exactly the three values the app cannot function without. It's a tuple of env-var names, checked before anything tries to build a Config.
  • generation_provider and nim_api_key default to the "off" state ("groq" / None) — added in Task 11 for the Groq→NIM fallback chain, but defaulted so every earlier call site that builds a bare Config(...) keeps working unchanged.
def load_config() -> Config:
    missing = [name for name in REQUIRED_VARS if not os.environ.get(name)]
    if missing:
        raise ConfigError(f"Missing required environment variable(s): {', '.join(missing)}")

    return Config(
        voyage_api_key=os.environ["VOYAGE_API_KEY"],
        groq_api_key=os.environ["GROQ_API_KEY"],
        groq_model=os.environ.get("GROQ_MODEL", DEFAULT_GROQ_MODEL),
        database_url=os.environ["DATABASE_URL"],
        generation_provider=os.environ.get("GENERATION_PROVIDER", "groq"),
        nim_api_key=os.environ.get("NIM_API_KEY") or None,
    )
  • The missing-var check runs before any os.environ[...] indexing below it — if a key is absent, the error names exactly which one, instead of a bare KeyError three layers into a chat request.
  • GROQ_MODEL and the two provider-fallback vars use .get(...) with a default — they're optional, everything else is required.
  • os.environ.get("NIM_API_KEY") or None turns an empty string (unset-but-present env var) into a real None, so downstream code can do a plain truthiness check.

One line above the class, easy to miss: load_dotenv() runs at import time, reading a local .env file into the process environment before load_config() ever looks at os.environ. That's what lets a developer keep real keys in a gitignored .env instead of exporting them by hand every session.

Task 2 — Postgres schema & connection

schema.sql · sleuth/db.py

Two tables carry the whole system's state: which repos have been indexed, and every chunk of code pulled out of them.

CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE IF NOT EXISTS repos (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    github_url      text NOT NULL,
    status          text NOT NULL DEFAULT 'pending',
    error_message   text,
    indexed_at      timestamptz,
    embedding_model text,
    embedding_dim   int
);

ALTER TABLE repos ADD COLUMN IF NOT EXISTS embedding_model text;
ALTER TABLE repos ADD COLUMN IF NOT EXISTS embedding_dim int;

CREATE TABLE IF NOT EXISTS chunks (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    repo_id       uuid NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    file_path     text NOT NULL,
    symbol_name   text,
    kind          text NOT NULL,
    start_line    int NOT NULL,
    end_line      int NOT NULL,
    code_text     text NOT NULL,
    content_hash  text NOT NULL,
    embedding     vector(1024) NOT NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS chunks_identity_idx
    ON chunks (repo_id, file_path, COALESCE(symbol_name, ''));

CREATE INDEX IF NOT EXISTS chunks_embedding_idx
    ON chunks USING hnsw (embedding vector_cosine_ops);
  • pgvector's vector extension is what makes embedding vector(1024) a real, indexable column type instead of a plain array — a fixed-width 1024-float vector, matching Voyage's voyage-code-3 output dimension exactly.
  • pgcrypto supplies gen_random_uuid(), used as the default for both primary keys — the app never generates IDs itself.
  • repos.status is the state machine for one repo's index lifecycle: pending → indexing → ready, or failed with a message. Every reader of the DB (the ask, list, and eval commands) trusts this field instead of re-deriving "is this repo usable" from row counts.
  • Everything is CREATE ... IF NOT EXISTS — the whole file can be re-run against an already-provisioned database with no effect. The two ALTER TABLE ... ADD COLUMN IF NOT EXISTS lines exist because embedding_model/embedding_dim were added to the design after some dev databases already had a repos table without them — the CREATE TABLE IF NOT EXISTS above would silently no-op against an existing table and never add the new columns, so the explicit ALTER is what actually backfills them.
  • ON DELETE CASCADE on chunks.repo_id means deleting a repo row cleans up every chunk that belonged to it automatically — no separate cleanup query anywhere in the app.
  • The unique index on (repo_id, file_path, COALESCE(symbol_name, '')) is what makes re-indexing an upsert instead of a pile of duplicates — see Task 8. COALESCE matters here: SQL treats NULL != NULL, so without it, two module-level chunks (both with symbol_name = NULL) in the same file would never collide against each other.
  • chunks_embedding_idx is an HNSW (Hierarchical Navigable Small World) index — an approximate-nearest-neighbor structure that's what makes search_chunks (Task 10) fast at query time instead of comparing the question's vector against every single row in the table.
SCHEMA_PATH = Path(__file__).resolve().parent.parent / "schema.sql"
LOCK_TIMEOUT = "5s"


def get_connection(
    database_url: str, *, connect_timeout: int = 5, retries: int = 1, backoff_seconds: float = 0.5
) -> psycopg.Connection:
    attempt = 0
    while True:
        try:
            conn = psycopg.connect(database_url, autocommit=False, connect_timeout=connect_timeout)
            register_vector(conn)
            conn.execute(f"SET lock_timeout = '{LOCK_TIMEOUT}'")
            conn.commit()
            return conn
        except psycopg.OperationalError:
            if attempt >= retries:
                raise
            attempt += 1
            time.sleep(backoff_seconds)


def apply_schema(conn: psycopg.Connection) -> None:
    sql = SCHEMA_PATH.read_text()
    conn.execute(sql)
    conn.commit()
  • register_vector(conn) teaches psycopg how to convert between Postgres's vector type and a plain Python list of floats, in both directions, for this specific connection. Without it, a query returning an embedding column would come back as an opaque string.
  • autocommit=False — every statement runs inside an explicit transaction that the caller controls with conn.commit(). This is what lets Task 9's ingest pipeline treat a whole multi-step write as one atomic unit when it needs to.
  • The retry loop around psycopg.connect only catches OperationalError — a transient connection failure — and retries exactly once after a half-second pause. A bad password or a nonexistent database raises a different exception and fails immediately; retrying that would just waste half a second before failing anyway.
  • SET lock_timeout = '5s' then an immediate conn.commit() — added later, after a real bug (see the closing notes). Any statement on this connection that would otherwise wait forever on another session's lock now aborts after 5 seconds with a clear psycopg.errors.LockNotAvailable instead of hanging silently. The commit() right after closes out the transaction that SET itself opened, so the connection isn't handed back to the caller already sitting inside an open transaction.
  • apply_schema just reads the whole schema.sql file and executes it as one multi-statement string — safe to call on every single CLI invocation because every statement in the file is idempotent.

Task 3 — Chunk data model

sleuth/chunking.py

Before there's any parsing or embedding, there needs to be an answer to "what is a piece of indexed code, structurally." That's Chunk — pure data, no tree-sitter or database dependency at all.

@dataclass
class Chunk:
    file_path: str
    symbol_name: str | None
    kind: str  # 'function' | 'method' | 'class' | 'module'
    start_line: int
    end_line: int
    code_text: str

    @property
    def content_hash(self) -> str:
        return hashlib.sha256(self.code_text.encode("utf-8")).hexdigest()


def format_chunk_context(chunk: Chunk, language: str) -> str:
    symbol = chunk.symbol_name or "(module level)"
    header = (
        f"# File: {chunk.file_path}\n"
        f"# {chunk.kind}: {symbol}\n"
        f"# Language: {language}\n\n"
    )
    return header + chunk.code_text
  • symbol_name: str | None — None specifically means "this chunk isn't one named thing," i.e. the leftover module-level code (imports, constants, bare statements) that doesn't belong to any single function or class.
  • content_hash is a plain SHA-256 of the code text, computed on demand as a property rather than stored. It's the single mechanism that makes incremental re-indexing possible: Task 8's store keeps a map of (file_path, symbol_name) → content_hash for everything already in the database, and Task 9's pipeline only sends a chunk to the embedder if its hash doesn't match what's already stored. An unchanged function costs zero embedding calls on a repeat index.
  • format_chunk_context wraps the raw code with a small header — file, symbol, kind, language — before it goes anywhere. This exact wrapped text is what gets embedded (Task 7) and what gets shown to the LLM in the answer prompt (Task 11), so "what does the model actually see" is defined in exactly one place instead of being reconstructed twice.

Task 4 — tree-sitter parsing

sleuth/ingest/parse.py

tree-sitter turns source text into a concrete syntax tree — a real parse, not a regex guessing at where a function starts and ends. The grammars for Python/JS/TS are pre-compiled C parse tables shipped as Python packages; this file just loads the right one and runs it.

PY_LANGUAGE = Language(tspython.language())
JS_LANGUAGE = Language(tsjavascript.language())
TS_LANGUAGE = Language(tstypescript.language_typescript())


@dataclass(frozen=True)
class LanguageSpec:
    key: str
    ts_language: Language


LANGUAGES: dict[str, LanguageSpec] = {
    ".py": LanguageSpec("python", PY_LANGUAGE),
    ".js": LanguageSpec("javascript", JS_LANGUAGE),
    ".ts": LanguageSpec("typescript", TS_LANGUAGE),
}


class UnsupportedFileType(Exception):
    pass


def parse_source(source_bytes: bytes, extension: str) -> tuple[Tree, LanguageSpec]:
    spec = LANGUAGES.get(extension)
    if spec is None:
        raise UnsupportedFileType(extension)

    parser = Parser(spec.ts_language)
    tree = parser.parse(source_bytes)
    return tree, spec
  • LANGUAGES is the one dictionary that answers "which extensions does SLEUTH understand" — every other module (the chunker, the clone/file-listing step) derives its behavior from this map rather than hardcoding its own extension list.
  • parse_source returns the tree and the LanguageSpec together, not just the tree. That spec.key (e.g. "python") is exactly the language argument format_chunk_context needs — callers never have to re-derive the language name from a file extension a second time.
  • UnsupportedFileType is a dedicated exception rather than a raw KeyError — it lets Task 5's chunker catch specifically "I don't know this extension" and fall back to a generic splitter, without accidentally swallowing an unrelated bug.

Task 5 — Query-based chunker

sleuth/ingest/chunk.py · sleuth/ingest/query_chunker.py · sleuth/ingest/queries/*.scm

This is the piece that decides where one chunk ends and the next begins: every top-level function becomes its own chunk; every method inside a class becomes its own chunk (named ClassName.method_name); a class with no methods becomes one whole-class chunk; everything else at module level (imports, constants) becomes one trailing "module" chunk. The first version walked the AST positionally (checking each top-level child's exact node type) and broke the moment a decorator or an export keyword wrapped a definition — this is the rewritten, query-based version.

The query files — what to look for, not how to walk

; bare module-level (or nested-in-function) function
(function_definition
  name: (identifier) @name.function) @definition.function

; decorated function — @definition.function is the *wrapper*, so decorator
; text is included; @inner.function is the raw node, used only for dedup
; against the bare pattern above which also matches it independently
(decorated_definition
  definition: (function_definition
    name: (identifier) @name.function) @inner.function) @definition.function

; plain method
(class_definition
  name: (identifier) @name.class
  body: (block
    (function_definition
      name: (identifier) @name.method) @definition.method)) @definition.class_context

; decorated method
(class_definition
  name: (identifier) @name.class
  body: (block
    (decorated_definition
      definition: (function_definition
        name: (identifier) @name.method) @inner.method) @definition.method)) @definition.class_context

; whole class, bare
(class_definition
  name: (identifier) @name.class) @definition.class

; whole class, decorated (e.g. @dataclass)
(decorated_definition
  definition: (class_definition
    name: (identifier) @name.class) @inner.class) @definition.class

sleuth/ingest/queries/python.scm — a small pattern-matching language tree-sitter ships with. Each S-expression describes a shape in the syntax tree to find, wherever it occurs, tagged with capture names (@name.function, @definition.class, …). This is the fix for the original bug: a query says "find every function_definition anywhere, however deeply it's wrapped," instead of "check whether this exact child is a function." A @dataclass decorator or a wrapping decorated_definition node no longer breaks detection, because the query isn't looking at position — it's looking at shape.

typescript.scm mirrors this for JS/TS's export_statement wrapper, which is structurally the same problem as Python's decorators — export class Foo {} wraps a class_declaration exactly the way @dataclass class Foo: wraps a class_definition. (javascript.scm is the same pattern set again, for the JS grammar.) One notable difference: in this grammar, method decorators are siblings of the method, not wrappers around it — so TS never needed a separate "decorated method" pattern the way Python did.

run_query — turning matches into Chunks

def run_query(query: Query, root: Node, source_bytes: bytes, file_path: str) -> list[Chunk]:
    matches = query.matches(root)

    method_records = []
    for _, captures in matches:
        if "definition.method" not in captures:
            continue
        outer = captures["definition.method"][0]
        inner = captures.get("inner.method", [outer])[0]
        class_name = _node_text(captures["name.class"][0], source_bytes)
        method_name = _node_text(captures["name.method"][0], source_bytes)
        method_records.append(
            {
                "outer": outer,
                "key": _span_key(inner),
                "symbol_name": f"{class_name}.{method_name}",
                "kind": "method",
            }
        )
  • query.matches(root) runs every pattern in the .scm file against the whole tree at once and returns every match, each with its own dictionary of captures.
  • Methods are collected first and separately, because they take priority: a method's containing class must never also be emitted as its own whole-class chunk (that would duplicate the method's source inside two different chunks in the embedding index).
  • captures.get("inner.method", [outer])[0] — for an undecorated method there's no inner.method capture at all, so this falls back to the same node as outer. This one line is what lets decorated and undecorated methods share the rest of the logic.
    excluded_function_keys = {r["key"] for r in method_records}
    classes_with_methods = {
        _span_key(captures["definition.class_context"][0])
        for _, captures in matches
        if "definition.method" in captures
    }

    function_candidates: dict[tuple[int, int], dict] = {}
    class_candidates: dict[tuple[int, int], dict] = {}

    for _, captures in matches:
        if "definition.method" in captures or "definition.class_context" in captures:
            continue

        if "definition.function" in captures:
            outer = captures["definition.function"][0]
            inner = captures.get("inner.function", [outer])[0]
            key = _span_key(inner)
            if key in excluded_function_keys:
                continue
            _keep_largest(
                function_candidates, key, outer=outer,
                symbol_name=_node_text(captures["name.function"][0], source_bytes),
                kind="function",
            )
        elif "definition.class" in captures:
            outer = captures["definition.class"][0]
            inner = captures.get("inner.class", [outer])[0]
            key = _span_key(inner)
            _keep_largest(
                class_candidates, key, outer=outer,
                symbol_name=_node_text(captures["name.class"][0], source_bytes),
                kind="class",
            )
  • _span_key(node) is just (start_byte, end_byte) — a hashable identity for "this exact span of source," used to deduplicate matches and to check membership across sets.
  • The dedup problem this section solves: the bare @definition.function pattern and the decorated @definition.function pattern both independently match the same inner function node for a decorated function. _keep_largest resolves that by keeping whichever matched span is bigger — the decorated (outer) one — so a decorated function is captured with its decorator text intact instead of twice.
  • classes_with_methods records every class that had at least one method match, by the byte-span of its @definition.class_context capture — this is checked later so that class is excluded from getting its own whole-class chunk.
    records = (
        method_records
        + list(function_candidates.values())
        + [r for key, r in class_candidates.items() if key not in classes_with_methods]
    )

    # a class-with-methods is consumed at the root even though it emits no
    # whole-class chunk of its own — methods represent it instead
    top_level_keys = {_span_key(r["outer"]) for r in function_candidates.values()}
    top_level_keys |= {_span_key(r["outer"]) for r in class_candidates.values()}

    chunks = [
        Chunk(
            file_path=file_path,
            symbol_name=r["symbol_name"],
            kind=r["kind"],
            start_line=r["outer"].start_point[0] + 1,
            end_line=r["outer"].end_point[0] + 1,
            code_text=_node_text(r["outer"], source_bytes),
        )
        for r in records
    ]

    leftover = [child for child in root.children if _span_key(child) not in top_level_keys]
    if leftover:
        chunks.append(Chunk(
            file_path=file_path, symbol_name=None, kind="module",
            start_line=leftover[0].start_point[0] + 1,
            end_line=leftover[-1].end_point[0] + 1,
            code_text="\n".join(_node_text(n, source_bytes) for n in leftover),
        ))

    return chunks
  • start_point[0] + 1 — tree-sitter's line numbers are 0-indexed; +1 converts to the 1-indexed line numbers everything else in the app (and every editor) uses.
  • The subtle bug this code specifically had to get right, called out in the code comment: a class-with-methods still has to be added to top_level_keys even though it never produces its own chunk — otherwise it would leak into leftover and get re-emitted, whole, inside the trailing module chunk.
  • Everything not claimed by a function, method, or standalone class — imports, constants, bare top-level statements — falls through to leftover and becomes one final kind="module", symbol_name=None chunk.

chunk_source and the size cap — sleuth/ingest/chunk.py

def chunk_source(source_bytes: bytes, file_path: str, extension: str) -> list[Chunk]:
    try:
        tree, spec = parse_source(source_bytes, extension)
    except UnsupportedFileType:
        chunks = _fallback_chunk(source_bytes, file_path)
    else:
        query = _load_query(spec.key, spec.ts_language)
        chunks = run_query(query, tree.root_node, source_bytes, file_path)

    return _cap_chunk_sizes(chunks)

An unsupported extension no longer returns an empty list (the original behavior) — it falls back to _fallback_chunk, a plain blank-line-block splitter, so nothing silently vanishes from the index just because it isn't Python/JS/TS. _cap_chunk_sizes runs on every chunk regardless of path: anything over 4000 characters gets sliced into name#1, name#2, ... parts on line boundaries, so one enormous generated file or minified bundle can't produce a single chunk too large to embed sensibly.

Task 6 — Git clone & file listing

sleuth/ingest/clone.py

class CloneError(Exception):
    pass


def clone_repo(url: str, dest_dir: str) -> Path:
    dest = Path(dest_dir)
    result = subprocess.run(
        ["git", "clone", "--depth", "1", url, str(dest)],
        capture_output=True,
        text=True,
    )
    if result.returncode != 0:
        raise CloneError(result.stderr.strip())
    return dest


def list_source_files(repo_path: Path, extensions: set[str]) -> list[Path]:
    files = []
    for path in Path(repo_path).rglob("*"):
        if ".git" in path.parts:
            continue
        if path.is_file() and path.suffix in extensions:
            files.append(path)
    return files
  • --depth 1 — a shallow clone. Indexing only ever needs the current state of the files, never the commit history, so there's no reason to pull the whole history down.
  • subprocess.run(..., capture_output=True, text=True) — git's own stderr becomes the CloneError message directly, rather than letting a raw subprocess.CalledProcessError bubble up. It keeps the exception surface local to sleuth.ingest: Task 9's pipeline only ever needs to know about exceptions this package defines, not subprocess internals.
  • list_source_files takes the extension set as a parameter instead of hardcoding {".py", ".js", ".ts"} — the caller (Task 9's pipeline) drives it off Task 4's LANGUAGES dict, so "which extensions we support" stays defined in exactly one place.
  • .git is explicitly skipped — walking a repo's own git internals would waste time and could pick up junk that isn't source code at all.

Task 7 — HTTP retry & Voyage embedder

sleuth/http_retry.py · sleuth/ingest/embed.py

TRANSIENT_STATUS_CODES = {429, 500, 502, 503, 504}


async def post_with_retry(
    client: httpx.AsyncClient, url: str, *, retries: int = 1, backoff_seconds: float = 1.0, **kwargs
) -> httpx.Response:
    attempt = 0
    while True:
        try:
            response = await client.post(url, **kwargs)
        except httpx.TransportError:
            if attempt < retries:
                attempt += 1
                await asyncio.sleep(backoff_seconds)
                continue
            raise

        if response.status_code in TRANSIENT_STATUS_CODES and attempt < retries:
            attempt += 1
            await asyncio.sleep(backoff_seconds)
            continue

        response.raise_for_status()
        return response
  • One shared helper instead of duplicating retry logic in the Voyage client, the Groq client, and the NIM client — every outbound HTTP call in the app goes through this function, so the retry policy (what counts as transient, how many attempts, how long to wait) is defined once.
  • Two separate failure paths are handled: a network-level exception (httpx.TransportError — the request never got a response at all) and a transient status code (429 rate-limited, or a 5xx server error) — both retry once after a fixed backoff, everything else (a 400, a 401, a 404) raises immediately via response.raise_for_status().
  • That immediate-raise-on-non-transient behavior matters: retrying blindly on any failure would silently double-call on a permanent error like bad auth. Only the allowlisted transient codes get a second attempt.
class VoyageEmbedder(Embedder):
    model_name = "voyage-code-3"
    dim = 1024

    def __init__(self, api_key: str, batch_size: int = 128, max_concurrency: int = 5):
        self.api_key = api_key
        self.batch_size = batch_size
        self.max_concurrency = max_concurrency

    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
        batches = [texts[i : i + self.batch_size] for i in range(0, len(texts), self.batch_size)]
        semaphore = asyncio.Semaphore(self.max_concurrency)

        async with httpx.AsyncClient() as client:
            results = await asyncio.gather(
                *(self._embed_one_batch(client, semaphore, batch) for batch in batches)
            )

        vectors: list[list[float]] = []
        for batch_vectors in results:
            vectors.extend(batch_vectors)
        return vectors

    async def _embed_one_batch(
        self, client: httpx.AsyncClient, semaphore: asyncio.Semaphore, batch: list[str]
    ) -> list[list[float]]:
        async with semaphore:
            response = await post_with_retry(
                client, VOYAGE_EMBEDDINGS_URL,
                headers={"Authorization": f"Bearer {self.api_key}"},
                json={"input": batch, "model": self.model_name},
            )

        data = response.json()["data"]
        data.sort(key=lambda item: item["index"])
        return [item["embedding"] for item in data]
  • Texts are split into fixed-size batches, then all batches are fired concurrently through asyncio.gather, bounded by asyncio.Semaphore(max_concurrency) so at most max_concurrency requests are ever in flight at once. Embedding is network-bound, so one request per chunk would be dominated by round-trip latency; unbounded concurrency risks tripping the provider's rate limit. The semaphore is the middle ground.
  • data.sort(key=lambda item: item["index"]) is the one line in this whole codebase where a silent bug would be the most dangerous and the least visible: Voyage's response doesn't guarantee its data array comes back in the same order the input texts were sent, and neither does running several batches concurrently. If embeddings ever landed mismatched against their source chunks, every one of them would silently point at the wrong vector forever — no crash, no error, just permanently wrong retrieval. Sorting explicitly by the index field Voyage returns removes the assumption entirely instead of trusting the ordering to hold.

Task 8 — Repo/chunk store

sleuth/store.py

Raw SQL, no ORM — every function here takes a plain psycopg.Connection and issues one parameterized query. Nothing here commits on its own; the caller controls the transaction boundary.

def create_repo(conn: psycopg.Connection, github_url: str) -> str:
    row = conn.execute(
        "INSERT INTO repos (github_url) VALUES (%s) RETURNING id", (github_url,)
    ).fetchone()
    return str(row[0])


def get_existing_hashes(conn: psycopg.Connection, repo_id: str) -> dict[tuple[str, str | None], str]:
    rows = conn.execute(
        "SELECT file_path, symbol_name, content_hash FROM chunks WHERE repo_id = %s", (repo_id,)
    ).fetchall()
    return {(file_path, symbol_name): content_hash for file_path, symbol_name, content_hash in rows}

get_existing_hashes is the read side of incremental re-indexing: it loads every chunk already stored for a repo as a {(file_path, symbol_name): content_hash} map. Task 9's pipeline diffs a fresh parse's hashes against this map and only sends the changed/new ones to the embedder.

def upsert_chunks(
    conn: psycopg.Connection, repo_id: str,
    chunks_with_embeddings: list[tuple[Chunk, list[float]]],
) -> None:
    for chunk, embedding in chunks_with_embeddings:
        conn.execute(
            """
            INSERT INTO chunks
                (repo_id, file_path, symbol_name, kind, start_line, end_line, code_text, content_hash, embedding)
            VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
            ON CONFLICT (repo_id, file_path, COALESCE(symbol_name, ''))
            DO UPDATE SET
                kind = EXCLUDED.kind, start_line = EXCLUDED.start_line, end_line = EXCLUDED.end_line,
                code_text = EXCLUDED.code_text, content_hash = EXCLUDED.content_hash, embedding = EXCLUDED.embedding
            """,
            (repo_id, chunk.file_path, chunk.symbol_name, chunk.kind,
             chunk.start_line, chunk.end_line, chunk.code_text, chunk.content_hash, embedding),
        )


def delete_stale_chunks(
    conn: psycopg.Connection, repo_id: str, current_keys: set[tuple[str, str | None]]
) -> None:
    existing = get_existing_hashes(conn, repo_id)
    stale_keys = existing.keys() - current_keys
    for file_path, symbol_name in stale_keys:
        conn.execute(
            "DELETE FROM chunks WHERE repo_id = %s AND file_path = %s AND COALESCE(symbol_name, '') = COALESCE(%s, '')",
            (repo_id, file_path, symbol_name),
        )
  • ON CONFLICT (...) DO UPDATE SET is the whole upsert: insert a new chunk, or if one with the same (repo_id, file_path, symbol_name) already exists, overwrite it in place instead of erroring or duplicating. This is what the unique index from Task 2's schema exists for.
  • delete_stale_chunks is a plain set difference — existing.keys() - current_keys — every key that was stored before but doesn't appear in the latest parse gets deleted. This is what handles a function being deleted or renamed in the source repo between index runs; without it, old chunks would accumulate forever.
  • COALESCE(symbol_name, '') shows up in the conflict target, the delete's match clause, and the schema's unique index — all three have to agree on how NULL is treated, or the upsert and the stale-delete would disagree about whether two module-level chunks are "the same row."

Task 9 — Ingest pipeline orchestration

sleuth/ingest/pipeline.py

This is the one function that wires Tasks 4 through 8 together into a full clone-to-searchable-repo run.

async def ingest_repo(github_url: str, conn, config: Config) -> str:
    repo_id = _find_or_create_repo(conn, github_url)
    update_repo_status(conn, repo_id, "indexing")
    conn.commit()

    embedder = VoyageEmbedder(api_key=config.voyage_api_key)

    workdir = tempfile.mkdtemp(prefix="sleuth-clone-")
    try:
        try:
            repo_path = clone_repo(github_url, workdir)
        except CloneError as exc:
            update_repo_status(conn, repo_id, "failed", str(exc))
            conn.commit()
            return repo_id

        files = list_source_files(repo_path, SUPPORTED_EXTENSIONS)

        all_chunks = []
        for file_path in files:
            relative_path = str(file_path.relative_to(repo_path))
            source_bytes = file_path.read_bytes()
            try:
                chunks = chunk_source(source_bytes, relative_path, file_path.suffix)
            except Exception:
                continue  # skip files that fail to parse, don't abort the whole index
            all_chunks.extend(chunks)
  • _find_or_create_repo makes ingest_repo safe to call again on a URL that's already been indexed — it looks up the existing row by github_url rather than always inserting a new one, which is what makes re-indexing (as opposed to indexing-from-scratch every time) possible at all.
  • Status flips to "indexing" and commits immediately, before any of the slow work starts — a concurrent sleuth list or sleuth ask against this repo sees accurate state the whole time, not a stale "pending" or a state that only updates at the very end.
  • A per-file try/except Exception: continue around chunk_source means one malformed or unparseable file skips itself and doesn't abort indexing the other 500 files in the repo.
  • A failed clone is caught, recorded as status = "failed" with git's own error message, and returns normally — ingest_repo never raises for this specific failure mode.
        current_keys = {(c.file_path, c.symbol_name) for c in all_chunks}
        existing_hashes = get_existing_hashes(conn, repo_id)

        to_embed = [
            c for c in all_chunks
            if existing_hashes.get((c.file_path, c.symbol_name)) != c.content_hash
        ]

        if to_embed:
            texts = [
                format_chunk_context(c, EXTENSION_TO_LANGUAGE.get("." + c.file_path.rsplit(".", 1)[-1], ""))
                for c in to_embed
            ]
            vectors = await embedder.embed_batch(texts)
            upsert_chunks(conn, repo_id, list(zip(to_embed, vectors)))
            conn.commit()

        set_repo_embedding_info(conn, repo_id, embedder.model_name, embedder.dim)
        conn.commit()

        delete_stale_chunks(conn, repo_id, current_keys)
        conn.commit()

        update_repo_status(conn, repo_id, "ready")
        conn.commit()
        return repo_id
    finally:
        shutil.rmtree(workdir, ignore_errors=True)
  • The diff line — existing_hashes.get(key) != c.content_hash — is the entire incremental-reindex mechanism in one comparison. A chunk whose hash already matches what's stored is simply never added to to_embed, so it costs zero Voyage API calls on a repeat index.
  • if to_embed: guards the whole embed-and-upsert block — if nothing changed since last time, the embedder is never even called.
  • Each step commits as it goes, rather than wrapping the entire run in one giant transaction. If the process crashes partway through, the database is left in a legible state — e.g. "indexing" with some chunks already upserted — instead of silently rolling everything back with no trace of what happened.
  • finally: shutil.rmtree(workdir, ...) guarantees the temporary clone directory is cleaned up whether the run succeeded, failed, or raised — so repeated or interrupted index attempts don't leak disk space.
Scope note carried through Tasks 7–11: the plan's original design called for a pluggable Voyage/NIM embedder with separate per-dimension chunk tables. Implementation narrowed this to Voyage-only — one VoyageEmbedder, one chunks table, no get_embedder(config) factory. This function calls VoyageEmbedder directly as a result. The narrower scope was a deliberate, confirmed decision, revisited only if/when NIM embedding actually becomes necessary.

Task 10 — Vector search

sleuth/retrieve/search.py

@dataclass
class SearchResult:
    file_path: str
    symbol_name: str | None
    kind: str
    start_line: int
    end_line: int
    code_text: str
    distance: float


def search_chunks(
    conn: psycopg.Connection, repo_id: str, query_embedding: list[float], top_k: int = 8,
) -> list[SearchResult]:
    rows = conn.execute(
        """
        SELECT file_path, symbol_name, kind, start_line, end_line, code_text,
               embedding <=> %(query)s::vector AS distance
        FROM chunks
        WHERE repo_id = %(repo_id)s
        ORDER BY distance
        LIMIT %(top_k)s
        """,
        {"query": query_embedding, "repo_id": repo_id, "top_k": top_k},
    ).fetchall()
    return [SearchResult(*row) for row in rows]
  • <=> is pgvector's cosine-distance operator — smaller means "more similar." Ordering by it and taking the first top_k rows is the entire similarity search; Postgres does the ranking, and the HNSW index built in Task 2's schema is what keeps this fast without a full table scan as the chunks table grows.
  • %(query)s::vector — the explicit cast matters. The query embedding arrives as a plain Python list, which psycopg would otherwise send as a double precision[] parameter; Postgres refuses to compare that against a vector column without the cast. (register_vector, from Task 2, handles conversion for values going in and out of a known vector column — not for a bare parameter used inline in an expression like this one.)
  • WHERE repo_id = %(repo_id)s scopes every search to one repo — asking a question about repo A never returns chunks from repo B, even though they live in the same physical table.

Task 11 — Generator & answer generation

sleuth/llm/generate.py · sleuth/retrieve/answer.py

class Generator(ABC):
    model_name: str
    timeout: float = DEFAULT_TIMEOUT

    def __init__(self, api_key: str, model_name: str | None = None):
        self.api_key = api_key
        if model_name:
            self.model_name = model_name

    @abstractmethod
    def _url(self) -> str: ...

    async def chat(self, messages: list[dict], stream: bool = True) -> AsyncIterator[str]:
        async with httpx.AsyncClient(timeout=self.timeout) as client:
            if stream:
                async for token in self._stream_chat(client, messages):
                    yield token
            else:
                yield await self._chat_once(client, messages)

Generator is an abstract base wrapping one HTTP call shape shared by Groq and NIM — both are OpenAI-compatible chat-completions endpoints, so the only thing a subclass has to supply is its URL (and optionally a different model_name/timeout). chat() is an async generator either way; for stream=False it just yields a single item so callers don't need two different code paths depending on whether they want streaming.

    async def _stream_chat(self, client: httpx.AsyncClient, messages: list[dict]) -> AsyncIterator[str]:
        headers = {"Authorization": f"Bearer {self.api_key}"}
        payload = {"model": self.model_name, "messages": messages, "stream": True}
        async with client.stream("POST", self._url(), headers=headers, json=payload) as response:
            response.raise_for_status()
            async for line in response.aiter_lines():
                if not line.startswith("data: "):
                    continue
                data = line[len("data: "):]
                if data == "[DONE]":
                    break
                delta = json.loads(data)["choices"][0]["delta"].get("content")
                if delta:
                    yield delta

This is hand-rolled Server-Sent-Events parsing — no SDK. Groq/NIM stream a chat completion as a sequence of lines each starting with data: , ending with a literal data: [DONE] sentinel. Every other line is a JSON chunk carrying one token's worth of delta.content, which gets yielded immediately as it arrives — this is what makes the CLI's ask command print tokens as they're generated instead of waiting for the whole answer.

class GroqGenerator(Generator):
    model_name = "openai/gpt-oss-120b"
    def _url(self) -> str:
        return GROQ_URL


class NimGenerator(Generator):
    model_name = "meta/llama-3.1-70b-instruct"
    timeout = 120
    def _url(self) -> str:
        return NIM_URL


def get_fallback_chain(config: Config) -> list[Generator]:
    chain = [get_generator(config)]
    if config.generation_provider == "groq" and config.nim_api_key:
        chain.append(NimGenerator(api_key=config.nim_api_key))
    return chain


async def chat_with_fallback(
    chain: list[Generator], messages: list[dict], stream: bool = True
) -> AsyncIterator[str]:
    last_error: Exception | None = None
    for generator in chain:
        try:
            async for token in generator.chat(messages, stream=stream):
                yield token
            return
        except (httpx.HTTPStatusError, httpx.TransportError) as exc:
            last_error = exc
            continue
    raise RuntimeError(f"All generators in fallback chain failed: {last_error}")
  • get_fallback_chain builds a chain that's Groq-primary, NIM-second — but only if an NIM key is actually configured; otherwise the chain is just the one generator.
  • chat_with_fallback walks that chain in order. If a generator's chat() raises an HTTP-level or transport-level error, it moves to the next one; if every generator in the chain fails, it raises one combined RuntimeError naming the last error. This is a second, independent layer of retry on top of post_with_retry's single in-request retry — one retry lives at the HTTP layer per provider, provider-to-provider failover is the layer above it.
  • NimGenerator.timeout = 120 (vs. the 60s default) — added after real-world testing showed NIM's free-tier hosted inference has enough latency variance to occasionally exceed 60 seconds; see the closing notes.

def build_prompt(question: str, results: list[SearchResult]) -> str:
    blocks = []
    for r in results:
        symbol = r.symbol_name or "(module level)"
        blocks.append(
            f"# File: {r.file_path}\n# {r.kind}: {symbol} (lines {r.start_line}-{r.end_line})\n\n{r.code_text}"
        )
    context = "\n\n---\n\n".join(blocks)
    return f"Question: {question}\n\nRelevant code:\n\n{context}"


async def stream_answer(question: str, repo_id: str, conn, config: Config) -> AsyncIterator[str]:
    row = conn.execute("SELECT status FROM repos WHERE id = %s", (repo_id,)).fetchone()
    if row is None or row[0] != "ready":
        raise ValueError(f"Repo {repo_id} is not ready to query (status={row[0] if row else 'missing'})")

    embedder = VoyageEmbedder(api_key=config.voyage_api_key)
    query_vector = (await embedder.embed_batch([question]))[0]
    results = search_chunks(conn, repo_id, query_vector)
    prompt = build_prompt(question, results)

    chain = get_fallback_chain(config)
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": prompt},
    ]
    async for token in chat_with_fallback(chain, messages, stream=True):
        yield token

This is the whole retrieval-augmented-generation loop for indexed mode, in one function: guard on repo status, embed the question with the exact same embedder that indexed the code (so the question and the chunks live in the same vector space), search, build a prompt out of the top-k results, then stream the model's answer. Guarding on status != "ready" up front means a question against a repo that's still indexing, or that failed, gets a clear error instead of a search over an empty or half-populated chunks table.

Task 13 — Agentic / live retrieval mode

sleuth/retrieve/agentic.py

The second retrieval mode: no clone, no index, no database — a bounded tool loop that reads a local directory directly and answers from whatever it finds.

MAX_ITERATIONS = 6
GREP_MAX_MATCHES = 50
READ_FILE_MAX_LINES = 400

SYSTEM_PROMPT = (
    "You are a code assistant investigating a local codebase to answer the user's "
    "question. You have three tools:\n"
    "  grep(pattern, glob=null) -- regex search across files, first 50 matches\n"
    "  list_files(glob) -- list files matching a glob\n"
    "  read_file(path, start_line=null, end_line=null) -- read up to 400 lines of a file\n"
    "To call a tool, respond with EXACTLY one line in this form and nothing else:\n"
    'TOOL: <tool_name> {"arg": "value", ...}\n'
    "When you have enough information to answer, respond with your final answer as "
    "plain prose (no TOOL: prefix)."
)

_TOOL_LINE_RE = re.compile(r"^TOOL:\s*(\w+)\s*(\{.*\})\s*$", re.MULTILINE)


def _parse_tool_call(text: str) -> tuple[str, dict] | None:
    match = _TOOL_LINE_RE.search(text.strip())
    if not match:
        return None
    try:
        args = json.loads(match.group(2))
    except json.JSONDecodeError:
        return None
    return match.group(1), args

The whole "protocol" is deliberately just text: the model either responds with exactly one line matching TOOL: name {json}, or it responds with plain prose meant as the final answer. No function-calling API, no tools=[...] schema — a plain chat-completions endpoint is enough. re.MULTILINE plus .search() (rather than .match() anchored to the very start) is a real fix made during testing: some models prepend visible reasoning before the actual tool-call line, and the original anchored-to-start regex missed it entirely. Searching for the pattern anywhere, on any line, tolerates that preamble while still requiring the tool call itself to be one clean line.

def _tool_grep(root: Path, pattern: str, glob: str | None = None) -> str:
    regex = re.compile(pattern)
    matches = []
    paths = sorted(root.rglob(glob or "*"))
    for path in paths:
        if not path.is_file() or ".git" in path.parts:
            continue
        try:
            text = path.read_text(errors="ignore")
        except OSError:
            continue
        for lineno, line in enumerate(text.splitlines(), start=1):
            if regex.search(line):
                matches.append(f"{path.relative_to(root)}:{lineno}: {line.strip()}")
                if len(matches) >= GREP_MAX_MATCHES:
                    return "\n".join(matches) + "\n... (truncated at 50 matches)"
    return "\n".join(matches) if matches else "(no matches)"


def _tool_read_file(root: Path, path: str, start_line=None, end_line=None) -> str:
    target = root / path
    try:
        lines = target.read_text(errors="ignore").splitlines()
    except OSError as exc:
        return f"(error reading {path}: {exc})"

    start = max((start_line or 1) - 1, 0)
    end = min(end_line or len(lines), start + READ_FILE_MAX_LINES, len(lines))
    snippet = lines[start:end]
    return "\n".join(f"{start + i + 1}: {line}" for i, line in enumerate(snippet))

Both tools cap their own output — grep stops at 50 matches, read_file at 400 lines — for the same reason Task 7's embedder bounds its concurrency: an unbounded tool result could blow the prompt budget on one large file or one very common pattern, so the tool protects itself rather than trusting the model to ask for small enough slices. Both are read-only and resolve paths relative to root only.

async def run_agentic(question: str, path: str, config: Config, generator=None) -> AsyncIterator[str]:
    generator = generator or get_generator(config)
    root = Path(path)
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": question},
    ]

    for _ in range(MAX_ITERATIONS):
        response_text = await _call(generator, messages)
        parsed = _parse_tool_call(response_text)

        if parsed is None:
            yield response_text
            return

        messages.append({"role": "assistant", "content": response_text})
        name, args = parsed
        result = _dispatch_tool(name, args, root)
        messages.append({"role": "user", "content": f"Tool result: {result}"})

    messages.append({
        "role": "user",
        "content": "Iteration limit reached. Answer the original question with what "
        "you've gathered so far, as plain prose.",
    })
    response_text = await _call(generator, messages)
    yield response_text + "\n\n(Note: search was cut short after reaching the iteration limit.)"
  • Each loop turn calls the generator with stream=False (inside _call) — the loop needs to see the model's complete response before it can tell whether it's a tool call or a final answer, so token-by-token streaming would be wasted work on every turn except possibly the last. This means the agentic answer arrives at the CLI as one chunk, not real token-by-token streaming the way indexed ask does — a deliberate simplicity trade-off, not an oversight.
  • A non-tool response ends the loop immediately and becomes the answer. A tool response gets dispatched, and its result is appended as the next user message — the model sees its own prior tool call and the result in the growing conversation, exactly like a real back-and-forth.
  • Hitting MAX_ITERATIONS without a final answer doesn't error out — one last forced, non-tool turn asks the model to answer with whatever it's gathered so far, and the returned text is suffixed with an explicit note that the search was cut short. A partial answer beats a hard failure.

Task 14 — Eval harness

sleuth/eval/runner.py

The regression suite: a golden set of questions with known-correct answers, scored automatically against whatever the pipeline actually returns.

@dataclass
class GoldenCase:
    question: str
    expected_files: list[str]
    expected_symbols: list[str] = field(default_factory=list)
    reference_answer: str = ""


def load_golden(path: str) -> tuple[str, list[GoldenCase]]:
    data = yaml.safe_load(Path(path).read_text())
    cases = [
        GoldenCase(
            question=c["question"],
            expected_files=c.get("expected_files", []),
            expected_symbols=c.get("expected_symbols", []),
            reference_answer=c.get("reference_answer", ""),
        )
        for c in data.get("cases", [])
    ]
    return data["repo"], cases


def _hit_and_rank(results, case: GoldenCase) -> tuple[bool, float]:
    for rank, r in enumerate(results, start=1):
        file_hit = r.file_path in case.expected_files
        symbol_hit = bool(case.expected_symbols) and r.symbol_name in case.expected_symbols
        if file_hit or symbol_hit:
            return True, 1.0 / rank
    return False, 0.0

A golden case names the files/symbols a good retrieval should surface, plus a reference answer for grading. _hit_and_rank walks the ranked search results and finds the first one that matches the expected file or symbol — a "hit" — and its reciprocal rank (1/rank: a hit at rank 1 scores 1.0, at rank 4 scores 0.25, no hit at all scores 0.0). This is retrieval quality, completely independent of whether the generated answer is any good.

async def run_eval(golden_yaml_path: str, conn, config: Config) -> str:
    repo_id, cases = load_golden(golden_yaml_path)
    row = conn.execute("SELECT id FROM repos WHERE id = %s", (repo_id,)).fetchone()
    if row is None:
        raise ValueError(f"Repo {repo_id} not found")

    embedder = VoyageEmbedder(api_key=config.voyage_api_key)
    chain = get_fallback_chain(config)
    judge = get_generator(config)

    results: list[CaseResult] = []
    for case in cases:
        query_vector = (await embedder.embed_batch([case.question]))[0]
        search_results = search_chunks(conn, repo_id, query_vector, top_k=TOP_K)
        hit, rr = _hit_and_rank(search_results, case)

        prompt = build_prompt(case.question, search_results)
        answer = "".join([t async for t in chat_with_fallback(chain, [{"role": "user", "content": prompt}], stream=False)])

        judge_score = None
        if case.reference_answer:
            judge_text = "".join([t async for t in judge.chat(
                [{"role": "user", "content": JUDGE_PROMPT.format(reference=case.reference_answer, produced=answer)}],
                stream=False,
            )])
            judge_score = _parse_judge_score(judge_text)

        results.append(CaseResult(case.question, hit, rr, judge_score, answer))

    return _format_table(results)
  • Every case runs the real pipeline — the same VoyageEmbedder, search_chunks, and chat_with_fallback that ask uses. This is what makes it a true end-to-end regression check rather than a unit test with mocked internals.
  • The judge score is a second, independent metric on top of hit/MRR: the same generator is asked to grade the produced answer against the case's reference_answer on a 1–5 scale. This separates two different failure modes — a bad answer built from good retrieval (a generation problem) versus a good answer that got lucky despite bad retrieval (a retrieval problem that generation happened to paper over).
  • if case.reference_answer: — judging is skipped entirely for a case with no reference answer to grade against, rather than scoring against nothing.
Scope note: like Task 9, this was adapted from the plan's pluggable-embedder design down to the same Voyage-only scope established in Tasks 7–11 — no _EMBEDDER_BY_MODEL lookup, no dim parameter threaded through search_chunks. run_eval calls VoyageEmbedder directly, exactly like pipeline.py and answer.py do.

Real-world findings

Every test above is green against mocked HTTP calls. Running the actual CLI against real Voyage, Groq, and NIM APIs (and a real Supabase Postgres instance) surfaced things no mock could catch:

Supabase's direct host is IPv6-only

db.<project-ref>.supabase.co resolves to an IPv6 address with no IPv4 fallback; many networks (including the one this was built on) can't route to it at all. Fix: use Supabase's Session pooler connection string instead (still port 5432, still supports the session-level SET/DDL this app needs) — not the Transaction pooler on 6543, which doesn't reliably support session-scoped statements.

Voyage's trial tier: 3 RPM, 10K TPM

No payment method on file caps a Voyage key hard. VoyageEmbedder's default batch_size=128 can trivially exceed 10K tokens in a single request against real code chunks — an instant 429, unrelated to request frequency. Fix (for this trial key): a smaller batch_size and a smaller target repo, not a code change — production use with a funded account wouldn't hit this at all.

llama-3.3-70b-versatile is dead on Groq

The model this whole design was built and documented against — including the plan's own default — has been deprecated and removed from Groq's catalog; requesting it now returns a plain 404. Fixed by moving DEFAULT_GROQ_MODEL and GroqGenerator.model_name to openai/gpt-oss-120b, currently live and working well for indexed ask/ eval.

gpt-oss-120b breaks the agentic text protocol

This is the interesting one. Groq's openai/gpt-oss-120b does its own native tool-call detection server-side, even though the request never declares any tools=[...]. It sees the model's own output land on a TOOL: name {json}-shaped line, decides that's a tool call, and rejects it with 400 tool_use_failed / output_parse_failed — because no tool schema was ever declared for it to validate against. Task 13's plain-text protocol was designed against a model with no native tool-calling behavior at all (the now-dead llama-3.3-70b-versatile); a reasoning/tool-tuned model doesn't fit that assumption. Tried two live alternatives on Groq: qwen/qwen3.6-27b wraps its answer in a visible <think>...</think> block before the tool line (fixed by relaxing _parse_tool_call's regex to search anywhere, not just the start of the string — a genuine, now-tested robustness improvement); allam-2-7b is simply too weak to follow the exact format. NIM's plain (non-reasoning-tuned) meta/llama-3.1-70b-instruct followed the protocol correctly across multiple real tool-call iterations with zero deviation.

Individual calls ranged from ~4s to over 60s on the same model, same prompt shape, no payment method on that key either. Not an error — just latency variance under shared, on-demand hosted inference. Fixed by making Generator.timeout overridable per subclass and setting NimGenerator.timeout = 120 instead of hardcoding 60s everywhere.

apply_schema's own lock, and the fix that generalized

apply_schema() re-running schema.sql — including an ALTER TABLE ... ADD COLUMN, which always needs an ACCESS EXCLUSIVE lock even when the column already exists — on every single CLI invocation meant any other long-lived connection touching repos could freeze the next command indefinitely, with zero feedback. First caught by a test fixture accidentally leaving an uncommitted read open. Fixed at the root with SET lock_timeout = '5s' on every connection (Task 2) — not by caching "schema already applied," since this project has no migration framework and unconditional idempotent re-apply is the only mechanism by which a future schema.sql edit ever reaches an already-provisioned database.
