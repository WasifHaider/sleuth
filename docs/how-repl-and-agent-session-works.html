SLEUTH — How the REPL & AgentSession Work

The agentic/live half of SLEUTH: no database, no embeddings, no upfront indexing — just an LLM given three small tools and let loose on a local directory, plus a real terminal UI built around it. Same teaching style as its companions (how-indexing-works.html, how-chat-works.html): concept first, then real code, then — since this document was specifically requested to go one level deeper — every import at the top of both files gets its own short "why this one, why it matters here" explanation before the code that uses it. Read this after the other two; it assumes you already understand RAG, embeddings, and vector search from them.

Revised 2026-09-02 — the REPL was rebuilt, and the tool layer had four real bugs. Parts 10, 12, 13 and 14 originally documented a full-screen prompt_toolkit application with a bordered input box pinned to the bottom and a hand-written scrolling transcript pane. That design was replaced, because it did not work: touchpad/wheel scrolling was impossible by construction, the spinner silently ate transcript content, and Ctrl-C could not interrupt an in-flight question. Separately, the three tools in Part 3 had four defects that only appeared when running from native Windows Python. Those four Parts are now rewritten to describe the code as it actually is, and Part 17 is a new post-mortem of all the bugs — what broke, why, and how each was proven fixed. Sections describing unchanged code (Parts 0-2, 4-9, 11, 15) are untouched.

Part 0 — The big picture

What problem does this whole subsystem solve, and why does it need to exist as a second retrieval mode alongside indexed search?

Concept — retrieval without an index how-indexing-works.html and how-chat-works.html both describe a mode that needs an upfront investment: clone a repo, chunk it, embed every chunk, store it in Postgres — then questions are cheap. That's the right trade for a remote GitHub repo you'll ask many questions about over days. But sometimes you just want to ask ONE quick question about the code sitting in your current local directory right now — cd into a project and ask "where's the retry logic" without waiting through a full index run first. Agentic mode is built for exactly that case: skip indexing entirely, and instead give the LLM itself three small tools — grep, list_files, read_file — and let it decide, turn by turn, what to look at. This mirrors how a human explores an unfamiliar codebase far more directly than "compute a vector and find its nearest neighbors" does — and it costs nothing upfront, at the price of a hard cap on how much ground it can cover per question (Part 6).

Two files carry this whole subsystem, and it's worth being clear about the boundary between them before diving in:

FileWhat it ownsKnows about a terminal UI?
sleuth/retrieve/agent_session.py The tool-call protocol, the three tools, the multi-turn loop itself — this is the actual "agent" No — it yields plain dataclass events and has zero print/terminal code anywhere
sleuth/repl.py A full-screen terminal interface: reads what a user types, drives an AgentSession, renders its events as colored, scrolling text Yes — everything terminal-specific lives here, nowhere else
Why this split matters, concretely: AgentSession is reused by three different callers that have nothing to do with a terminal — the one-shot sleuth agentic CLI command (Part 7), the interactive REPL this document mostly covers, and — a genuine third caller, not a hypothetical — the repo-summarization step that now runs during ingestion itself (sleuth/summarize.py::summarize_repo_agentic, see how-indexing-works.html Part 10). If tool-call parsing and terminal rendering were tangled together in one file, that third caller would have had no clean class to import — it would either duplicate the loop or drag a terminal dependency into a background ingestion task that never prints anything to any screen at all.

Part 1 — agent_session.py's imports, one by one

Every top-of-file import, and specifically why this module needs it and not something heavier or lighter.

File: sleuth/retrieve/agent_session.py

import json

The model's tool-call arguments arrive as a JSON object embedded in plain text (TOOL: grep {"pattern": "foo"} — Part 2). Standard library json.loads is all that's needed to turn that string into a real Python dict — no schema validation library, no Pydantic model, because the "schema" here is just "some tool, some string-keyed JSON object," and each tool function (Part 3) does its own args.get(key, default) extraction rather than needing a formal contract enforced up front.

import re

Two distinct regex uses in this file, both small and specific: recognizing the TOOL: name {...} line shape (_TOOL_LINE_RE, Part 2), and nothing else — the actual tool implementations (Part 3) now shell out to ripgrep/sed rather than using Python regex for scanning file contents, which is a change from this module's very first version (see the warning in Part 3).

import subprocess

The three tools are implemented by shelling out to real, battle-tested command-line programs — ripgrep (rg) for grep/list_files, sed for read_file — rather than hand-rolling file-walking and line-matching in pure Python. subprocess.run with an explicit argument list (never a formatted shell string) is what makes that safe: Part 3 covers exactly why shell=False-by-default argument lists matter when one of those arguments is text the LLM itself supplied.

from collections.abc import AsyncIterator

The return type of AgentSession.ask() — it doesn't return one answer, it's an async generator that yields a sequence of events (tool calls, tool results, finally an answer) as they happen, so a caller can react to each one live instead of waiting for the whole multi-step loop to finish silently. AsyncIterator[AgentEvent] is the type-hint spelling of "something you can async for over, that produces AgentEvent values" — the same pattern pipeline-deep-dive.html Part 1 introduces for LLM token streaming, reused here for a different kind of stream: whole structured events, not raw text tokens.

from dataclasses import dataclass, field

@dataclass is used repeatedly in this file — for the three event types (Part 5) and for AgentSession itself (Part 4). field specifically is needed for AgentSession's init=False fields (Part 4) — a dataclass feature beyond the basic "generate __init__ from the field list" behavior pipeline-deep-dive.html Part 1 covers, needed here because some of this class's fields shouldn't be constructor arguments at all, only things computed once construction finishes.

from pathlib import Path

Every tool operates relative to one root directory — the directory the user pointed the REPL/CLI at. Path objects (rather than raw strings) are what let the code write root / path to safely join a path, and .resolve() to get an absolute, symlink-resolved form for the sandboxing check in Part 3 — string concatenation would get both of those wrong on different platforms (Windows vs. POSIX separators) and wouldn't have a built-in way to normalize away .. segments at all.

import httpx

Not used to make HTTP calls directly in this file — imported specifically so ask()'s except clauses (Part 6) can catch httpx.HTTPStatusError/ httpx.TransportError by name. Those are the exact exception types sleuth/llm/generate.py's Generator classes raise on a real network/API failure (how-chat-works.html Part 8) — catching them specifically, rather than a bare except Exception, means a genuine bug in this module's own code (a TypeError, an AttributeError) still propagates and fails loudly instead of being silently swallowed and shown to the user as "the model backend is unavailable."

from sleuth.config import Config

The same immutable, frozen Config dataclass every other module in this project reads API keys and model settings from (pipeline-deep-dive.html Part 2) — AgentSession takes it once at construction and uses it to build its own default generator chain (Part 4), exactly the same pattern stream_answer uses for chat.

from sleuth.llm.generate import GroqGenerator, Generator, NimGenerator, chat_with_fallback

The exact same Generator ABC, concrete provider classes, and fallback-chain helper that back regular indexed chat (how-chat-works.html Part 8) — reused here without a single line of new LLM-provider code. What's different is which model gets used (Part 4 explains AGENTIC_GROQ_MODEL) and how the chain is built, not the underlying mechanism for talking to Groq/NIM at all. This is the same "shared building blocks, not shared endpoints" reuse pattern the eval harness uses (pipeline-deep-dive.html Part 17).

Part 2 — The text protocol: tool calling with no native API

How an LLM that has no built-in "function calling" feature still reliably calls tools.

File: sleuth/retrieve/agent_session.py

Concept — why not use a provider's native tool-calling API? Many LLM providers offer a structured "function calling" mode: you describe available tools as a JSON schema, and the model returns a properly typed tool-call object instead of free text. SLEUTH deliberately doesn't use that — consistent with the project's "no black-box library doing this for you" philosophy, the system prompt itself defines a tiny, fully transparent text protocol: respond with exactly one line TOOL: toolname {"arg": "value"} to call a tool, or plain prose (no such prefix) to give a final answer. This is more fragile — a model that slightly deviates in formatting can break the parser — but every part of what "tool calling" even means here is one small regex and a json.loads call away, not hidden inside a provider SDK. 
SYSTEM_PROMPT = (
    "You are a code assistant investigating a local codebase to answer the user's "
    "question. You have three tools:\n"
    "  grep(pattern, glob=null) -- regex search across files, first 50 matches\n"
    "  list_files(glob) -- list files matching a glob\n"
    "  read_file(path, start_line=null, end_line=null) -- read up to 400 lines of a file\n"
    "To call a tool, respond with EXACTLY one line in this form and nothing else:\n"
    'TOOL: <tool_name> {"arg": "value", ...}\n'
    "Example of a correct tool call (args must be a valid JSON object with "
    "double-quoted keys/values):\n"
    'TOOL: grep {"pattern": "def foo", "glob": "*.py"}\n'
    "Do not add explanation before or after the TOOL: line when calling a tool.\n"
    "When you have enough information to answer, respond with your final answer as "
    "plain prose (no TOOL: prefix)."
)

_TOOL_LINE_RE = re.compile(r"^TOOL:\s*(\w+)\s*(\{.*\})\s*$", re.MULTILINE)
  • The system prompt now includes a worked example of a correctly formatted call — this wasn't in the original one-shot version. Empirically, models following a hand-rolled text protocol are meaningfully more reliable when shown one concrete instance of the exact shape expected, not just an abstract grammar description.
  • _TOOL_LINE_RE: ^TOOL:\s*(\w+)\s*(\{.*\})\s*$ with re.MULTILINE — anchors to any line start/end in the text (not just the whole string's start/end), matches the literal TOOL: prefix plus whitespace, captures the tool name as word characters, then captures everything from the first { to the last } on that line as the JSON blob (greedy .*, which matters for correctly capturing nested JSON objects).
class MalformedToolCall(Exception):
    def __init__(self, raw_text: str, parse_error: str):
        self.raw_text = raw_text
        self.parse_error = parse_error
        super().__init__(f"malformed tool call: {parse_error}")


def _parse_tool_call(text: str) -> tuple[str, dict] | None:
    match = _TOOL_LINE_RE.search(text.strip())
    if not match:
        return None
    try:
        args = json.loads(match.group(2))
    except json.JSONDecodeError as exc:
        raise MalformedToolCall(raw_text=match.group(0), parse_error=str(exc)) from exc
    return match.group(1), args
A real correctness gap this fixes, versus the module's original version: the very first implementation of this parser treated "matched the TOOL: shape but the JSON failed to parse" identically to "no tool call at all" — both fell through to "just show this text as the final answer." That meant a model that almost-but-not-quite got the JSON right (a trailing comma, single quotes instead of double) would have its broken, literal TOOL: grep {pattern: foo} line shown to the user as if it were the answer to their question — confusing and wrong. MalformedToolCall is a distinct exception specifically so the caller (ask(), Part 6) can tell these two cases apart: a genuine final answer gets shown to the user; a malformed tool call gets fed back to the model as an error message instead, giving it a chance to correct its own syntax on the next turn — and it still counts toward the iteration cap, so a persistently broken model still terminates rather than looping forever.

Part 3 — The three tools: ripgrep, sed, and a sandbox

What the model can actually touch — and the six real hardening changes made since the first version.

File: sleuth/retrieve/agent_session.py

Change #1 — from hand-rolled Python to real CLI tools. The original grep tool was a pure-Python implementation: root.rglob("*"), read every file, regex-match every line by hand. That has two real problems a hand-rolled walk doesn't solve for free: it has no concept of .gitignore (so it would happily grep through node_modules/.venv/ dist/build unless every such directory is separately, manually excluded), and it re-implements regex/encoding/binary-file-detection edge cases that a real, heavily used tool already handles correctly. The current version shells out to ripgrep (rg) instead — it respects .gitignore automatically, and is simply a better-tested implementation of the same idea. 
def _tool_grep(root: Path, pattern: str, glob: str | None = None) -> str:
    args = ["rg", "--line-number", "--no-heading", "--color", "never", "--no-require-git"]
    glob = _normalize_glob(glob)                    # change #4
    if glob:
        args += ["--glob", glob]
    args += [pattern, str(root)]
    try:
        proc = _run_tool_subprocess(args, cwd=root)  # change #3
    except FileNotFoundError:
        return "(error: ripgrep (rg) is not installed or not on PATH)"

    lines = [_relativize_rg_line(line, root) for line in proc.stdout.splitlines()]

    if proc.returncode == 2 and not lines:           # change #5
        return f"(invalid pattern or rg error: {proc.stderr.strip()})"
    ...
  • args = ["rg", ...] — an argument list, not a single formatted shell string. This is the deliberate, load-bearing safety choice: subprocess.run given a list never invokes a shell to interpret it, so a model-supplied pattern containing shell metacharacters (;, |, backticks) is passed to rg as one opaque argument, never as something a shell could execute. Building this as f"rg {pattern} {root}" and running it with shell=True would have been a textbook command-injection vulnerability the moment an adversarial or just-confused model produced a pattern like "; rm -rf / #".
  • --no-require-git — ripgrep by default assumes it's inside a git repo and behaves slightly differently if not; this flag makes it work identically for a plain directory the REPL was pointed at, git repo or not.
  • FileNotFoundError is caught specifically for the case where rg itself isn't installed — a clear, actionable message instead of an opaque traceback (this is a real environment gap the project hit directly: see this file's memory notes on WSL needing sudo apt-get install ripgrep).

Change #3 — decoding pinned to UTF-8, not the locale codepage

The bug: all three tools called subprocess.run(..., text=True) with no encoding=. text=True decodes using the locale encoding, which on native Windows Python is cp1252 — a 256-character codepage. Source files are UTF-8, so a single curly quote (", bytes \xe2\x80\x9c) in a matched line raised UnicodeDecodeError: 'charmap' codec can't decode byte 0x9d. And it raised on the background reader thread that subprocess spawns, not in the calling code — so the exception was never propagated: subprocess.run() returned "successfully" with proc.stdout = None, and the tool then died on AttributeError: 'NoneType' object has no attribute 'splitlines'. See Part 17 for the captured reproduction. 
def _run_tool_subprocess(args: list[str], cwd: Path | None = None) -> subprocess.CompletedProcess:
    return subprocess.run(
        args,
        capture_output=True,
        encoding="utf-8",
        errors="replace",
        cwd=cwd,
    )
  • One shared helper, used by all three tools, so the fix cannot be applied to two of them and forgotten on the third.
  • encoding="utf-8" is correct regardless of host locale — the files being read are UTF-8, which is a property of the data, not of whoever happens to be running the program.
  • errors="replace" is the second half of the fix, and it is not optional. Pinning UTF-8 alone still raises on genuinely non-UTF-8 bytes (a latin-1 file, a binary blob rg didn't classify as binary). A tool whose output is destined for an LLM prompt wants a replacement character in that situation, never an exception.

Change #4 — a match-everything glob must not defeat .gitignore

The bug: in ripgrep, passing any explicit --glob switches it out of gitignore-respecting mode for matching. A model that reflexively adds glob: "*" — a complete no-op as a filter — therefore silently dragged every ignored directory back into the search. Measured on this very repo: --glob '*' scanned 12,853 files under .venv/ and produced 2,440,969 bytes of output, where the identical search with no glob produced 5,815 bytes from zero ignored files. A 420× blowup of third-party code the user never wrote, flooding the model's context — and the source of the undecodable bytes in change #3. 
_MATCH_EVERYTHING_GLOBS = {"*", "**", "**/*", "*/*", ".", "./*"}


def _normalize_glob(glob: str | None) -> str | None:
    if glob is None:
        return None
    if glob.strip() in _MATCH_EVERYTHING_GLOBS:
        return None
    return glob
  • Dropping such a glob is semantically identical to honoring it — it excludes nothing either way — while restoring ignore filtering. Verified both directions: no glob at all lists 184 files here, and a real glob like "*.py" still filters correctly (75 files, zero of them under .venv).
  • This is deliberately a no-op-glob check rather than a hand-maintained exclusion list (--glob '!.venv' --glob '!node_modules'). That alternative was tried first and measured failing on this repo: those two negations still let 7,202 files through from .venv-win/, a third virtualenv directory nobody thought to add. Exclusion lists are whack-a-mole; .gitignore already knows every ignorable directory, so the right fix is to stop overriding it.

Change #5 — exit code 2 is often a partial success

The bug: rg exits 2 if any path was unreadable — which is routine here, because .venv/lib64 is a WSL-created symlink that Windows rg cannot traverse (os error 1920), as are npm's node_modules/.bin/* links. The old code treated every exit 2 as "invalid pattern," discarding the ~195 KB of real matches rg had already printed to stdout. The model was told its search had failed when it hadn't, so it retried the same search until MAX_ITERATIONS was exhausted — this was the REPL's "gets stuck on a codebase question" symptom. 
    note = ""
    if proc.returncode == 2:
        skipped = len([ln for ln in proc.stderr.splitlines() if ln.strip()])
        note = f"\n(note: {skipped} path(s) could not be read and were skipped; ...)"

    if len(lines) > GREP_MAX_MATCHES:
        return "\n".join(lines[:GREP_MAX_MATCHES]) + "\n... (truncated at 50 matches)" + note
    return "\n".join(lines) + note
  • The distinguishing test is whether stdout has matches, not the exit code alone: exit 2 with matches is a partial success (return them, plus a note), exit 2 with empty stdout is a genuine failure (report it, so the model can fix its own regex). Blanket accepting exit 2 would have broken self-correction for malformed patterns; blanket rejecting it was the original bug.
  • The note is surfaced rather than hidden, so the model knows the search was not exhaustive and can caveat its answer accordingly.
  • _tool_list_files received the identical treatment — same three changes (#3, #4, #5), for the same reasons.

Change #6 — Windows drive letters broke the citation format

The bug (found while verifying the others): _relativize_rg_line parsed ripgrep's path:lineno:content output with line.split(":", 2). But a Windows absolute path carries its own colon: C:\repo\a.py:1:x splits into path="C", lineno="\repo\a.py", content="1:x". So relative_to() always failed, no path was ever relativized on Windows (leaking the host's absolute filesystem layout into the model's context), and the path:lineno: text contract the model cites from came out mangled. 
_RG_LINE_RE = re.compile(r"^(?P<path>.*?):(?P<lineno>\d+):(?P<content>.*)$", re.DOTALL)
  • Anchoring on the :<digits>: separator instead of "the first two colons" is what makes a drive letter harmless — C: is not followed by digits-then-colon.
  • The non-greedy .*? deliberately stops at the first such separator, which is correct because rg emits the line number immediately after the path. A greedy pattern would split on the last one, mangling any matched line that itself contains :<digits>: — a URL like http://x:8080/p, a dict literal, a type annotation. Both behaviors are pinned by tests.
def _tool_read_file(root: Path, path: str, start_line=None, end_line=None) -> str:

    if not (target == resolved_root or resolved_root in target.parents):
        return f"(error: path {path!r} escapes the sandboxed root directory)"
    if not target.is_file():
        return f"(error reading {path}: not a file)"

    end = min(requested_end, start + READ_FILE_MAX_LINES - 1)
    proc = _run_tool_subprocess(["sed", "-n", f"{start},{end}p", str(target)])

Change #2 — the path-traversal guard. The original version joined root / path and read it directly, with no check that the result actually stayed under root. A model asked (or tricked, or simply confused) into requesting read_file("../../../../etc/passwd") would have had that request honored — Python's / path-join doesn't stop .. segments from walking back out of the intended directory. target.resolve() collapses any .. segments and symlinks into a final absolute path, and resolved_root in target.parents (or an exact match, for reading the root directory itself) is the actual guard: if the resolved path isn't under the sandboxed root, the tool refuses and returns an error string instead of ever touching the filesystem outside the intended directory. Low severity for a personal local tool where you trust the model isn't adversarial — but a genuine hardening fix, not a hypothetical one.

read_file shells out to sed -n '<start>,<end>p' rather than reading the whole file into Python and slicing a list — consistent with the grep/list_files tools also shelling out rather than hand-rolling. end is capped at start + READ_FILE_MAX_LINES - 1 (400 lines) regardless of what the model asked for, the same token-budget-protection idea as GREP_MAX_MATCHES: an unbounded read of a huge file could itself blow the model's context window. Of the three tools this is the one most exposed to change #3, since it reads whole source files where non-ASCII prose in comments and docstrings is common.

Part 4 — AgentSession: the dataclass

Why some fields are constructor arguments and others explicitly aren't.

File: sleuth/retrieve/agent_session.py

AGENTIC_GROQ_MODEL = "qwen/qwen3.8-27b"

@dataclass
class AgentSession:
    path: str
    config: Config | None = None
    generator: Generator | None = None
    fallback_chain: list[Generator] | None = None
    max_messages: int = DEFAULT_MAX_MESSAGES
    root: Path = field(init=False)
    messages: list[dict] = field(init=False)
    _chain: list[Generator] = field(init=False)

    def __post_init__(self) -> None:
        self.root = Path(self.path)
        self.messages = [{"role": "system", "content": SYSTEM_PROMPT}]
        if self.fallback_chain is not None:
            self._chain = self.fallback_chain
        elif self.generator is not None:
            self._chain = [self.generator]
        else:
            self._chain = _default_agentic_chain(self.config)
  • path, config, generator, fallback_chain, max_messages are real constructor arguments — what a caller supplies to create a session (AgentSession("/some/repo", config=cfg) is the common case; tests instead pass generator= or fallback_chain= to inject a fake, never touching a real API).
  • root, messages, _chain are marked field(init=False) — they must not be constructor arguments at all, because they're not raw inputs, they're derived from the real inputs. Accepting them as constructor args would let a caller construct a session with, say, messages already populated with something other than a fresh system prompt — a footgun with no legitimate use case. __post_init__ (a dataclass hook that runs automatically right after the generated __init__ finishes) is where they actually get computed.
  • The override precedence in __post_init__ matters and is deliberate: an explicit fallback_chain wins over everything (full caller control, mainly for tests); failing that, a single generator is treated as a one-generator chain (a convenience for "I don't need fallback, just use this one"); only if neither is supplied does it fall through to building the real default chain from config. This is never routed through get_fallback_chain(config) (the helper regular chat uses) — that helper pins config.groq_model, which is tuned for answer-quality on indexed chat, a different concern from "will this model reliably follow a strict text protocol."
Why AGENTIC_GROQ_MODEL is a separate constant, and why this specific model: the code comment above this constant documents a real empirical check (2026-08-31) against Groq's catalog — the shared default chat model threw 400 output_parse_failed on this exact prompt shape (some models actively refuse to emit non-JSON structured text once they detect what looks like a function-call request), another candidate hit rate limits before a fair test could even run, and qwen/qwen3.8-27b reliably produced a well-formed TOOL: name {...} line once the system prompt included one worked example (Part 2). This is a genuinely different tuning problem from "which model gives the best prose answer," which is exactly why it's a separate constant instead of reusing config.groq_model.

Part 5 — Events: how the loop talks to callers

The seam that lets a REPL show live tool-call activity without the loop itself knowing anything about terminals.

File: sleuth/retrieve/agent_session.py

@dataclass
class ToolCallEvent:
    name: str
    args: dict

@dataclass
class ToolResultEvent:
    name: str
    result: str

@dataclass
class AnswerEvent:
    text: str
    truncated: bool = False

AgentEvent = ToolCallEvent | ToolResultEvent | AnswerEvent
Concept — why three small dataclasses instead of just yielding text? The original one-shot run_agentic only ever yielded the final answer text — a caller watching it had no visibility into what the model was doing along the way, just silence followed by an answer. That's fine for a script piping output to a file, but actively bad for an interactive REPL: a user staring at a blank screen for several seconds with no indication whether the model is "thinking" or has hung has a worse experience than one who can see ⚙ grep(pattern='...') scroll by live. Three distinct event types — dataclasses, not just tagged dicts — give the REPL (or any future caller) a type it can isinstance()-check and render differently: a tool call gets a gear icon and dim styling, a tool result gets truncated preview text, a final answer gets full markdown-lite rendering (Part 11). AgentEvent = ToolCallEvent | ToolResultEvent | AnswerEvent is a union type — "this variable is one of these three shapes" — used as the element type of the AsyncIterator Part 1 introduced.

Crucially, nothing in this file ever calls print() or imports anything terminal-related. The loop's only communication with the outside world is yielding these three event types — which is exactly what makes the same class usable from a REPL that renders them as colored scrolling text (repl.py, Part 13), from a one-shot CLI command that just prints tool-call lines then the final answer (agentic.py, Part 7), and from a background ingestion task that discards every event except the final AnswerEvent's text (summarize_repo_agentic, see how-indexing-works.html Part 10) — three completely different consumers of the identical stream, none of which required a single change to this file.

Part 6 — ask(): the loop, message growth, and trimming

The actual multi-turn mechanism, and what changed to make repeated questions in one session sustainable.

File: sleuth/retrieve/agent_session.py

async def ask(self, question: str) -> AsyncIterator[AgentEvent]:
    self.messages.append({"role": "user", "content": question})

    for _ in range(MAX_ITERATIONS):
        try:
            response_text = await _call(self._chain, self.messages)
        except (httpx.HTTPStatusError, httpx.TransportError, RuntimeError):
            yield AnswerEvent(text=UNAVAILABLE_MESSAGE)
            return

        try:
            parsed = _parse_tool_call(response_text)
        except MalformedToolCall as exc:
            self.messages.append({"role": "assistant", "content": response_text})
            error_result = f"(error: malformed TOOL call — args must be valid JSON: {exc.parse_error})"
            self.messages.append({"role": "user", "content": f"Tool result: {error_result}"})
            self._trim_messages()
            continue

        if parsed is None:
            self.messages.append({"role": "assistant", "content": response_text})
            yield AnswerEvent(text=response_text)
            self._trim_messages()
            return

        self.messages.append({"role": "assistant", "content": response_text})
        name, args = parsed
        yield ToolCallEvent(name=name, args=args)
        result = _dispatch_tool(name, args, self.root)
        yield ToolResultEvent(name=name, result=result)
        self.messages.append({"role": "user", "content": f"Tool result: {result}"})
        self._trim_messages()
    ...
  • self.messages.append({"role": "user", "content": question}) — the very first line, and the single most important difference from the original one-shot version: self.messages is an instance attribute, not a local variable created fresh inside this function. A second call to ask() on the same AgentSession appends to whatever's already there from the first question's entire back-and-forth — the model genuinely sees the full prior conversation, tool calls and all, which is what lets a REPL user ask a follow-up question ("what does that function call") that only makes sense in light of what the first question already established.
  • The loop runs MAX_ITERATIONS (6) times per question. Each pass calls the model non-streaming (_call wraps chat_with_fallback(chain, messages, stream=False) and joins the result) — non-streaming is required here for the same reason pipeline-deep-dive.html Part 16 explains: the loop needs the model's complete response before it can decide "is this a tool call or a final answer," which is impossible to know from a partial stream of tokens.
  • Three distinct outcomes per iteration, each handled differently: a malformed tool call feeds the parse error back and continues (Part 2); a real final answer yields an AnswerEvent and returns immediately, ending the whole generator; a valid tool call yields ToolCallEvent then ToolResultEvent (in that order, deliberately — Part 5 explains why that ordering lets a REPL show "in flight" before showing the result), appends both to messages, and loops again.
  • Only httpx.HTTPStatusError/httpx.TransportError/RuntimeError (the last is what chat_with_fallback raises once every generator in the chain has failed) turn into the friendly UNAVAILABLE_MESSAGE answer — anything else propagates as a real exception, so a genuine bug in this code doesn't get silently mislabeled as "the model backend is down."
def _trim_messages(self) -> None:
    while len(self.messages) > self.max_messages:
        del self.messages[1:3]
Concept — why trimming exists at all, and why this specific approach The old one-shot run_agentic never needed this: messages was a fresh local list per call, thrown away the moment the function returned, so it could never grow unbounded across many questions. A multi-turn AgentSession is fundamentally different — a real interactive REPL session could run for dozens of questions, and every tool call/result pair from every one of them stays in messages unless something prunes it. Left unbounded, the prompt sent to the LLM on question 40 would include the full transcript of questions 1 through 39, which is both slow and eventually exceeds the model's context window entirely.

del self.messages[1:3] drops indices 1 and 2 — the oldest non-system message pair — every time the list exceeds max_messages, in a loop (so a single huge tool result can still trigger multiple trims in one pass if needed). Index 0 (the system prompt) is always preserved by starting the slice at 1. Deleting exactly a pair at a time, not a single message, is deliberate: an assistant's tool-call message and the following user-role "tool result" message are logically one unit — deleting only one half would leave a dangling, orphaned tool-result message with no corresponding call for the model to make sense of, or vice versa. This is the classic trade-off of any fixed context window: the model progressively "forgets" the earliest parts of a very long session, but never ends up with a malformed, half-orphaned message list.

Part 8 — repl.py's imports: why a whole new UI toolkit

The project's first external runtime dependency — what it buys, and how much smaller that turned out to be than first thought.

File: sleuth/repl.py, requirements.txt

Concept — why not just print()/input() like a normal script? Two things a bare input() loop cannot do, and they are the entire justification for a dependency here. First, line editing: input() gives you no left/right cursor movement, no word-wise deletion, no history recall — every terminal that feels usable implements those, and implementing them means putting the terminal into raw mode and decoding escape sequences by hand. Second, styled output with correct terminal detection: emitting ANSI color safely means knowing whether the destination is a real TTY, what it supports, and how to reset state cleanly.

prompt_toolkit is this project's first external runtime dependency (everything else is Python stdlib or a raw REST call via httpx) — a deliberate, acknowledged departure from the "hand-roll everything" philosophy.

_BLOCK_FONT = {
    "S": [" ███ ", "█    ", " ███ ", "    █", " ███ "],
    "L": ["█    ", "█    ", "█    ", "█    ", "█████"],
    ...
}

def _render_wordmark(word: str, spacing: int = 1) -> list[str]:
    rows = ["" for _ in range(5)]
    for ch in word:
        glyph = _BLOCK_FONT[ch]
        for i in range(5):
            rows[i] += glyph[i] + " " * spacing
    return rows

Rather than pulling in a figlet-style ASCII-art font library (another external dependency, for something purely cosmetic), the six letters SLEUTH actually needs are hand-drawn as a small dict: each letter maps to a list of 5 strings, one per row of a 5-row-tall block letter, using plain Unicode block-drawing characters (█). _render_wordmark then builds the whole word row-by-row: for each of the 5 rows, walk every letter in order and concatenate that letter's row-i string plus a spacing gap — the same "build one row across every letter, then move to the next row" approach a real typesetting system uses, just at a tiny, purpose-built scale (six letters, never any other text) that doesn't justify a whole font-rendering dependency.

Part 10 — The Transcript: printing into the terminal's own scrollback

The single most important architectural decision in this file — and it is a decision about what not to build.

File: sleuth/repl.py

Concept — a full-screen app has to reimplement the terminal Terminals have two screen buffers. The normal buffer is the one with scrollback: everything ever printed stays there, and the terminal itself handles scrolling it — mouse wheel, two-finger touchpad swipe, PageUp, click-and-drag text selection, copy, even the terminal's own find function. The alternate buffer is a blank fixed-size screen with no history, which is what full-screen programs like vim, htop and less switch into.

The moment a program enters the alternate buffer, it inherits responsibility for all of that: scrolling, following new output, selection. None of it comes for free anymore. That is a large amount of machinery to rebuild, and rebuilding it badly is worse than not having it.
This is what the first version got wrong. The original REPL was Application(full_screen=True) with a hand-written transcript pane: a read-only Buffer, a custom Lexer for per-line color, a following flag for tail-mode, and key bindings for line/page scrolling. It looked right and was fundamentally broken. Mouse scroll was disabled outright (mouse_support=False), so no wheel or touchpad event ever reached the app. Worse, it could not have worked even if enabled: prompt_toolkit's Window._scroll() recomputes the scroll position from the cursor on every repaint, the transcript pinned the cursor to its own last line, and the spinner forced a repaint every 80ms — so any scroll position the user reached was snapped back to the bottom within one frame. See Part 17 for the full post-mortem.

Claude Code, Codex and Hermes all sidestep this entirely: they never enter the alternate buffer. The transcript is simply printed, like any ordinary command's output, and only the input line is a managed widget. Scrolling works because the terminal is doing it. That is now what SLEUTH does, and it is why _Transcript shrank to this: 

class _Transcript:
    def __init__(self, output: Output | None = None):
        self.lines: list[str] = []
        self._output = output

    def _emit(self, fragments: list[tuple[str, str]]) -> None:
        self.lines.append("".join(text for _, text in fragments))
        print_formatted_text(
            FormattedText(fragments),
            style=STYLE,
            output=self._output,
        )

    def append(self, text: str, style: str = "") -> None:
        for line in text.split("\n"):
            self._emit([(style, line)])
  • print_formatted_text is prompt_toolkit's styled equivalent of print(). It takes the same (style, text) fragment list the old Lexer produced and writes it to the terminal with real ANSI color — so Part 11's markdown renderer needed no changes at all. The fragment format was always the right abstraction; only the thing consuming it changed.
  • There is no Buffer, no Lexer, no Document, no fragments list, no following flag, no _sync(), no scroll(), no invalidate(). Roughly 200 lines became 15. Everything they existed to do, the terminal already did better.
  • self.lines survives, but only as a record of what was printed — not as the thing being rendered. It has two jobs: run_repl() returns it (tests assert against it, since a DummyOutput swallows real rendering), and it makes this class trivially testable. Nothing reads it to draw the screen.
  • output is injectable purely for testing. Real usage passes None, meaning "the actual terminal."
The tradeoff, stated honestly. The bordered input box is no longer pinned to the bottom of the screen — it scrolls up with the content, exactly like Claude Code's does. That is the price of letting the terminal own scrolling, and it is a price worth paying: a pinned box that fights your touchpad is worse than an unpinned one that doesn't.

append_markdown and append_lines are thin variants of append, both routing to the same _emit. One extra method deserves mention: record_question(), which appends the user's question to self.lines without printing it — because the prompt widget has already drawn ❯ <question> into the scrollback as part of accepting the keystrokes. Printing it again would double it on screen.

Part 11 — A hand-rolled markdown-lite renderer

The model's answers can contain **bold**, `code`, headings, bullets — turning that into real terminal styling without a markdown library.

File: sleuth/repl.py

_INLINE_CODE_RE = re.compile(r"`([^`]+)`")
_BOLD_RE = re.compile(r"\*\*([^*]+)\*\*")
_HEADING_RE = re.compile(r"^(#{1,6})\s+(.*)$")
_BULLET_RE = re.compile(r"^(\s*)([-*])\s+(.*)$")

def _render_inline_markdown(text: str, base_style: str) -> list[tuple[str, str]]:
    fragments = []
    pos = 0
    pattern = re.compile(f"{_BOLD_RE.pattern}|{_INLINE_CODE_RE.pattern}")
    for match in pattern.finditer(text):
        if match.start() > pos:
            fragments.append((base_style, text[pos:match.start()]))
        if match.group(1) is not None:
            fragments.append(("class:answer.bold", match.group(1)))
        else:
            fragments.append(("class:answer.code", match.group(2)))
        pos = match.end()
    if pos < len(text):
        fragments.append((base_style, text[pos:]))
    return fragments or [(base_style, text)]
Concept — why not just pull in a real markdown library? A real markdown parser (CommonMark-compliant) handles tables, nested blockquotes, link syntax, footnotes — none of which ever actually appear in this model's answers, which are always prose paragraphs and short lists. Pulling in a full dependency to handle cases that structurally can't occur here would be adding weight for nothing. Instead this is a deliberately tiny "markdown-lite" subset: headings, bold, inline code, and bullets — exactly the constructs a chat LLM's plain-prose answers actually use, hand-matched with four small regexes.

_render_inline_markdown is the interesting part: it can't just run the bold regex over the whole line and then separately run the code regex, because a span like **bold `code`** would have its inner backticks silently missed once the bold pass has already consumed the entire match as one opaque bold fragment. Instead, one combined pattern (bold_pattern|code_pattern) is scanned once, left to right, via finditer — at each match, whichever pattern actually matched (match.group(1) is non-None for bold, None for code, since only one alternative in an A|B regex ever actually captures) determines which style class the matched span gets, and any plain text between matches is appended with the caller's base_style untouched. _render_markdown_line layers heading/bullet detection on top, per whole line, before handing the remainder off to this inline function.

Part 12 — The spinner: repainting one terminal line in place

A "thinking" indicator that must never touch the transcript — because the version that did, corrupted it.

File: sleuth/repl.py

The original spinner silently ate the transcript. It worked by appending a blank transcript line, then overwriting that line on a timer via replace_last(). Two things made that fatal. First, start() was a no-op if a task was already running (if self._task is None), but process_question called start() again after every tool call without stopping it first — so the original timer kept running. Second, replace_last() overwrites whatever line is currently last, and by then that was no longer the spinner's placeholder: it was real content appended in the meantime. The running timer overwrote genuine tool output with ⠙ thinking..., and stop()'s transcript.pop() then deleted a real line. With three tool calls in one turn, everything after the first was destroyed. Part 17 has the captured proof.
Concept — in-place animation with three escape codes Now that output goes to normal scrollback (Part 10), the spinner can do what command-line tools have always done: write text, then move the cursor back over it and overwrite it. Three terminal operations are all it takes — cursor_backward(n) to step back over what was written, erase_end_of_line() to clear it, then write the next frame. The animation happens on one physical line that never becomes part of the scrollback history, so there is nothing for it to corrupt. 
class _Spinner:
    def _write(self, text: str) -> None:
        if self._output is None:
            return
        if self._width:
            self._output.cursor_backward(self._width)
            self._output.erase_end_of_line()
        self._output.write(text)
        self._output.flush()
        self._width = len(text)

    async def _spin(self) -> None:
        started = time.monotonic()
        i = 0
        try:
            while True:
                frame = _SPINNER_FRAMES[i % len(_SPINNER_FRAMES)]
                elapsed = time.monotonic() - started
                self._write(f"{frame} thinking… {elapsed:.0f}s (ctrl-c to interrupt)")
                i += 1
                await asyncio.sleep(_SPINNER_INTERVAL)
        except asyncio.CancelledError:
            raise
        finally:
            self._clear()

    def start(self) -> None:
        if self._task is None or self._task.done():
            self._task = asyncio.ensure_future(self._spin())
  • self._width tracks how many characters were last written, which is what makes cursor_backward land in exactly the right place. Frames differ in length (the elapsed seconds grow from 1s to 10s), so a fixed backward step would leave stale characters behind.
  • The finally: self._clear() matters more than it looks. Cancellation is the normal way this task ends, and without the finally, a cancelled spinner would leave a half-drawn frame sitting on the line where real output is about to be printed. Note also except asyncio.CancelledError: raise — deliberately re-raised, not swallowed, so the task is correctly recorded as cancelled rather than as completed normally.
  • self._task.done() in start() is the fix for the bug above: a task that has finished or been cancelled no longer blocks a restart. The old if self._task is None left a dead task in place, so subsequent start() calls silently did nothing while the real spinner had already stopped.
  • The elapsed-seconds counter is a deliberate honesty feature. An agentic turn can legitimately run for tens of seconds (up to six non-streaming model calls), and a spinner with a visibly ticking timer is the difference between "it's working" and "it's frozen" — which was the user's original complaint. It also advertises ctrl-c to interrupt, which is now true (Part 13).
  • if self._output is None: return makes the spinner a silent no-op under a test harness that passes no output, so tests never depend on animation timing.

Part 13 — run_repl: the prompt loop and interruptible turns

An ordinary while True loop — plus the one genuinely hard problem: making a long model call cancellable.

File: sleuth/repl.py

Concept — with the terminal owning the screen, the loop gets boring The old version needed a scheduler. Because it was one long-lived Application, submitting a question happened inside a key handler, and key handlers must not block for seconds — so each turn became a background task, which then needed a queue to stop two turns interleaving their output.

A scrollback REPL has no such problem. prompt_async() asks for one line and returns it; the prompt widget is torn down while the turn runs and rebuilt for the next question. Turns are therefore sequential by construction — there is no second turn to interleave with, and the whole schedule()/pending machinery disappears. 
prompt_session: PromptSession[str] = PromptSession(
    message=FormattedText([("class:prompt", "❯ ")]),
    style=STYLE,
    history=InMemoryHistory(),
    multiline=False,
    key_bindings=kb,
    input=input,
    output=output,
)

while True:
    try:
        question = await prompt_session.prompt_async()
    except KeyboardInterrupt:
        continue          # Ctrl-C at an empty prompt: clear the line, like a shell
    except EOFError:
        break             # Ctrl-D: leave

    question = question.strip()
    if not question:
        continue
    if question.lower() in EXIT_COMMANDS:
        transcript.record_question(question)
        break

    transcript.record_question(question)
    await run_turn_interruptibly(question)
  • history=InMemoryHistory() gives up-arrow recall of previous questions — which the old version could never have, because it bound up globally to transcript scrolling and thus stole the key from its own input box (Part 14).
  • KeyboardInterrupt and EOFError are how prompt_toolkit reports Ctrl-C and Ctrl-D while waiting for input. Distinguishing them matters: Ctrl-C at an idle prompt should clear the line and continue (shell behavior), whereas Ctrl-D means "I'm done."
  • await run_turn_interruptibly(question) is a plain await — the loop simply stops here until the turn finishes. No queue, no ordering guarantees to maintain, nothing to get subtly wrong.

Making a turn interruptible

Ctrl-C used to be queued behind the very thing it was meant to cancel. The old key binding did schedule(do_exit), and schedule's runner began with await previous — so pressing Ctrl-C appended an exit request to the end of the queue, behind the in-flight turn. Since a turn can run up to MAX_ITERATIONS (6) non-streaming model calls, each with a 60-second HTTP timeout plus a retry, the REPL could be unquittable and uncancellable for several minutes. There was no per-turn cancellation of any kind. 
async def run_turn_interruptibly(question: str) -> None:
    task = asyncio.ensure_future(process_question(question))

    def on_sigint(_signum, _frame) -> None:
        task.cancel()

    previous_handler = None
    installed = False
    try:
        previous_handler = signal.signal(signal.SIGINT, on_sigint)
        installed = True
    except (ValueError, OSError):
        pass

    try:
        await task
    except asyncio.CancelledError:
        await spinner.stop()
        transcript.append("  ⏹ interrupted", "class:dim")
        transcript.append("")
    finally:
        if installed:
            signal.signal(signal.SIGINT, previous_handler)
  • The turn runs as a real asyncio task specifically so it has a cancel() method. cancel() raises CancelledError at the coroutine's next await point — which, mid-HTTP-request, is essentially immediate.
  • Why a raw signal handler rather than a prompt_toolkit key binding? Because while the turn is running, the prompt widget is not reading input — prompt_toolkit's key handling is not active at all, so there is no binding to trigger. The OS-level SIGINT that Ctrl-C generates is the only signal that still arrives.
  • The handler is installed for the turn's duration and the previous one is restored in finally — leaving a permanent handler installed would break Ctrl-C handling for the prompt itself (which relies on prompt_toolkit's own behavior) after the first question.
  • except (ValueError, OSError): pass is a deliberate graceful degradation. signal.signal() only works on the main thread and is unavailable in some embedded hosts; there, the turn is simply not interruptible rather than crashing at startup.
  • Catching CancelledError around the await is what turns a hard cancellation into a clean, visible ⏹ interrupted line, after which the loop continues to the next prompt — the session is not torn down.
async def process_question(question: str) -> None:
    spinner.start()
    try:
        async for event in session.ask(question):
            await spinner.stop()
            if isinstance(event, ToolCallEvent):
                transcript.append(_format_tool_call(event), "class:tool")
                spinner.start()
            elif isinstance(event, ToolResultEvent):
                transcript.append(_format_tool_result(event), "class:dim")
                spinner.start()
            elif isinstance(event, AnswerEvent):
                transcript.append_markdown(event.text, prefix=[("class:accent", "● ")])
                ...
    finally:
        await spinner.stop()
    transcript.append("")
  • Still the direct payoff of Part 5's event design: one async for, one isinstance check per event type. AgentSession was never touched by the REPL rewrite — the event contract is the entire interface between them.
  • Note await spinner.stop() now runs unconditionally at the top of every iteration, replacing the old first_event flag. Combined with the explicit start() after each event, the spinner is always stopped before anything is printed and restarted only afterward — which is precisely the invariant whose absence corrupted the transcript before (Part 12).
  • The try/finally guarantees the spinner is stopped even if the turn is cancelled mid-stream, so a cancelled turn can never leave an animating spinner behind.

  • The KeyBindings object is still created and passed to the PromptSession, but it registers nothing. It exists as the extension point for genuinely REPL-specific keys later (a / command menu, say) without re-plumbing anything.
  • Every key that previously needed a custom binding now works better by falling through to either the terminal or prompt_toolkit's own defaults. This is the payoff of Part 10's decision, made concrete: the fix for "the keybindings don't work" was to stop writing keybindings.
  • Ctrl-C and Ctrl-D are no longer bindings at all — they surface as KeyboardInterrupt and EOFError from prompt_async() while idle, and Ctrl-C becomes a real SIGINT during a turn (Part 13). Two different mechanisms for two genuinely different situations.

Part 15 — Wired into the CLI: one line

How this whole subsystem becomes reachable by typing nothing but `sleuth`.

File: sleuth/cli.py

parser = argparse.ArgumentParser(prog="sleuth")

async def main(argv: list[str] | None = None) -> None:
    args = _build_parser().parse_args(argv)

        await run_repl(".", config)

    ...
  • required=False on add_subparsers is the one flag that makes this possible at all — by default, argparse subparsers are required, meaning running the bare program name with no subcommand is an error. Turning that off is what lets args.command come back as None instead of argparse exiting with a usage error first.
  • if args.command is None: await run_repl(".", config); return — the entire routing decision, right at the top of main(), before any database connection is ever opened. "." is passed as the path — the REPL always scopes itself to the current working directory when launched this way, exactly matching how cding into a project and typing claude or hermes with no arguments works for those tools, which is the explicit UX this was modeled on.
  • Notice this branch returns before get_connection(config.database_url) is ever called (further down in main(), used by add/list/ ask/eval) — the REPL, like sleuth agentic, never touches Postgres at all. This is why the REPL/agentic path works identically from either the WSL dev environment or a native Windows Python install, unlike the DB-backed commands, which this project's own memory notes flag as needing WSL specifically because of a Windows-to-Docker port-forwarding issue.

That's the whole agentic subsystem, start to finish. Notice, same as the other two companion documents conclude: most of the genuinely hard engineering here isn't "AI" at all — it's a small hand-rolled text protocol, a sandboxing guard, message-history trimming, and correct subprocess/terminal plumbing. The two genuinely intelligent steps (the model deciding what to look at, and writing the final answer) are each a handful of lines; everything else in this document is the careful plumbing that makes those two steps usable, safe, and pleasant to actually sit in front of.

And — the lesson of Part 17 — the plumbing is also where every single real bug turned out to live. Not one of the six was in the prompt, the protocol, or the model's reasoning.

Part 17 — Post-mortem: six bugs, how they were found and proven fixed

The REPL "got stuck," scrolling didn't work, and a raw traceback appeared mid-answer. Here is what was actually wrong.

Files: sleuth/repl.py, sleuth/retrieve/agent_session.py, sleuth/ingest/clone.py

Concept — one search triggered three bugs at once The reported symptom was a single agentic question producing a wall of Python traceback plus (invalid pattern or rg error: ...). Three independent defects stacked: the model passed glob: "*", which dragged ~100k third-party library files into the search (bug 4); one of those files contained a UTF-8 curly quote that native Windows Python couldn't decode (bug 3); and a Linux-created symlink in the same tree made ripgrep exit 2, which caused SLEUTH to discard every real match and tell the model its search was invalid (bug 5). The model then retried the "failed" search until it ran out of iterations — the "gets stuck" symptom.

The six bugs

#BugSymptomRoot cause
1 Touchpad/wheel scroll did nothing Two-finger scroll had no effect mouse_support=False, so prompt_toolkit never emitted scroll events. Unfixable in that design anyway: Window._scroll() recomputes scroll from the cursor every repaint, and the transcript pinned the cursor to its own tail while the spinner forced a repaint every 80ms
2 Screen froze / output vanished mid-answer "The screen gets stuck" The spinner was a transcript line mutated on a timer. start() no-op'd if a task existed, but was re-called after every tool call without stopping the old one — so the live timer overwrote real content via replace_last(), and stop()'s pop() deleted a genuine line
3 UnicodeDecodeError traceback Raw thread traceback printed over the REPL text=True with no encoding= decodes with the locale codepage (cp1252 on Windows). A UTF-8 curly quote raised on subprocess's reader thread, uncatchable, leaving proc.stdout = None
4 420× output blowup Context flooded with library code Any explicit --glob switches ripgrep out of gitignore-respecting mode, so the no-op glob="*" un-ignored .venv and node_modules
5 Real matches thrown away (invalid pattern or rg error) on a valid pattern; model retried until iteration cap rg exits 2 if any path is unreadable (WSL symlinks, os error 1920). Exit 2 was treated as total failure even with matches on stdout
6 Citations mangled on Windows Absolute host paths leaked into model context line.split(":", 2) broke on the drive-letter colon in C:\repo\a.py:1:x, so relative_to() always failed
Bug 6 was not reported — it was found while verifying the others. It surfaced in the raw output of the cp1252 reproduction script, where a match line came back with a full C:\Users\...\Temp\... path still attached. Worth noting because it had been silently wrong on every Windows run since the tool was written.

How each fix was proven, not assumed

  • Reproduce before fixing. Bug 3's exact traceback was reproduced first — same 0x9d byte, same subprocess.py:1599 _readerthread frame as the user's report. That run also revealed the downstream AttributeError: 'NoneType' object has no attribute 'splitlines', confirming the output was silently lost rather than merely garbled.
  • Measure claims, don't estimate them. Bug 4's "420×" is a measurement: 2,440,969 bytes with --glob '*' versus 5,815 bytes without, and 12,853 versus 0 .venv files.
  • Test the fix against the old code. Every regression test was run against the reverted source and confirmed to fail there. This caught a bad test: the first version of the bug-2 spinner test passed against the buggy code, because the existing FakeSession yields all events synchronously, so the spinner's timer never got scheduled mid-turn. Rewritten with real awaits between events, it failed correctly — and the captured failure showed alpha_file.py and every later event replaced by ⠙ thinking..., exactly the predicted corruption.
  • Verify where the bug actually lives. Bugs 3's tests cannot fail under WSL, whose locale is already UTF-8. They were verified separately against native Windows Python with cp1252: FAIL before, PASS after.
  • Test the real rendering path. The REPL rewrite was smoke-tested through a real PTY with an actual Vt100_Output (not DummyOutput), confirming banner, ANSI color, markdown, in-place spinner, and clean exit — because a DummyOutput would have hidden any escape-code mistake.
  • Guard the fix from over-reach. Two tests exist purely to pin the limits of fixes: a real glob (*.py) must still filter (bug 4), and exit 2 with empty stdout must still report an error so the model can correct its own regex (bug 5).
Final state: 206 tests passing, 0 failing. The suite also went from "164 passed" to "206 passed" over these two rounds — most of the increase is these regression tests.

The rejected fix, and why it was rejected

Bug 4's first attempted fix was an exclusion list: --glob '!.venv' --glob '!node_modules'. It was measured, and it leaked 7,202 files from .venv-win/ — a third virtualenv directory that simply wasn't on the list. That is the whole argument against denylists in one number: they encode a snapshot of what someone remembered, and .gitignore already encodes the truth. The shipped fix drops the no-op glob so ripgrep's own ignore logic is never overridden in the first place.

Concept — the pattern shared by five of six bugs Bugs 1, 2, 3, 5 and 6 all have the same shape: an error that could not be seen from where it happened. Mouse events that were never emitted. A timer overwriting lines with no error. A decode exception on a thread nobody was watching. A warning exit code indistinguishable from a fatal one. A path parse that silently produced a wrong-but-plausible string. None of them threw an exception into code that could handle it — which is exactly why they survived a green test suite, and why "reproduce it first, then prove the test fails without the fix" was the only reliable way through.
