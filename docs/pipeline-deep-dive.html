Part 0 — The 30,000ft view

What is SLEUTH actually doing, mechanically, before we open a single file?

SLEUTH answers questions about a codebase by finding the most relevant pieces of code and handing them to an LLM as context. That's the entire idea — this pattern is called RAG (Retrieval-Augmented Generation). The LLM doesn't "know" your repo; it has never seen it during training. Instead, every time you ask a question, SLEUTH:

  1. Turns your question into a vector (a long list of numbers) using an embedding model.
  2. Searches a database of pre-computed vectors — one per function/class/method in the repo — for the ones geometrically closest to your question's vector.
  3. Takes the actual source code behind those closest vectors and pastes it into a prompt.
  4. Sends that prompt (question + relevant code) to a chat LLM and streams back the answer.

There are two completely different modes for step 1-2, and this trips people up, so nail it down now:

ModeWhen usedHow it finds relevant code
Indexed (sleuth add then sleuth ask) Remote GitHub repo, asked more than once Upfront: clone → parse → chunk → embed → store in Postgres. Query time: embed the question, vector-search Postgres.
Agentic / live (sleuth agentic) Your current local directory, one-off question, no indexing wait No embeddings, no DB at all. The LLM itself decides to call grep/list_files/ read_file tools in a loop, like a human would explore the repo.

Part 1 — Python building blocks used everywhere

Five Python features show up constantly across this codebase. If these click, the rest of the code reads almost like English. Skip ahead if you already know them cold.

1. @dataclass — a class that's just a labeled bag of fields

Concept Lots of code needs a small structured object — "a chunk has a file path, a symbol name, a kind, a start line, an end line, and the code text." Writing that as a plain class means hand-writing __init__, plus __repr__ if you want it to print nicely, plus __eq__ if you want to compare two instances. @dataclass generates all of that for you from just the field list. 
@dataclass
class Chunk:
    file_path: str
    symbol_name: str | None
    kind: str  # 'function' | 'method' | 'class' | 'module'
    start_line: int
    end_line: int
    code_text: str

This one declaration is equivalent to writing an __init__(self, file_path, symbol_name, kind, start_line, end_line, code_text) that assigns each argument to self.xxx, plus a __repr__ that prints Chunk(file_path='sleuth/db.py', symbol_name='get_connection', ...), plus an __eq__ that compares field-by-field. You construct it exactly like a normal class: Chunk(file_path="x.py", symbol_name="foo", kind="function", start_line=1, end_line=5, code_text="...").

@dataclass(frozen=True) (used for Config in Part 2) additionally makes the instance immutable — trying config.database_url = "x" after construction raises FrozenInstanceError. That's a deliberate design choice, not a Python default: Config is supposed to be handed around read-only so no module can quietly mutate shared settings.

2. Type hints (str | None, list[Chunk]) — documentation the tools can check

Concept Python doesn't enforce types at runtime by default — you could pass a number where Chunk expects a string and nothing crashes until something downstream chokes on it. Type hints don't change that; they're metadata a human (or an IDE, or a linter like mypy) reads to know what's expected, without running the code.

str | None reads as "a string, or None". This is the modern spelling (Python 3.10+) of what used to be written Optional[str]. You'll see it on symbol_name: str | None everywhere — a chunk for a top-level function has no enclosing class, so symbol_name is just the function name, but a "junk"/module-level chunk (leftover code that isn't a function or class) has no meaningful symbol name at all, hence None.

list[Chunk], dict[tuple[str, str], str], AsyncIterator[str] — these are generic type hints: "a list of Chunk objects", "a dict whose keys are (str, str) tuples and values are str", "something you can iterate over asynchronously that yields strings". You'll see this exact pattern in store.get_existing_hashes's return type: dict[tuple[str, str | None], str] — a dict mapping (file_path, symbol_name) pairs to a content_hash string. Reading the type hint alone tells you the shape of the data without reading the body.

3. Abstract Base Classes (ABC) — "here's the shape every implementation must have"

Concept SLEUTH supports two embedding providers in the design (Voyage, NIM — though Part 8 explains why only Voyage got built) and two LLM generation providers (Groq, NIM) that actually did both get built. The rest of the codebase (the ingest pipeline, the answer builder) shouldn't need to know or care which one is active — it just wants "a thing I can call .embed_batch(texts) on" or "a thing I can call .chat(messages) on". An ABC is Python's way of declaring that contract formally: a base class that cannot be instantiated directly and that forces every subclass to implement specific methods, or Python raises TypeError at construction time. 

class Embedder(ABC):
    model_name: str
    dim: int

    @abstractmethod
    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
        ...


class VoyageEmbedder(Embedder):
    model_name = "voyage-code-3"
    dim = 1024

    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
        ...  # actual implementation

Try to write class Broken(Embedder): pass (no embed_batch override) and then Broken() — Python refuses with TypeError: Can't instantiate abstract class Broken with abstract method embed_batch. This is the same pattern used for sleuth/llm/generate.py's Generator ABC, with GroqGenerator and NimGenerator as the two concrete subclasses — both only need to implement one method, _url(), because Generator.chat() itself is shared logic written once on the base class (this is the practical payoff of ABCs: shared logic lives in one place, provider-specific bits are the only thing each subclass supplies).

4. async/await and asyncio — doing many slow things at once

Concept Most of SLEUTH's real work is waiting on the network: calling the Voyage API to embed hundreds of code chunks, calling Groq/NIM to generate text. A normal ("synchronous") Python program calling these one at a time would sit idle waiting for each HTTP response before starting the next request — if embedding 500 chunks takes 200ms each sequentially, that's 100 seconds of mostly just waiting. asyncio lets Python start many requests, then while each one is waiting on the network, work on (or start) another, without needing real OS threads. It's cooperative: a function marked async def can pause itself at an await point and let something else run, then resume later when its result is ready. 

async def embed_batch(self, texts: list[str]) -> list[list[float]]:
    batches = [texts[i : i + self.batch_size] for i in range(0, len(texts), self.batch_size)]
    semaphore = asyncio.Semaphore(self.max_concurrency)

    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(
            *(self._embed_one_batch(client, semaphore, batch) for batch in batches)
        )

Line by line: texts (say 500 code chunks) is sliced into batches of batch_size (128) — Voyage's API accepts a batch per HTTP call rather than one chunk per call, so this cuts 500 network round trips down to ~4. asyncio.Semaphore(max_concurrency) is a counter-based lock: it allows at most max_concurrency (5) coroutines to be "inside" it simultaneously — everyone else waits. Without it, all 4 batches would fire simultaneously; with 500 chunks split across many more batches that number could spike and get you rate-limited. asyncio.gather(*(...)) takes a list of not-yet-run coroutines (one per batch, each wrapped by self._embed_one_batch) and runs them concurrently, returning a list of results in the same order once all of them finish. The * unpacks the generator expression into separate positional arguments — gather(coro1, coro2, coro3) rather than gather([coro1, coro2, coro3]), because that's the signature gather expects.

The semaphore is used inside _embed_one_batch as async with semaphore: ... — "wait until a slot is free, take it, run the HTTP call, release the slot when done (even on exception)." That's the concurrency-bounding mechanism: many batches queued, only 5 in flight to Voyage at once.

async with httpx.AsyncClient() as client: is an async context manager — same idea as a regular with open(file) as f: (guarantees cleanup happens even if an exception is raised inside the block), but for something that needs await to set up/tear down, like an HTTP connection pool that needs to asynchronously close its sockets on exit.

5. Generators & yield — producing a stream of values lazily

Concept When you ask SLEUTH a question, you don't want to stare at a blank terminal until the entire answer is generated, then have it all dumped at once — you want to see tokens appear as the LLM produces them, like ChatGPT's UI. A generator function (one using yield instead of return) doesn't compute its whole result upfront; each call to it hands back a lazy iterator that produces one value at a time, on demand, pausing its own execution between values. 

async def _stream_chat(self, client, messages) -> AsyncIterator[str]:
    ...
    async with client.stream("POST", self._url(), headers=headers, json=payload) as response:
        response.raise_for_status()
        async for line in response.aiter_lines():
            if not line.startswith("data: "):
                continue
            data = line[len("data: "):]
            if data == "[DONE]":
                break
            delta = json.loads(data)["choices"][0]["delta"].get("content")
            if delta:
                yield delta

This is an async generator — async def combined with yield inside. Groq/NIM's streaming API sends the response as Server-Sent Events: a sequence of lines each prefixed data: {...json...}, ending with a line data: [DONE]. This function reads that stream line by line (async for line in response.aiter_lines()) and, for every line that carries an actual text token, yields just that token string. The caller (sleuth ask's CLI loop, or stream_answer) does async for token in generator.chat(...): print(token, end="") — each iteration of that loop resumes this generator right after its last yield, gets the next token, prints it immediately, and repeats. That's the entire mechanism behind the token-by-token streaming you see in the terminal.

Part 2 — Config & secrets

The one place every module goes to ask "what are my credentials / settings?"

Files: sleuth/config.py

Concept — why not just os.environ["VOYAGE_API_KEY"] everywhere? Two reasons. First, fail fast with a clear error: if you forget to set GROQ_API_KEY, you want the program to refuse to start with "Missing required environment variable(s): GROQ_API_KEY" — not crash 40 seconds into an ingest run with a cryptic 401 from Groq's API. Second, a single typed object instead of scattered os.environ calls: every module that needs settings receives one Config object as a function argument, instead of reaching into environment variables directly. This makes testing trivial (just construct a Config(...) by hand in a test, no environment-variable juggling) and makes it impossible for a module to accidentally read a stale or wrong env var name, because it's not touching os.environ at all — it only sees whatever fields Config exposes. 
load_dotenv()

DEFAULT_GROQ_MODEL = "openai/gpt-oss-120b"

@dataclass(frozen=True)

def load_config() -> Config:
    missing = [name for name in REQUIRED_VARS if not os.environ.get(name)]
    if missing:
        raise ConfigError(f"Missing required environment variable(s): {', '.join(missing)}")

    return Config(
        voyage_api_key=os.environ["VOYAGE_API_KEY"],
        groq_api_key=os.environ["GROQ_API_KEY"],
        groq_model=os.environ.get("GROQ_MODEL", DEFAULT_GROQ_MODEL),
        database_url=os.environ["DATABASE_URL"],
        generation_provider=os.environ.get("GENERATION_PROVIDER", "groq"),
        nim_api_key=os.environ.get("NIM_API_KEY") or None,
    )
  • load_dotenv() (from the python-dotenv package) reads a .env file in the project root and copies its key=value lines into os.environ as if they'd been set in the shell. This runs at import time — the moment anything does from sleuth.config import ..., this line executes, so by the time any other code asks for env vars, .env has already been loaded.
  • REQUIRED_VARS is a tuple of the three env-var names that must exist for the app to function at all: Voyage (embeddings), Groq (default generation), and the Postgres connection string. Notice GROQ_MODEL and NIM_API_KEY are not in this list — they're optional, with sensible defaults/fallback-off behavior.
  • missing = [name for name in REQUIRED_VARS if not os.environ.get(name)] — a list comprehension. Reads as: "for each required name, keep it in the list if os.environ.get(name) is falsy" (missing entirely, or set to an empty string). os.environ.get(name) (vs. os.environ[name]) returns None instead of raising KeyError when the var doesn't exist — needed here since we're checking for absence, not assuming presence.
  • If missing is non-empty, raise ConfigError with all the missing names joined into one message — better than crashing on the first one found and forcing the user to fix-and-rerun three separate times.
  • Only after that check passes does it actually construct the Config. At this point every "required" access via os.environ["X"] (square brackets, not .get) is guaranteed safe.
  • nim_api_key=os.environ.get("NIM_API_KEY") or None — a small trick: if the env var is unset, .get() already returns None; but if it's set to an empty string "" (falsy but not None), "" or None evaluates to None too. So both "unset" and "set but blank" normalize to the same None, which downstream code (the fallback-chain logic in Part 13) treats uniformly as "NIM fallback is not configured."
Why frozen=True matters here specifically: Config gets passed into nearly every function in the codebase (ingest_repo(github_url, conn, config), stream_answer(question, repo_id, conn, config), etc.). If it were mutable, any one of those functions could reassign config.groq_model = "something else" and every other function holding a reference to that same object would silently see the changed value too — a classic action-at-a-distance bug. Freezing it makes that category of bug impossible: the only way to get a "different" Config is to construct a new one.

Part 3 — Postgres, pgvector, and why HNSW

The database schema, and the actual math/data-structure idea behind fast vector search.

The schema

CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE IF NOT EXISTS repos (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    github_url      text NOT NULL,
    status          text NOT NULL DEFAULT 'pending',
    error_message   text,
    indexed_at      timestamptz,
    embedding_model text,
    embedding_dim   int
);

CREATE TABLE IF NOT EXISTS chunks (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    repo_id       uuid NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    file_path     text NOT NULL,
    symbol_name   text,
    kind          text NOT NULL,
    start_line    int NOT NULL,
    end_line      int NOT NULL,
    code_text     text NOT NULL,
    content_hash  text NOT NULL,
    embedding     vector(1024) NOT NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS chunks_identity_idx
    ON chunks (repo_id, file_path, COALESCE(symbol_name, ''));

CREATE INDEX IF NOT EXISTS chunks_embedding_idx
    ON chunks USING hnsw (embedding vector_cosine_ops);
  • CREATE EXTENSION IF NOT EXISTS vector loads pgvector, a Postgres extension that adds a new column type, vector(N) — a fixed-length array of floats Postgres understands natively, plus distance operators (<=> for cosine distance, used in Part 12) and index types built specifically for nearest-neighbor search on those arrays.
  • pgcrypto gives us gen_random_uuid(), used as the default for both primary keys — every repo and every chunk gets a random UUID instead of an auto-incrementing integer (UUIDs are collision-safe across machines/environments without coordination, which matters less here with one DB, but it's the standard default for anything Supabase-hosted).
  • repos.status is a simple state machine as a text column: pending → indexing → ready, or → failed with error_message populated. There's no separate enum type or state-machine library — just a string field that the ingest pipeline (Part 11) writes to at each stage. Simple, and grep-able.
  • chunks.embedding vector(1024) — fixed width 1024 because Voyage's voyage-code-3 model always returns 1024-dimensional vectors. pgvector columns must declare their dimensionality upfront (unlike a plain array column); this is exactly why the original design had separate chunks_1024/chunks_2048 tables to support a second embedding model with a different dimension count — since only Voyage got implemented, there's just the one chunks table.
  • chunks_identity_idx is a unique index, not just a regular index — it makes (repo_id, file_path, symbol_name-or-empty-string) a de-facto composite key. This is what lets upsert_chunks (Part 10) use ON CONFLICT (...) DO UPDATE: re-running the indexer on a repo that changed doesn't create duplicate rows for the same function, it updates the existing row in place. COALESCE(symbol_name, '') exists because SQL's uniqueness/equality checks treat NULL as "unknown" rather than a comparable value — two rows with symbol_name = NULL are NOT considered duplicates of each other by a plain unique index, so module-level "junk" chunks (which legitimately have no symbol name) needed the NULL coalesced to an empty string to participate in uniqueness correctly.

Why HNSW — the actual idea, not just the acronym

Concept — the nearest-neighbor problem Once you have thousands of 1024-number vectors, and a new "query" vector (the embedded question), you need the K vectors geometrically closest to it. The naive approach — compute the distance from the query to every single stored vector, then sort — is called a brute-force / flat scan. It's exact (always finds the true nearest neighbors) and it's fine for a few thousand rows, but it's O(n) per query: double the chunks, double the search time, linearly, forever. For a codebase with 50,000 chunks queried repeatedly, that adds up.
Concept — Navigable Small World (NSW) graphs Instead of a flat list, imagine every vector as a node in a graph, connected to a handful of its nearest neighbors — like a social network where you're "friends" with people similar to you. This is the "six degrees of separation" idea applied to vectors: to find something close to your query, you don't scan everyone — you start at some node, greedily hop to whichever of your current node's neighbors is closer to the query than you are, and repeat. You "walk" toward the target through short hops, the same way you might navigate to a stranger's house by asking a friend, who asks their friend closer to that neighborhood, and so on. This turns most searches from O(n) into something close to O(log n) — dramatically faster at scale — at the cost of no longer being guaranteed exact (it's an approximate nearest neighbor search; in practice it's extremely close to exact for well-tuned graphs).
Concept — the "H" in HNSW: hierarchy Plain NSW still has a problem: if your graph is huge and mostly local (each node only connected to near neighbors), a search that starts far from the target still needs many hops to cross the space — like still needing dozens of local "ask a friend" hops to get from one side of a city to the other, with no highways. HNSW fixes this by building multiple layers of the same graph: the top layer has very few nodes with long-range connections (like a highway), each layer below has progressively more nodes and shorter connections (a city street, then a neighborhood street). A search starts at the sparse top layer, quickly gets into roughly the right neighborhood using a couple of long hops, then drops down a layer and refines, then drops again — like using a highway to get across town fast, then surface streets to find the exact house. That's what USING hnsw (embedding vector_cosine_ops) builds and what powers ORDER BY embedding <=> query LIMIT 8 in Part 12 being fast instead of a full table scan.

vector_cosine_ops tells the HNSW index which distance metric to optimize the graph for — cosine distance (angle between two vectors, ignoring their magnitude) rather than Euclidean (straight-line) distance. Embedding models are generally trained so that "similar meaning" correlates with "small angle between vectors" rather than "similar vector length," so cosine is the standard choice for text/code embeddings — matches what <=> computes in Part 12's query.

def get_connection(database_url, *, connect_timeout=5, retries=1, backoff_seconds=0.5):
    attempt = 0
    while True:
        try:
            conn = psycopg.connect(database_url, autocommit=False, connect_timeout=connect_timeout)
            register_vector(conn)
            conn.execute(f"SET lock_timeout = '{LOCK_TIMEOUT}'")
            conn.commit()
            return conn
        except psycopg.OperationalError:
            if attempt >= retries:
                raise
            attempt += 1
            time.sleep(backoff_seconds)


def apply_schema(conn: psycopg.Connection) -> None:
    sql = SCHEMA_PATH.read_text()
    conn.execute(sql)
    conn.commit()
  • psycopg is the raw Postgres driver (psycopg3, the modern rewrite) — no ORM (SQLAlchemy, Django ORM, etc.) sits between this code and SQL, by deliberate project choice (see CLAUDE.md: "the user wants to personally understand every piece"). Every query in this codebase is a literal SQL string.
  • register_vector(conn) — this is the pgvector Python adapter registering itself on this specific connection, teaching psycopg how to convert between a Python list[float] and Postgres's vector type in both directions. Without this, you'd have to manually format vectors as strings like '[0.1,0.2,...]' for every query.
  • autocommit=False means every statement is inside an implicit transaction until you call conn.commit() — nothing is durably saved until commit, and you can conn.rollback() to undo everything since the last commit if something goes wrong mid-operation.
  • SET lock_timeout = '5s' — this is the fix for a real bug hit during development (documented in CLAUDE.md Task 12): apply_schema() re-runs schema.sql on every CLI invocation (deliberately — see below), and that SQL includes an ALTER TABLE ... ADD COLUMN IF NOT EXISTS, which needs an ACCESS EXCLUSIVE lock on the repos table (Postgres's strictest lock — blocks even reads). If another connection was holding an open, uncommitted transaction that had merely read from repos, that ALTER would queue up and wait — by default, forever, with no error, just an indefinitely hanging CLI command. Setting a 5-second lock_timeout means any statement that can't acquire its lock within 5 seconds fails loudly with psycopg.errors.LockNotAvailable instead of hanging silently — much easier to debug.
  • The retry loop around psycopg.connect handles transient connection failures (DB still starting up, brief network blip) — one retry, half-second backoff, then give up and propagate the real error.
  • apply_schema() is intentionally re-run on every single CLI invocation rather than once. Why not cache "already applied"? Because there's no migration framework in this project — schema.sql is the only source of truth for the DB shape, and it's written entirely with IF NOT EXISTS guards specifically so it's idempotent (safe to run repeatedly, no error, no duplicate side effects). If schema.sql is edited later to add a new column, the very next CLI call — any of them, unconditionally — is what applies that change to an already-existing database. Caching "already applied" would silently break that upgrade path.

Part 4 — The Chunk model & content hashing

The one shared data shape that flows through the entire pipeline.

Files: sleuth/chunking.py

Concept — why chunk at all, and why not whole files? An LLM's context window is finite, and more importantly, relevance degrades the more irrelevant text you cram in alongside the relevant part — "needle in a haystack" effects are real even with large context windows. If you embedded and searched over whole files, asking "how does retry work?" might retrieve a 2,000-line file where the retry logic is 15 lines and the rest is unrelated noise, both diluting the embedding's meaning (the vector represents an average of everything in the file, blurring the "retry" signal) and wasting prompt space. Chunking at the function/method/class level (rather than whole-file) keeps each embedded unit semantically coherent — one clear "topic" per chunk. 
@dataclass
class Chunk:
    file_path: str
    symbol_name: str | None
    kind: str  # 'function' | 'method' | 'class' | 'module'
    start_line: int
    end_line: int
    code_text: str

    @property
    def content_hash(self) -> str:
        return hashlib.sha256(self.code_text.encode("utf-8")).hexdigest()


def format_chunk_context(chunk: Chunk, language: str) -> str:
    symbol = chunk.symbol_name or "(module level)"
    header = (
        f"# File: {chunk.file_path}\n"
        f"# {chunk.kind}: {symbol}\n"
        f"# Language: {language}\n\n"
    )
    return header + chunk.code_text
  • @property on content_hash makes it read like an attribute (chunk.content_hash) rather than a method call (chunk.content_hash()), even though it's actually computing something every time it's accessed. It's not stored on the object — it's recalculated from code_text whenever you ask for it. That's a deliberate design signal: this value is derived from code_text, not independent state that could get out of sync with it.
  • SHA-256 is a cryptographic hash function: feed it any bytes, get back a fixed-length (64 hex character) fingerprint. The same input always produces the same hash; changing even one character of the input produces a completely different hash (this is the "avalanche effect" — by design, hashes don't degrade gracefully with small changes, so you can't infer "how similar" two pieces of code are from how similar their hashes look — that's not the point here anyway). The point of using it here isn't security, it's a cheap, reliable way to answer "has this exact function's code changed since I last indexed it?" in O(1) — compare two 64-character strings instead of diffing two multi-line code blocks character by character. This underpins the whole incremental re-index feature in Part 10/11: unchanged chunks get skipped, saving an embedding API call (which costs money and time) for every chunk that hasn't actually changed.
  • format_chunk_context is deliberately the single, centralized place that decides what text actually gets sent to the embedding model. It's reused identically when building the prompt sent to the LLM in build_prompt (Part 14) — same header format, same information. This matters because embeddings and generation both benefit from the model seeing "this is a method named foo in file bar.py, written in Python" rather than bare code with no context — a method named save means something very different in a Django model vs. a file-writer utility, and the surrounding metadata disambiguates that both for the embedding (so it retrieves correctly) and for the LLM (so it explains correctly).
Why not put content_hash logic inside store.py instead of on Chunk itself? Keeping hash computation as a property of the Chunk means anything holding a Chunk object — the chunker, the pipeline, tests — can ask "what's your hash?" without importing store.py or knowing anything about the database. It's a property of the data, not of persistence.

Part 5 — tree-sitter: parsing code into an AST

How SLEUTH actually "understands" code well enough to find function/class boundaries.

Files: sleuth/ingest/parse.py

Concept — what is an AST, and why not just use regex or count braces? An Abstract Syntax Tree is a structured, hierarchical representation of source code's actual grammar — not the raw text, but its parsed meaning. def foo(): return 1 becomes a tree: a function_definition node, with an identifier child node (foo) and a block child node containing a return_statement. Regex can find text that looks like def foo(, but it has no concept of "where does this function's body actually end" — nested functions, multi-line strings containing the word def, decorators, comments that mention "def" — all of these break naive text-based heuristics. A real parser that understands the language's grammar gets this exactly right, because it's the same technology a compiler or the Python interpreter itself uses to make sense of your code before running it.
Concept — why tree-sitter specifically? tree-sitter is a parser-generator library (originally built for GitHub's code navigation / Atom editor) with two properties that matter here: it's fast enough to parse on every keystroke in an editor (so parsing an entire repo at index time is trivially fast by comparison), and it has pre-built grammars for dozens of languages as separate installable packages (tree-sitter-python, tree-sitter-javascript, tree-sitter-typescript) that all expose a uniform API — you don't write a parser per language, you just plug in the grammar and get a tree back in the same shape of API regardless of which language it is.

  • LanguageSpec is a tiny frozen dataclass bundling two things that always travel together: a human-readable key ("python", used later as metadata in chunk headers and to pick which .scm query file to load — Part 6) and the actual tree-sitter Language object needed to construct a parser.
  • LANGUAGES is a dict keyed by file extension. This is the single "language registry" — the whole codebase's answer to "what language is this file?" is "look up its extension here." Adding a fourth language (say Go) means: add the grammar package to requirements, one new .py: LanguageSpec(...) entry, one new .scm query file (Part 6). Nothing else changes — this centralization is exactly what makes it easy to extend later.
  • UnsupportedFileType is a custom exception, deliberately — rather than silently returning None or crashing with an unrelated error for, say, a .json or .md file encountered while walking the repo. The pipeline (Part 6, 11) catches this specific exception and falls back to a simpler line-based chunking strategy instead of aborting the whole ingest run over one file it doesn't have a grammar for.
  • parser.parse(source_bytes) — note this takes bytes, not a Python str. tree-sitter works on raw byte offsets internally (its nodes report start_byte/end_byte, used constantly in Part 6 to slice out source text) because byte offsets are unambiguous across encodings, whereas Python string indices count Unicode code points, which can disagree with byte offsets for non-ASCII text. This is why chunk_source upstream always reads files as file_path.read_bytes(), not .read_text().
  • The return value Tree is the parsed AST; tree.root_node (used in Part 6) is the entry point for walking it — every node has .type (a string like "function_definition"), .children, .start_point/ .end_point (row, column), and .start_byte/.end_byte.

Part 6 — Query-based chunking: turning the AST into Chunks

This is the trickiest, most-iterated-on part of the whole codebase. Worth reading slowly.

Files: sleuth/ingest/chunk.py, sleuth/ingest/query_chunker.py, sleuth/ingest/queries/*.scm

The history: why this file exists in its current form

Per Note.md and CLAUDE.md, Task 5 was originally implemented as a hand-rolled tree walker that inspected each direct child of the root node and matched it against literal node-type strings — "if this child's .type == 'function_definition', it's a function." This broke on two real cases that are extremely common in real code:

  • Wrapped nodes. export class Foo {} in TS/JS doesn't have a root child of type class_declaration — it has an export_statement whose child is the class. Same for Python decorators: @app.get("/")\ndef handler(): ... is a decorated_definition node wrapping a function_definition. The old walker's exact-type check missed all of these — they fell into a "junk" bucket instead of being chunked as functions/classes, meaning basically every FastAPI route handler and every exported NestJS/Vue class was misclassified.
  • Worse — decorated methods inside a class were silently dropped entirely, not even landing in junk, because only root-level leftover children were collected into junk, and a decorated method lives inside a class body, not at the root.

The fix rewrote chunking around tree-sitter queries instead of manual tree-walking — which turned out to be the more idiomatic tree-sitter approach anyway.

Concept: what is a tree-sitter query?

Concept A tree-sitter query is written in a small S-expression pattern language (.scm files — the extension is borrowed from Scheme, since the syntax resembles it) that describes a shape to match against the AST, similar in spirit to how a regex describes a shape to match against text, but operating on tree structure instead of a flat character stream. You hand the query engine a compiled query plus the root node, and it returns every place in the tree where that shape occurs — no manual recursion required, and crucially, a query pattern can match a node regardless of what wraps it, because you write the pattern to describe "a decorated_definition whose definition is a function_definition" as its own explicit case, rather than hoping a flat type check happens to catch it. 
; bare module-level (or nested-in-function) function
(function_definition
  name: (identifier) @name.function) @definition.function

; decorated function — @definition.function is the *wrapper*, so decorator
; text is included; @inner.function is the raw node, used only for dedup
; against the bare pattern above which also matches it independently
(decorated_definition
  definition: (function_definition
    name: (identifier) @name.function) @inner.function) @definition.function

; plain method
(class_definition
  name: (identifier) @name.class
  body: (block
    (function_definition
      name: (identifier) @name.method) @definition.method)) @definition.class_context

; decorated method
(class_definition
  name: (identifier) @name.class
  body: (block
    (decorated_definition
      definition: (function_definition
        name: (identifier) @name.method) @inner.method) @definition.method)) @definition.class_context

; whole class, bare
(class_definition
  name: (identifier) @name.class) @definition.class

; whole class, decorated (e.g. @dataclass)
(decorated_definition
  definition: (class_definition
    name: (identifier) @name.class) @inner.class) @definition.class
  • Reading the syntax: (function_definition name: (identifier) @name.function) @definition.function means "match a node of type function_definition, whose name field is an identifier node — capture that identifier as @name.function, and capture the whole function_definition node as @definition.function." The @something tags are captures — labels attached to whichever node matched at that position, retrievable afterward by name.
  • The bare pattern and the decorated pattern are two separate, independent top-level patterns in the same file. Both can match the same underlying function_definition node (a decorated function's inner function_definition satisfies the bare pattern too, since the bare pattern doesn't care what's around it) — this is why query_chunker.py needs deduplication logic (below): the same physical function can be captured twice, once per matching pattern, and the code has to pick one canonical version (the one with the decorator/export wrapper included, since that's more complete/accurate).
  • Note the comment: "decorators on methods are siblings in this grammar, not wrappers" in the JS query file — this is a real, language-specific grammar difference. In tree-sitter's Python grammar, a decorator wraps the function it decorates (decorated_definition is the parent node). In tree-sitter's JavaScript/TypeScript grammar, decorators on class methods are just adjacent sibling nodes, not a wrapper — so the JS query file doesn't need a separate "decorated method" pattern at all; the plain method pattern already matches regardless of whether a decorator sits next to it. This is exactly the kind of grammar quirk you only discover by actually testing against real code, which is presumably how this comment came to exist.
  • @definition.class_context — used specifically for classes that contain methods. It exists so query_chunker.py can later ask "which classes had at least one method captured?" and, for those, skip emitting a separate whole-class chunk — because if a class has methods, you want one chunk per method (each independently retrievable and embeddable), not one giant chunk for the whole class plus N more chunks per method (which would be redundant, wasting embedding calls and diluting search relevance with duplicated text).

query_chunker.py — resolving the query matches into a final chunk list

def run_query(query: Query, root: Node, source_bytes: bytes, file_path: str) -> list[Chunk]:
    matches = query.matches(root)

    method_records = []
    for _, captures in matches:
        if "definition.method" not in captures:
            continue
        outer = captures["definition.method"][0]
        inner = captures.get("inner.method", [outer])[0]
        class_name = _node_text(captures["name.class"][0], source_bytes)
        method_name = _node_text(captures["name.method"][0], source_bytes)
        method_records.append({
            "outer": outer,
            "key": _span_key(inner),
            "symbol_name": f"{class_name}.{method_name}",
            "kind": "method",
        })
  • query.matches(root) runs the compiled query against the whole tree and returns a list of (pattern_index, captures_dict) pairs — one entry per place in the tree that matched any of the query's patterns. captures maps capture names (like "definition.method") to a list of matched nodes (a list, because in general a single pattern match could capture a name more than once, though here it's always exactly one).
  • This first loop specifically pulls out every method match. captures.get("inner.method", [outer])[0] — this is the dedup key logic: for a decorated method, there are two nodes in play, the inner (bare function, undecorated) and outer (the decorated_definition wrapper, decorator included). The chunk's actual text should use outer (so the decorator text like @property is preserved in what gets embedded and shown to the LLM), but the identity/dedup key uses inner's byte span — because that inner span is what a different pattern (the plain, non-decorated method pattern) would also capture as its outer if it happened to match the same underlying function. Using the inner span as the key means both patterns agree on "this is the same function" even though they captured it via different wrapper nodes.
  • captures.get("inner.method", [outer])[0] — if there's no inner.method capture at all (a plain undecorated method matched only the plain pattern), default to [outer] so inner just equals outer — a bare method's own span is its own dedup key, which is correct since nothing else would also match that same span under a different capture name.
    excluded_function_keys = {r["key"] for r in method_records}
    classes_with_methods = {
        _span_key(captures["definition.class_context"][0])
        for _, captures in matches
        if "definition.method" in captures
    }

    function_candidates: dict[tuple[int, int], dict] = {}
    class_candidates: dict[tuple[int, int], dict] = {}

    for _, captures in matches:
        if "definition.method" in captures or "definition.class_context" in captures:
            continue

        if "definition.function" in captures:
            outer = captures["definition.function"][0]
            inner = captures.get("inner.function", [outer])[0]
            key = _span_key(inner)
            if key in excluded_function_keys:
                continue
            _keep_largest(function_candidates, key, outer=outer,
                          symbol_name=_node_text(captures["name.function"][0], source_bytes),
                          kind="function")
        elif "definition.class" in captures:
            outer = captures["definition.class"][0]
            inner = captures.get("inner.class", [outer])[0]
            key = _span_key(inner)
            _keep_largest(class_candidates, key, outer=outer,
                          symbol_name=_node_text(captures["name.class"][0], source_bytes),
                          kind="class")
  • excluded_function_keys — set of every method's identity key. Why would a method's span ever also show up as a "function" candidate? Because tree-sitter's Python grammar represents a method the exact same node type as a top-level function (function_definition) — a method is structurally "a function_definition that happens to live inside a class body." The bare function pattern ((function_definition name: ... ) @definition.function, with no constraint on where it lives) matches methods too, unintentionally. This set is how the code prevents a method from also being emitted as a separate standalone-function chunk.
  • classes_with_methods — every class node that had at least one method captured. Used right after this snippet to filter class_candidates down to only classes that DON'T have methods (see below) — the "represent a class either as N method chunks or as one whole-class chunk, never both" rule mentioned earlier.
  • The main loop skips anything that was already claimed as a method or as a "class-that-has-methods" context match, then classifies the rest into function_candidates or class_candidates, keyed by span.
  • _keep_largest is the actual dedup resolution: when the same span shows up more than once (bare pattern AND decorated pattern both matching the same underlying function via different wrapper nodes), keep whichever candidate has the larger byte span — i.e. prefer the decorated/exported wrapper version over the bare inner version, since the wrapper's text is a superset that includes the decorator/export keyword: 
    def _keep_largest(candidates, key, *, outer, symbol_name, kind):
    span = outer.end_byte - outer.start_byte
    existing = candidates.get(key)
    if existing is None or span > existing["span"]:
        candidates[key] = {"outer": outer, "symbol_name": symbol_name, "kind": kind, "span": span}
    records = (
        method_records
        + list(function_candidates.values())
        + [r for key, r in class_candidates.items() if key not in classes_with_methods]
    )

    top_level_keys = {_span_key(r["outer"]) for r in function_candidates.values()}
    top_level_keys |= {_span_key(r["outer"]) for r in class_candidates.values()}

    chunks = [
        Chunk(
            file_path=file_path,
            symbol_name=r["symbol_name"],
            kind=r["kind"],
            start_line=r["outer"].start_point[0] + 1,
            end_line=r["outer"].end_point[0] + 1,
            code_text=_node_text(r["outer"], source_bytes),
        )
        for r in records
    ]

    leftover = [child for child in root.children if _span_key(child) not in top_level_keys]
    if leftover:
        chunks.append(Chunk(
            file_path=file_path, symbol_name=None, kind="module",
            start_line=leftover[0].start_point[0] + 1,
            end_line=leftover[-1].end_point[0] + 1,
            code_text="\n".join(_node_text(n, source_bytes) for n in leftover),
        ))

    return chunks
  • records combines all three categories: every method, every standalone function, and every whole-class-without-methods (the class candidates whose key is NOT in classes_with_methods — a class with methods contributes its methods to method_records already and deliberately does not also get a whole-class chunk).
  • top_level_keys is used only to compute what's left over at module level — root children not covered by any function/class match at all (import statements, module-level variable assignments, top-level if __name__ == "__main__": blocks, etc.). Note this is built from function_candidates/class_candidates keys only, not method keys — methods live inside a class body, not as root children, so they were never going to appear in root.children in the first place; only the enclosing class (or the class's absence from this set, if it has methods and thus isn't in class_candidates) matters for leftover-detection at the root level.
  • r["outer"].start_point[0] + 1 — tree-sitter's start_point is a (row, column) tuple, 0-indexed (first line is row 0). The + 1 converts to the conventional 1-indexed line numbers humans expect (start_line/end_line stored in the DB and shown in prompts/answers).
  • The "leftover" (junk/module) chunk collects any remaining root children whose span wasn't claimed, concatenates their text with newlines, and reports a start/end line spanning from the first to the last leftover node — this was explicitly called out as a known limitation being fixed: earlier code reported a "start to end" span even when the actual joined text skips whatever fell in between (chunks that WERE claimed by functions/classes) — meaning the reported line range can be wider than what the actual code_text covers. Worth knowing this is a known/accepted imprecision, not a bug you need to chase.
Why not just always emit one chunk per class AND one per method (never suppress the whole-class chunk)? Because for retrieval quality, a class with 10 methods emitted as 11 chunks (10 method chunks + 1 whole-class chunk containing all 10 methods again) means the whole-class chunk's embedding is diluted (its vector is an "average" of 10 different concerns, matching none of them well) AND it's pure duplication in the retrieved context if both a method chunk and the whole-class chunk happen to both rank in the top-K for some query — wasted prompt space explaining the same code twice. Suppressing the whole-class chunk when methods exist keeps each stored chunk singularly meaningful.

chunk.py — the public entry point, fallback, and size capping

def chunk_source(source_bytes: bytes, file_path: str, extension: str) -> list[Chunk]:
    try:
        tree, spec = parse_source(source_bytes, extension)
    except UnsupportedFileType:
        chunks = _fallback_chunk(source_bytes, file_path)
    else:
        query = _load_query(spec.key, spec.ts_language)
        chunks = run_query(query, tree.root_node, source_bytes, file_path)

    return _cap_chunk_sizes(chunks)
  • This is the only function other modules (the ingest pipeline, tests) actually call — everything in query_chunker.py/parse.py is an implementation detail behind this one entry point. try/except/else: the else branch runs only if the try block raised no exception — i.e. "if parsing succeeded (this is a supported language), do the real query-based chunking; if it raised UnsupportedFileType, fall back instead." This is slightly different from putting the query-chunking code directly after the try block, which would also run it if the except handler itself somehow raised — using else makes the "only on success" intent explicit.
  • _fallback_chunk handles any file extension with no tree-sitter grammar registered — splits on blank lines into paragraph-like blocks, tagged kind="module". Crude, but it means the pipeline never crashes or silently skips a whole file just because it's, say, a .md or config file slipping through the extension filter — though in practice SUPPORTED_EXTENSIONS in the pipeline (Part 11) only walks .py/ .js/.ts files to begin with, so this path is more of a safety net than something hit often today.
  • @lru_cache(maxsize=None) on _load_query — caches the compiled Query object per (language_key, ts_language) pair so the .scm file is read from disk and compiled only once per language, no matter how many thousands of files of that language get chunked in one ingest run. maxsize=None means unbounded cache size — fine here since there are only 3 possible languages, so at most 3 cached entries ever.
  • _cap_chunk_sizes (not fully shown above, but worth knowing it exists): splits any single chunk whose code_text exceeds MAX_CHUNK_CHARS (4000) into multiple numbered parts (symbol_name#1, symbol_name#2, ...), splitting on line boundaries so it never cuts a line in half. This guards against a single enormous function (some legacy codebases have 1000+ line functions) blowing past embedding-model input limits or dominating the prompt context on its own.

class CloneError(Exception):
    pass


def clone_repo(url: str, dest_dir: str) -> Path:
    dest = Path(dest_dir)
    result = subprocess.run(
        ["git", "clone", "--depth", "1", url, str(dest)],
        capture_output=True,
        text=True,
    )
    if result.returncode != 0:
        raise CloneError(result.stderr.strip())
    return dest


def list_source_files(repo_path: Path, extensions: set[str]) -> list[Path]:
    files = []
    for path in Path(repo_path).rglob("*"):
        if ".git" in path.parts:
            continue
        if path.is_file() and path.suffix in extensions:
            files.append(path)
    return files
  • subprocess.run([...], capture_output=True, text=True) shells out to the real git binary rather than using a Python git library (GitPython etc.) — simpler, and git itself is the one true implementation of git behavior. capture_output=True captures stdout/stderr instead of letting them print to the terminal directly; text=True decodes them as strings instead of raw bytes.
  • --depth 1 is a shallow clone — fetches only the latest commit's tree, not the full git history. SLEUTH only ever needs the current state of the files (it's chunking source code, not analyzing commit history), so pulling the entire history would be pure waste — slower and much larger on disk for any repo with real history behind it.
  • result.returncode != 0 is how you check a subprocess failed — by Unix convention, exit code 0 means success, anything else means failure. On failure, this raises a custom CloneError carrying git's own stderr message (a bad URL, a private repo without credentials, network failure, etc.) rather than a generic subprocess exception — that message is what ends up in repos.error_message in Part 11, so it needs to actually be informative to a human reading it later.
  • Path(repo_path).rglob("*") — rglob is "recursive glob": walks every file and directory under repo_path, at any depth, matching the pattern "*" (everything). Path objects (from the standard library's pathlib) are the modern, preferred way to handle filesystem paths in Python — preferred over raw string manipulation with os.path.join because operations like .suffix, .parts, .relative_to(...) (used in Part 11) are just attributes/methods on the object rather than separate os.path function calls.
  • ".git" in path.parts — .parts breaks a path into its component pieces as a tuple, e.g. Path("repo/.git/objects/ab").parts == ("repo", ".git", "objects", "ab"). Checking membership this way (rather than ".git" in str(path)) avoids a false positive on some hypothetical file literally named my.gitconfig.py — it only matches an exact path segment equal to .git, i.e. actually being inside git's internal bookkeeping directory, which you never want to parse as source code.
  • extensions is passed in by the caller (Part 11 passes SUPPORTED_EXTENSIONS = set(LANGUAGES.keys()), i.e. {".py", ".js", ".ts"}) — this function itself has no hardcoded language knowledge, keeping the "what languages do we support" decision centralized in parse.py's registry (Part 5), not duplicated here.

Part 8 — Embeddings, httpx, and async concurrency

Turning code text into vectors — and doing it fast for hundreds of chunks at once.

Files: sleuth/ingest/embed.py

Concept — what is an embedding, actually? An embedding model takes a piece of text and outputs a fixed-length list of floating point numbers (here, 1024 of them) — a point in a 1024-dimensional space. The model is trained so that texts with similar meaning end up as points that are geometrically close together in that space, and dissimilar texts end up far apart. "voyage-code-3" specifically is trained on code (and code+text pairs like docstrings/comments next to functions), so it's tuned to understand that a Python function computing a hash and a JavaScript function computing a hash are semantically similar even though the literal text looks nothing alike. This is what makes vector search (Part 3, Part 12) work at all — the entire scheme depends on "semantically similar things are near each other" holding true, which is the model's job, not anything SLEUTH's own code does.

Scope note: why only Voyage, not also NIM embeddings

From CLAUDE.md: the original v2 design called for a pluggable embedder (Voyage OR NVIDIA NIM, chosen per-repo, with two differently-sized pgvector tables to match each model's output dimension). During actual implementation (Tasks 7-8) this was deliberately narrowed to Voyage-only — one VoyageEmbedder class, one fixed vector(1024) column, no get_embedder() factory function picking between providers. This was a conscious scope cut confirmed with the user, not an oversight — revisit only if NIM embeddings are actually needed later. Note this is different from generation (the LLM that writes the answer), where both Groq and NIM WERE both implemented, with real fallback logic (Part 13) — the embedder and the generator went different directions on pluggability despite the original design wanting both pluggable.

        self.max_concurrency = max_concurrency

    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
        batches = [texts[i : i + self.batch_size] for i in range(0, len(texts), self.batch_size)]
        semaphore = asyncio.Semaphore(self.max_concurrency)

        async with httpx.AsyncClient() as client:
            results = await asyncio.gather(
                *(self._embed_one_batch(client, semaphore, batch) for batch in batches)
            )

        vectors: list[list[float]] = []
        for batch_vectors in results:
            vectors.extend(batch_vectors)
        return vectors

    async def _embed_one_batch(self, client, semaphore, batch: list[str]) -> list[list[float]]:
        async with semaphore:
            response = await post_with_retry(
                client, VOYAGE_EMBEDDINGS_URL,
                headers={"Authorization": f"Bearer {self.api_key}"},
                json={"input": batch, "model": self.model_name},
            )

        data = response.json()["data"]
        data.sort(key=lambda item: item["index"])
        return [item["embedding"] for item in data]
  • This class was already introduced conceptually in Part 1 (async/gather/semaphore) — here's the RAG-specific detail that matters: why sort by item["index"]? Voyage's API, like most batch embedding APIs, doesn't strictly promise to return embeddings in the same order you submitted the input texts — it returns each result tagged with the original input's index, and it's the caller's job to re-sort by that index to line results back up with inputs. Skipping this step would silently produce embeddings attached to the wrong chunk of code — a correctness bug that wouldn't throw any error, just quietly return wrong search results forever. This is exactly the kind of subtle contract that's easy to get wrong once and never notice.
  • batch_size=128, max_concurrency=5 are constructor defaults, not magic numbers buried in the method — meaning tests (and, if needed later, tuning) can override them per instance without touching this file.
  • Notice httpx.AsyncClient() is created fresh, once, inside embed_batch (not per sub-batch) and shared across all the concurrent _embed_one_batch calls via the closure — AsyncClient internally pools TCP connections, so reusing one client across many requests to the same host (api.voyageai.com) avoids the overhead of a fresh TCP+TLS handshake per request.
  • httpx itself (rather than requests, the more famous HTTP library) is used specifically because requests has no async support at all — it's a purely synchronous library. httpx was built as a modern replacement offering both a sync AND async API with a very similar feel, which is why it's the choice everywhere in this codebase that talks to an external API (Voyage, Groq, NIM).

Part 9 — The retry helper (shared plumbing)

One small function, reused by every single external API call in the codebase.

Files: sleuth/http_retry.py

Concept — why retry at all, and why only once? Networks and third-party APIs fail transiently, constantly, for reasons that have nothing to do with your request being wrong: a brief network blip, the provider being momentarily overloaded (HTTP 429 "too many requests", or 5xx server errors), a connection reset. Retrying once, after a short pause, resolves the vast majority of these without any user-visible impact. Retrying unboundedly, though, is dangerous — if the failure isn't transient (bad API key → permanent 401, malformed request → permanent 400), infinite retries just hang forever or hammer a struggling server harder. This code retries exactly once, only for status codes that are conventionally transient, and gives up immediately (no retry) for anything else — like a 401, which retrying will never fix. 
TRANSIENT_STATUS_CODES = {429, 500, 502, 503, 504}


async def post_with_retry(client, url, *, retries=1, backoff_seconds=1.0, **kwargs) -> httpx.Response:
    attempt = 0
    while True:
        try:
            response = await client.post(url, **kwargs)
        except httpx.TransportError:
            if attempt < retries:
                attempt += 1
                await asyncio.sleep(backoff_seconds)
                continue
            raise

        if response.status_code in TRANSIENT_STATUS_CODES and attempt < retries:
            attempt += 1
            await asyncio.sleep(backoff_seconds)
            continue

        response.raise_for_status()
        return response
  • *, retries=1, backoff_seconds=1.0, **kwargs — the * forces every parameter after it to be passed by keyword only (you cannot call post_with_retry(client, url, 1, 1.0) positionally — you must write post_with_retry(client, url, retries=1)). This is a deliberate readability choice at a call site — retries=1 is self-documenting, whereas a bare positional 1 tells you nothing without checking the function signature. **kwargs forwards any other keyword arguments (like headers= and json=, as used by both the embedder and the generator callers) straight through to client.post(...) untouched — this function doesn't need to know or care what those are, it just needs to add retry behavior around whatever POST call the caller wants to make.
  • Two distinct failure modes are handled separately: httpx.TransportError (the request never even got a response — DNS failure, connection refused, timeout) is caught with a Python try/except, since it's a raised exception. A "successful" request that came back with a bad status code (429, 500, etc.) is not an exception at this point — httpx doesn't raise automatically on 4xx/5xx by default — so that's checked explicitly via response.status_code in TRANSIENT_STATUS_CODES instead.
  • response.raise_for_status() — this IS where httpx converts a bad status code into a raised httpx.HTTPStatusError exception, but only called at the very end, after retry logic has already had its chance. So a permanent error (say, 401) flows straight through to this line without ever matching the transient-code check, gets converted to an exception immediately, and propagates up to the caller (further retry/fallback logic — like the Groq→NIM chain in Part 13 — decides what to do with it from there).
  • while True: ... continue is the actual retry loop shape — rather than recursion, it's a straightforward "keep looping until we successfully return or raise." attempt tracks how many retries have been used so far; once attempt >= retries, the next failure is allowed to propagate instead of being retried again.
Notice what's absent: no exponential backoff (it's a fixed 1-second pause, not 1s-then-2s-then-4s), no jitter (randomized delay to avoid many clients retrying in lockstep), no distinction between different transient codes needing different backoff strategies. This is a deliberately minimal implementation — appropriate for "retry once" semantics where a more elaborate backoff strategy wouldn't add much value; it would matter more if retries were routinely set higher than 1.

Part 10 — The store: raw SQL CRUD, upsert, incremental re-index

Every read and write to Postgres in the entire codebase lives in this one file.

Files: sleuth/store.py

Concept — CRUD, and why raw SQL instead of an ORM CRUD = Create, Read, Update, Delete — the four basic operations any persistence layer needs. This project deliberately writes every query as a literal SQL string via psycopg, rather than using an ORM like SQLAlchemy that would let you write Repo.objects.filter(...) in Python and have it translate to SQL for you. Per the project's own stated constraint (CLAUDE.md: "no black-box library doing... for them"), this is intentional — the tradeoff is more verbose code (you write the SQL yourself, including thinking about placeholders/escaping) in exchange for there being no hidden layer translating your intent into SQL you didn't write and might not fully understand. 
def create_repo(conn, github_url: str) -> str:
    row = conn.execute(
        "INSERT INTO repos (github_url) VALUES (%s) RETURNING id", (github_url,)
    ).fetchone()
    return str(row[0])
  • %s is a parameterized query placeholder — psycopg substitutes the value from the tuple (github_url,) safely, escaping it as needed. This is the standard defense against SQL injection: never build a query string by directly interpolating user-controlled values (f"...WHERE url = '{github_url}'") — always let the driver handle substitution, which treats the value strictly as data, never as SQL syntax to execute.
  • RETURNING id is a Postgres extension to standard INSERT — it hands back the newly-generated id (remember, gen_random_uuid() from Part 3 generates it server-side) in the same round trip, instead of needing a separate SELECT afterward to find out what ID got assigned.
  • str(row[0]) — psycopg returns the UUID column as Python's own uuid.UUID type, converted to a plain string here so every function in this module consistently deals in string repo IDs rather than mixing UUID objects and strings across the codebase.

The upsert — the heart of incremental re-indexing

def upsert_chunks(conn, repo_id, chunks_with_embeddings) -> None:
    for chunk, embedding in chunks_with_embeddings:
        conn.execute(
            """
            INSERT INTO chunks
                (repo_id, file_path, symbol_name, kind, start_line, end_line, code_text, content_hash, embedding)
            VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
            ON CONFLICT (repo_id, file_path, COALESCE(symbol_name, ''))
            DO UPDATE SET
                kind = EXCLUDED.kind, start_line = EXCLUDED.start_line, end_line = EXCLUDED.end_line,
                code_text = EXCLUDED.code_text, content_hash = EXCLUDED.content_hash, embedding = EXCLUDED.embedding
            """,
            (repo_id, chunk.file_path, chunk.symbol_name, chunk.kind, chunk.start_line,
             chunk.end_line, chunk.code_text, chunk.content_hash, embedding),
        )
  • "Upsert" = insert-or-update in one atomic statement. Postgres's INSERT ... ON CONFLICT (columns) DO UPDATE SET ... tries the insert; if it would violate the unique index on those columns (recall chunks_identity_idx from Part 3 — (repo_id, file_path, symbol_name-or-empty)), instead of erroring, it updates the existing conflicting row's other columns instead. This is exactly what makes re-running the indexer on a repo that already exists safe and correct: a function that hasn't moved files or changed its symbol name, but whose body changed, gets its existing row's code_text/ content_hash/embedding updated in place — not a duplicate row.
  • EXCLUDED.kind etc. — inside the DO UPDATE SET clause, EXCLUDED is special Postgres syntax referring to "the row that was proposed for insertion but conflicted" — i.e. the new values you tried to insert. So kind = EXCLUDED.kind reads as "set the kind column to whatever the new (conflicting) insert attempt was trying to set it to."
  • Note this loops and executes one INSERT per chunk, rather than batching all chunks into a single multi-row INSERT. Simpler to read and reason about; the tradeoff is more round trips to Postgres for repos with many chunks — a reasonable simplicity-over-raw-throughput choice for a personal/learning project, worth knowing about if this ever needs to scale to very large repos.

Deciding what actually needs re-embedding

def get_existing_hashes(conn, repo_id) -> dict[tuple[str, str | None], str]:
    rows = conn.execute(
        "SELECT file_path, symbol_name, content_hash FROM chunks WHERE repo_id = %s", (repo_id,)
    ).fetchall()
    return {(file_path, symbol_name): content_hash for file_path, symbol_name, content_hash in rows}
This builds a dict comprehension mapping every existing chunk's identity (file_path, symbol_name) to its already-stored content_hash. The ingest pipeline (Part 11) uses this to compute, for every freshly re-chunked piece of code, "is this identical to what's already stored?" — if existing_hashes.get((c.file_path, c.symbol_name)) == c.content_hash, nothing changed, skip re-embedding it entirely (an actual money/time saving, since embedding calls cost both). This is the concrete mechanism behind the "incremental re-index: chunks hashed, unchanged chunks skip re-embedding" feature mentioned in the project README.

Cleaning up deleted/renamed symbols

def delete_stale_chunks(conn, repo_id, current_keys: set[tuple[str, str | None]]) -> None:
    existing = get_existing_hashes(conn, repo_id)
    stale_keys = existing.keys() - current_keys
    for file_path, symbol_name in stale_keys:
        conn.execute(
            "DELETE FROM chunks WHERE repo_id = %s AND file_path = %s AND COALESCE(symbol_name, '') = COALESCE(%s, '')",
            (repo_id, file_path, symbol_name),
        )
existing.keys() - current_keys is Python set subtraction — dict .keys() behaves like a set, so this computes "every (file_path, symbol_name) pair that exists in the DB but is NOT present in the freshly-chunked-just-now set." Those are chunks whose source function/class/file was deleted or renamed since the last index — if left alone, stale rows would sit in the DB forever, occasionally getting retrieved and shown to the LLM as if they still existed. This is called near the end of the pipeline (Part 11), after the upsert of everything current, so it only ever deletes things confirmed absent from the current pass — never something that just hasn't been processed yet.

Part 11 — The ingest pipeline: wiring it all together

The one function that calls everything from Parts 5-10 in the right order.

async def ingest_repo(github_url: str, conn, config: Config) -> str:
    repo_id = _find_or_create_repo(conn, github_url)
    update_repo_status(conn, repo_id, "indexing")
    conn.commit()

    embedder = VoyageEmbedder(api_key=config.voyage_api_key)

    workdir = tempfile.mkdtemp(prefix="sleuth-clone-")
    try:
        try:
            repo_path = clone_repo(github_url, workdir)
        except CloneError as exc:
            update_repo_status(conn, repo_id, "failed", str(exc))
            conn.commit()
            return repo_id

        files = list_source_files(repo_path, SUPPORTED_EXTENSIONS)

        all_chunks = []
        for file_path in files:
            relative_path = str(file_path.relative_to(repo_path))
            source_bytes = file_path.read_bytes()
            try:
                chunks = chunk_source(source_bytes, relative_path, file_path.suffix)
            except Exception:
                continue  # skip files that fail to parse, don't abort the whole index
            all_chunks.extend(chunks)

        current_keys = {(c.file_path, c.symbol_name) for c in all_chunks}
        existing_hashes = get_existing_hashes(conn, repo_id)

        to_embed = [
            c for c in all_chunks
            if existing_hashes.get((c.file_path, c.symbol_name)) != c.content_hash
        ]

        if to_embed:
            texts = [format_chunk_context(c, ...) for c in to_embed]
            vectors = await embedder.embed_batch(texts)
            upsert_chunks(conn, repo_id, list(zip(to_embed, vectors)))
            conn.commit()

        set_repo_embedding_info(conn, repo_id, embedder.model_name, embedder.dim)
        conn.commit()

        delete_stale_chunks(conn, repo_id, current_keys)
        conn.commit()

        update_repo_status(conn, repo_id, "ready")
        conn.commit()
        return repo_id
    finally:
        shutil.rmtree(workdir, ignore_errors=True)
This is the whole indexed pipeline from the diagram in Part 0, as one function. Walk it top to bottom:
  • _find_or_create_repo — checks if this github_url already has a row (re-running sleuth add on the same repo re-indexes it in place rather than creating a duplicate repos row), else creates one.
  • update_repo_status(conn, repo_id, "indexing") + immediate conn.commit() — this commit matters: it makes the "indexing" status visible to any other connection (e.g. sleuth list run from a different terminal while this is running) immediately, rather than only becoming visible once the whole multi-step function finishes. Notice this function commits after nearly every logical step, not just once at the end — a deliberate choice for observability/crash-resilience over strict atomicity (if the process crashed halfway, you'd see it stuck in whatever the last committed status was, rather than the whole ingest completely vanishing).
  • workdir = tempfile.mkdtemp(...) + try/finally: shutil.rmtree(workdir, ...) — a temp directory is created for the clone, and the finally block guarantees it's cleaned up whether the function completes successfully, hits a handled failure (bad clone), or even an unhandled exception bubbles all the way up — finally always runs.
  • The inner try/except CloneError is a handled, expected failure path — a bad URL or unreachable repo isn't a bug in SLEUTH, it's a legitimate outcome, so it's caught, recorded into repos.error_message, status set to "failed", and the function returns normally (not raising) — this is what the module docstring in CLAUDE.md means by "wires clone→chunk→...→mark-ready, never raises (failures land in repos.status = 'failed')" — callers (the CLI) never need a try/except around ingest_repo itself; they just check the resulting status.
  • except Exception: continue inside the per-file chunking loop is a much broader catch, deliberately — if tree-sitter chokes on one malformed or unusual file (binary file with a misleading extension, syntax tree-sitter's grammar can't handle, etc.), that one file is skipped and ingestion continues with everything else, rather than one bad file aborting the whole multi-thousand-file index run.
  • current_keys = {(c.file_path, c.symbol_name) for c in all_chunks} — a set comprehension, building the "what exists right now, after this fresh chunking pass" set used later both to decide what to embed (diffed against existing_hashes) and what to delete as stale (Part 10's delete_stale_chunks).
  • The whole embed-and-upsert block is skipped entirely (if to_embed:) when nothing changed — re-running sleuth add on an already-indexed, unchanged repo does a full clone + full re-chunk + full hash comparison, but zero embedding API calls and zero DB writes to chunks, if literally nothing changed. This is the whole point of content hashing from Part 4, realized here.
  • Order matters at the end: embed+upsert current chunks, THEN update embedding info, THEN delete stale chunks, THEN mark ready — stale-deletion happens only after new/changed chunks are already safely written, so a crash between upsert and delete leaves you with old+new both present (safe, just slightly redundant) rather than deleting first and crashing before the replacement is written (which would leave gaps in the index).

Part 12 — Vector search: how retrieval actually works

Where the HNSW theory from Part 3 becomes one real SQL query.

Files: sleuth/retrieve/search.py

@dataclass
class SearchResult:
    file_path: str
    symbol_name: str | None
    kind: str
    start_line: int
    end_line: int
    code_text: str
    distance: float


def search_chunks(conn, repo_id: str, query_embedding: list[float], top_k: int = 8) -> list[SearchResult]:
    rows = conn.execute(
        """
        SELECT file_path, symbol_name, kind, start_line, end_line, code_text,
               embedding <=> %(query)s::vector AS distance
        FROM chunks
        WHERE repo_id = %(repo_id)s
        ORDER BY distance
        LIMIT %(top_k)s
        """,
        {"query": query_embedding, "repo_id": repo_id, "top_k": top_k},
    ).fetchall()
    return [SearchResult(*row) for row in rows]
  • embedding <=> %(query)s::vector — <=> is pgvector's cosine distance operator (added when the vector extension was loaded in Part 3). It computes, for every row, how far that row's stored embedding is from the query vector you're searching with — smaller distance means more similar. This single expression is doing the entire "find similar code" computation; nothing about "similarity" is implemented in Python at all, it's pushed down into the database, which is exactly what the HNSW index (Part 3) is built to accelerate.
  • %(query)s/%(repo_id)s/%(top_k)s — this is psycopg's named parameter style (a dict, rather than the positional tuple style seen in Part 10's %s placeholders). Functionally identical safety guarantee (still fully parameterized, still injection-safe), just more readable when there are several placeholders, since you don't have to count position to know which value fills which slot.
  • ::vector is a Postgres type cast — psycopg sends the Python list as a generic value, and this tells Postgres explicitly "treat this as the vector type" so the <=> operator (which is only defined for vector-typed operands) applies correctly.
  • ORDER BY distance LIMIT %(top_k)s — critically, ORDER BY on a column computed via <=> against an hnsw-indexed column is exactly the query shape Postgres's query planner recognizes and routes through the HNSW index automatically, rather than computing the distance for every row and sorting all of them (which is what would happen without the index, or with a filter shape the planner doesn't recognize as index-friendly). top_k defaults to 8 — the "K" in "top-K retrieval," how many chunks get pulled into the prompt per question. This is a tunable trade-off: too few risks missing the answer entirely; too many dilutes the prompt with less-relevant code and costs more tokens.
  • SearchResult(*row) — row is a plain tuple from psycopg (one per SQL column, in the order selected); *row unpacks it as positional arguments into the dataclass constructor. This relies on the SELECT column order exactly matching SearchResult's field declaration order — a small implicit coupling worth being aware of if either one is ever reordered independently.
Notice there's no WHERE filtering by kind/file/language — every search is scoped only by repo_id (so results from a different indexed repo never leak in) and otherwise searches the entire vector space for that repo indiscriminately. A function, a class, and a leftover module-level chunk all compete on equal footing for the same top-8 slots, purely by embedding distance to the question.

Part 13 — Generation: streaming LLM answers, fallback chains

Turning "question + relevant code" into a written answer, resiliently.

Files: sleuth/llm/generate.py

Concept — why an ABC here too, and why a "fallback chain"? Same reasoning as the Embedder ABC in Part 8: the rest of the codebase (answer-building, the eval harness, the agentic loop) just wants "something I can send chat messages to and get text back," without caring whether that's Groq or NVIDIA NIM under the hood. The added twist here is a fallback chain: if the primary provider (Groq, by default) fails — rate-limited, having an outage — the code automatically retries the exact same request against a secondary provider (NIM) instead of just failing the user's question outright. This is a step beyond the single-request retry in Part 9 (which handles one provider being briefly flaky) — this handles one entire provider being unavailable for longer, by having a second, independent provider ready to take over. 
class Generator(ABC):
    model_name: str
    timeout: float = DEFAULT_TIMEOUT

    def __init__(self, api_key: str, model_name: str | None = None):
        self.api_key = api_key
        if model_name:
            self.model_name = model_name

    @abstractmethod
    def _url(self) -> str: ...

    async def chat(self, messages: list[dict], stream: bool = True) -> AsyncIterator[str]:
        async with httpx.AsyncClient(timeout=self.timeout) as client:
            if stream:
                async for token in self._stream_chat(client, messages):
                    yield token
            else:
                yield await self._chat_once(client, messages)
  • This is the payoff of using an ABC mentioned back in Part 1: chat() — the actual public method everything else calls — is written once, here on the base class, not duplicated in GroqGenerator and NimGenerator. Each subclass supplies only _url() (and its own default model_name/timeout) — genuinely the only thing that differs between "call Groq" and "call NIM," since both providers speak an OpenAI-compatible chat completions API shape.
  • if model_name: self.model_name = model_name — lets a caller override the class-level default (GroqGenerator.model_name = "openai/gpt-oss-120b") per-instance. This is how Config.groq_model (from Part 2, defaulting to "openai/gpt-oss-120b" but overridable via the GROQ_MODEL env var) flows through to actually change which Groq model gets called, without editing this file.
  • stream: bool = True branching inside chat() — when stream=True (the normal interactive sleuth ask case, Part 14), it delegates to _stream_chat (the async generator from Part 1, yielding token by token). When stream=False (used by the agentic loop in Part 16 and the eval harness in Part 17, both of which need the complete response before they can decide what to do next), it awaits the whole response at once via _chat_once and yields it as a single item — note this still makes chat() an async generator either way (always has at least one yield in its body), so callers can always write the same async for token in generator.chat(...) loop regardless of which mode they used; in the non-streaming case that loop just runs exactly once.
class GroqGenerator(Generator):
    model_name = "openai/gpt-oss-120b"
    def _url(self) -> str: return GROQ_URL


class NimGenerator(Generator):
    model_name = "meta/llama-3.1-70b-instruct"
    timeout = 120
    def _url(self) -> str: return NIM_URL


def get_fallback_chain(config: Config) -> list[Generator]:
    chain = [get_generator(config)]
    if config.generation_provider == "groq" and config.nim_api_key:
        chain.append(NimGenerator(api_key=config.nim_api_key))
    return chain


async def chat_with_fallback(chain: list[Generator], messages: list[dict], stream: bool = True) -> AsyncIterator[str]:
    last_error: Exception | None = None
    for generator in chain:
        try:
            async for token in generator.chat(messages, stream=stream):
                yield token
            return
        except (httpx.HTTPStatusError, httpx.TransportError) as exc:
            last_error = exc
            continue
    raise RuntimeError(f"All generators in fallback chain failed: {last_error}")
  • get_fallback_chain builds an ordered list: the configured primary provider always first, and — only if the primary IS Groq (not already NIM) AND an NIM key is actually configured — NIM appended as a second option. If you've explicitly configured NIM as your primary, there's no third provider to fall back to; if you have no NIM key at all, the chain is just [GroqGenerator], one entry, and any Groq failure simply propagates with nothing to catch it.
  • chat_with_fallback is itself also an async generator (the AsyncIterator[str] return type + yield token inside), so it composes with everything else that expects "a thing I can async for token in ... over." Walk the logic: try the first generator in the chain; stream its tokens through as they arrive (yield token re-yields each one up to whoever called chat_with_fallback); if it completes without error, return immediately — done, no fallback needed. If it raises one of the two expected network/HTTP exception types, remember the error and continue to the next generator in the chain instead. Only if every generator in the chain fails does this raise its own RuntimeError, carrying the last error seen for debugging.
  • One subtlety worth flagging explicitly: because tokens are yielded as they stream in, a failure that happens partway through a streaming response (say, Groq streams 40 tokens successfully, then the connection drops) means the caller has already received and displayed those 40 tokens before the exception triggers a silent restart from NIM — the user would see a partial answer, then a second, independent, complete answer appended right after it, with no indication a fallback happened. This is a known rough edge of streaming + fallback combined, not something hidden from you — worth knowing if you ever see a garbled double-answer in practice.

SYSTEM_PROMPT = (
    "You are a code assistant. Answer the user's question about the repository "
    "using only the provided code excerpts. If the excerpts don't contain the "

def build_prompt(question: str, results: list[SearchResult]) -> str:
    blocks = []
    for r in results:
        symbol = r.symbol_name or "(module level)"
        blocks.append(
            f"# File: {r.file_path}\n# {r.kind}: {symbol} (lines {r.start_line}-{r.end_line})\n\n{r.code_text}"
        )
    context = "\n\n---\n\n".join(blocks)

async def stream_answer(question: str, repo_id: str, conn, config: Config) -> AsyncIterator[str]:
    row = conn.execute("SELECT status FROM repos WHERE id = %s", (repo_id,)).fetchone()
    if row is None or row[0] != "ready":
        raise ValueError(f"Repo {repo_id} is not ready to query (status={row[0] if row else 'missing'})")

    embedder = VoyageEmbedder(api_key=config.voyage_api_key)
    query_vector = (await embedder.embed_batch([question]))[0]
    results = search_chunks(conn, repo_id, query_vector)
    prompt = build_prompt(question, results)

    chain = get_fallback_chain(config)
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": prompt},
    ]
    async for token in chat_with_fallback(chain, messages, stream=True):
        yield token

  • Guard clause first: refuse to answer if the repo isn't status = 'ready' — you can't meaningfully search a repo that's still indexing, failed to index, or doesn't exist. This is a fast, clear failure instead of running a search against an empty or partial chunks table and getting a nonsensical or empty result silently.
  • Embed the question the exact same way chunks were embedded: embedder.embed_batch([question]) — note it's called with a list containing one string, because embed_batch's signature always takes a list (Part 8), even though here there's only one text to embed; [0] then pulls the single resulting vector back out. This is a hard requirement of how embedding spaces work — the question and the code chunks must be embedded by the same model for their vectors to be comparable at all; a Voyage-embedded question vector compared against a hypothetical NIM-embedded code vector would be comparing two unrelated coordinate systems, producing meaningless distances.
  • Search: search_chunks(conn, repo_id, query_vector) — Part 12's function, called with the default top_k=8.
  • build_prompt: this is where retrieval output (a list of SearchResult objects) becomes one plain string ready to hand to an LLM. Each result is formatted with the same "File / kind / symbol" header style established by format_chunk_context back in Part 4 (not literally the same function — this one additionally includes the line range — but the same design instinct: always tell the model exactly what it's looking at, not just bare code). Results are joined with a visible \n\n---\n\n separator so the model can clearly tell where one code excerpt ends and the next begins — a chunk boundary that's ambiguous to the model could cause it to misattribute code from one function to another when explaining.
  • System + user message split: the SYSTEM_PROMPT sets the model's role/behavior ("only use the provided excerpts, admit uncertainty rather than guess" — this is a deliberate anti-hallucination instruction, critical for a code assistant since a confidently wrong answer about how code works is worse than an honest "I don't have enough information"). The user message carries the actual question-plus-retrieved-code payload built by build_prompt. This system/user split is the standard chat-completions message structure essentially every modern chat LLM API expects.
  • Fallback + stream: get_fallback_chain(config) (Part 13) builds the Groq-then-maybe-NIM chain, and chat_with_fallback(..., stream=True) is what actually talks to the network and streams tokens back — this whole function (stream_answer) is itself an async generator, forwarding each token onward via its own yield. Ultimately the CLI's ask command (Part 15) is what actually print(token, end="")s these — the terminal you see tokens appear in one at a time is this exact generator chain, unwound.
async def get_answer(question: str, repo_id: str, conn, config: Config) -> str:

A small but useful pattern: [token async for token in ...] is an async list comprehension — same idea as a normal list comprehension, but iterating an async generator instead of a regular iterable. This exists because sometimes (the eval harness in Part 17, for instance) you don't want streaming at all — you just want the complete final answer as one string, to score it. Rather than duplicating the whole retrieval+prompt+generation logic, get_answer reuses stream_answer unchanged and simply drains every token it yields into one joined string. This is a common, useful trick: build the streaming version as the one true implementation, then derive a non-streaming convenience wrapper from it "for free" by just consuming it fully instead of incrementally.

  • Notice the early branch: if args.command == "agentic": ... return happens before a database connection is ever opened. Every other subcommand needs a connection (opened + schema-applied once, shared across that single invocation, closed in the finally — guaranteeing cleanup even if the command raises), agentic mode structurally cannot, because it returns before that code even runs.

Everything inside main and everything it calls can freely use await because it's all running inside this one event loop, started here, at the very outermost layer of the program. sys.argv[1:] slices off the program name itself (sys.argv[0], always the script name) so argv passed to main is just the actual user-supplied arguments.

Part 16 — Agentic mode: the tool-use loop

No database, no embeddings — the LLM investigates the repo itself, like a human would.

Files: sleuth/retrieve/agentic.py

Concept — what makes this "agentic," and why does it exist alongside indexed search? Indexed retrieval (Parts 5-12) requires an upfront cost: clone, parse, chunk, embed every file, before you can ask even one question. That's the right trade for a repo you'll query repeatedly (a remote GitHub URL you're studying over days). But if you just want to ask ONE quick question about the code sitting in your current local directory right now, waiting through a full index run first is wasteful. Agentic mode instead gives the LLM a small set of tools — grep, list_files, read_file — that mirror how a human developer would actually explore an unfamiliar codebase (search for a term, list files in a directory, open a specific file), and lets the model decide, turn by turn, which tool to call and with what arguments, feeding each tool's result back to it, until it has enough information to answer directly in plain prose. This pattern — model calls tools in a loop, observing results, deciding the next action — is the general definition of an "agent" as the term is used in LLM engineering right now. 
SYSTEM_PROMPT = (
    "You are a code assistant investigating a local codebase to answer the user's "
    "question. You have three tools:\n"
    "  grep(pattern, glob=null) -- regex search across files, first 50 matches\n"
    "  list_files(glob) -- list files matching a glob\n"
    "  read_file(path, start_line=null, end_line=null) -- read up to 400 lines of a file\n"
    "To call a tool, respond with EXACTLY one line in this form and nothing else:\n"
    'TOOL:  {"arg": "value", ...}\n'
    "When you have enough information to answer, respond with your final answer as "
    "plain prose (no TOOL: prefix)."

_TOOL_LINE_RE = re.compile(r"^TOOL:\s*(\w+)\s*(\{.*\})\s*$", re.MULTILINE)


def _parse_tool_call(text: str) -> tuple[str, dict] | None:
    match = _TOOL_LINE_RE.search(text.strip())
    if not match:
        return None
    try:
        args = json.loads(match.group(2))
    except json.JSONDecodeError:
        return None
    return match.group(1), args
  • This is a hand-rolled text protocol, not a "function calling" API feature. Some LLM providers offer a native structured "tool calling" mode where the model returns properly typed JSON tool-call objects instead of free text. SLEUTH's agentic mode doesn't use that — per the project's "no black-box library... for them" ethos, it defines its own tiny protocol directly in the system prompt: the model must respond with the literal text TOOL: toolname {"json": "args"} on one line to call a tool, or plain prose (no such prefix) when it's ready to give a final answer. This is more fragile than a provider's native structured mode (a model that slightly deviates in formatting breaks the parser) but is fully transparent and provider-agnostic — works identically with Groq or NIM, whichever the fallback chain (Part 13) resolves to.
  • _TOOL_LINE_RE is a compiled regex: ^TOOL:\s*(\w+)\s*(\{.*\})\s*$ with re.MULTILINE. Breaking it down — ^/$ anchor to a line start /end (only meaningful because of MULTILINE, which makes ^/$ match at every line boundary in the text, not just the very start/end of the whole string). TOOL:\s* matches the literal prefix plus any whitespace. (\w+) captures the tool name (word characters only). \s*(\{.*\})\s* captures everything from the first { to the last } on that line as the JSON arguments blob — .* is greedy, so it grabs as much as possible up to the last closing brace on the line, which matters for JSON containing nested objects.
  • _parse_tool_call returns either (tool_name, args_dict) or None — None covers two distinct cases treated identically by the caller: no TOOL: line was found at all (the model gave its final prose answer), OR a TOOL: line was found but its JSON was malformed (json.JSONDecodeError caught explicitly). Both cases fall through to "treat this response as the final answer" — a pragmatic choice: rather than crashing or retrying on a malformed tool call, the loop just accepts whatever text came back as the answer. This is a reasonable simplification for a hand-rolled protocol, though worth knowing it means a genuinely broken tool-call attempt silently becomes a (probably bad) final answer instead of an explicit error.
async def run_agentic(question: str, path: str, config: Config, generator=None) -> AsyncIterator[str]:
    generator = generator or get_generator(config)
    root = Path(path)
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": question},
    ]

    for _ in range(MAX_ITERATIONS):
        response_text = await _call(generator, messages)
        parsed = _parse_tool_call(response_text)

        if parsed is None:
            yield response_text
            return

        messages.append({"role": "assistant", "content": response_text})
        name, args = parsed
        result = _dispatch_tool(name, args, root)
        messages.append({"role": "user", "content": f"Tool result: {result}"})

    messages.append({"role": "user", "content": "Iteration limit reached. Answer the original question "
                      "with what you've gathered so far, as plain prose."})
    response_text = await _call(generator, messages)
    yield response_text + "\n\n(Note: search was cut short after reaching the iteration limit.)"
  • generator = generator or get_generator(config) — accepts an optional pre-built generator (used by tests, to inject a fake/mock generator instead of hitting a real API), defaults to constructing the real one from config otherwise. Note this uses get_generator (Part 13's single-provider factory), not get_fallback_chain — agentic mode does not get automatic Groq→NIM fallback; a provider failure here just raises. A deliberate simplicity trade-off, or possibly an area worth extending later.
  • messages starts as a two-entry list (system prompt + the user's question) and grows every iteration — each tool call and its result get appended as {"role": "assistant", ...} (the model's own tool-call text) then {"role": "user", ...} (the tool's result, framed as if the user is reporting it back — a common convention since most chat APIs don't have a dedicated "tool result" role in this hand-rolled protocol). By the time the model is asked to respond again, it sees the entire conversation so far — its own past tool calls and every result — which is how it "remembers" what it already searched for and read, and can decide what to look at next instead of repeating itself.
  • The loop runs for _ in range(MAX_ITERATIONS) — MAX_ITERATIONS = 6. Each pass: call the model non-streaming (_call wraps generator.chat(messages, stream=False) and joins the single yielded chunk — see Part 13's note on why stream=False is required here: the loop needs the model's complete response before it can decide "is this a tool call or the final answer?", which is impossible to know from a partial stream of tokens). If the response parses as a tool call, dispatch it, append both the call and its result to messages, and loop again. If it does NOT parse as a tool call (parsed is None), treat it as the final answer — yield it and return immediately, ending the whole generator.
  • The iteration cap matters: if the model is still calling tools after 6 rounds without giving a final answer, the loop doesn't just cut off silently — it appends one more explicit instruction message ("Iteration limit reached. Answer with what you've gathered so far") forcing a final answer out of the model on this extra, 7th call, then appends a note to the user that the search was cut short. This guards against runaway loops (a model that keeps grep-ing forever, burning API calls/time indefinitely) while still trying to give a useful partial answer rather than just failing outright.

The tools themselves — deliberately small and sandboxed

def _tool_grep(root: Path, pattern: str, glob: str | None = None) -> str:
    regex = re.compile(pattern)
    matches = []
    paths = sorted(root.rglob(glob or "*"))
    for path in paths:
        if not path.is_file() or ".git" in path.parts:
            continue
        try:
            text = path.read_text(errors="ignore")
        except OSError:
            continue
        for lineno, line in enumerate(text.splitlines(), start=1):
            if regex.search(line):
                matches.append(f"{path.relative_to(root)}:{lineno}: {line.strip()}")
                if len(matches) >= GREP_MAX_MATCHES:
                    return "\n".join(matches) + "\n... (truncated at 50 matches)"
    return "\n".join(matches) if matches else "(no matches)"
  • This is a hand-written grep, not a subprocess call to the real grep binary (unlike Part 7's clone, which does shell out to real git) — likely because a pure-Python implementation avoids platform differences in grep flags/behavior and keeps the whole tool sandboxed to a single well-understood code path.
  • errors="ignore" on read_text — silently drops bytes that can't be decoded as UTF-8 rather than raising, so one file with unusual encoding doesn't blow up the whole search; similarly the try/except OSError: continue skips files that can't be read at all (permissions, broken symlinks) without aborting.
  • GREP_MAX_MATCHES = 50 — a hard cap, enforced by returning early the moment it's hit, not just truncating the final list. This bounds both the tool's own runtime (won't keep scanning a huge repo after 50 matches are already found) and, just as importantly, how many tokens get fed back into the model's context as a "tool result" — an unbounded grep result on a big codebase could itself blow the context budget.
  • Every tool takes root: Path as its scope, and root is always exactly the path argument the user passed to sleuth agentic <path> <question> — there's no way for the model to read_file("/etc/passwd") or otherwise escape that directory via these specific tool implementations as written (paths are joined under root, e.g. target = root / path in _tool_read_file), though it's worth knowing this project hasn't hardened against a deliberately malicious path like "../../etc/passwd" — Python's / path-join wouldn't stop .. segments from escaping root, and there's no explicit check here that the resolved path stays inside root.
Q for you: That last point (no path-escape guard on read_file/ grep) is a genuine, small security gap — low-severity for a personal local tool where you trust the model not to be adversarial, but worth knowing about. Part 17 — Eval harness: measuring if any of this actually works

The difference between "I built a RAG pipeline" and "I built a RAG pipeline that's actually good."

Files: sleuth/eval/runner.py

Concept — why an eval harness at all? It's easy to build a RAG pipeline that runs without crashing and produces plausible-sounding answers — and much harder to know whether it's actually retrieving the right code and giving correct answers, especially as you tweak chunking strategy, embedding model, prompt wording, or top_k. Without a repeatable, scored test set, every change is a guess evaluated by "eyeballing a few manual questions," which doesn't scale and doesn't catch regressions. A golden set — a fixed list of (question, expected correct file/symbol, optionally a reference answer) pairs — turns "is this good?" into a number you can track over time and compare before/after a change. 
@dataclass
class GoldenCase:
    question: str
    expected_files: list[str]
    expected_symbols: list[str] = field(default_factory=list)
    reference_answer: str = ""


def load_golden(path: str) -> tuple[str, list[GoldenCase]]:
    data = yaml.safe_load(Path(path).read_text())
    cases = [
        GoldenCase(
            question=c["question"],
            expected_files=c.get("expected_files", []),
            expected_symbols=c.get("expected_symbols", []),
            reference_answer=c.get("reference_answer", ""),
        )
        for c in data.get("cases", [])
    ]
    return data["repo"], cases
  • field(default_factory=list) — a dataclass quirk worth understanding: you cannot write expected_symbols: list[str] = [] directly as a dataclass field default. Python mutable defaults are a classic footgun — if it were written that way, every instance of GoldenCase that didn't specify expected_symbols would share the exact same list object, so appending to one instance's list would silently affect all the others. field(default_factory=list) instead tells the dataclass machinery to call list() fresh for each new instance that needs the default, giving every instance its own independent empty list.
  • This is a plain YAML file being parsed into typed Python objects — yaml.safe_load (never plain yaml.load, which can execute arbitrary Python objects embedded in a malicious YAML file — safe_load restricts parsing to plain data types only) turns the file into nested dicts/lists, and the list comprehension explicitly constructs one GoldenCase per entry under the file's cases: key, using .get(key, default) for the optional fields so a golden case that omits reference_answer (skipping LLM-judge scoring for that one case, see below) doesn't break parsing.
def _hit_and_rank(results, case: GoldenCase) -> tuple[bool, float]:
    for rank, r in enumerate(results, start=1):
        file_hit = r.file_path in case.expected_files
        symbol_hit = bool(case.expected_symbols) and r.symbol_name in case.expected_symbols
        if file_hit or symbol_hit:
            return True, 1.0 / rank
    return False, 0.0

Two separate metrics computed here — this is standard information-retrieval evaluation, worth learning properly since it applies far beyond this project:

  • Hit rate: did the retrieved top-K results contain at least one chunk from the expected file(s) or symbol(s)? A simple yes/no per question. Aggregated across all cases (in _format_table), hit_rate = sum(hits) / len(cases) — e.g. "hit-rate@8: 0.85" means 85% of golden questions had a correct chunk somewhere in their top-8 retrieved results.
  • MRR (Mean Reciprocal Rank): hit rate alone doesn't distinguish "the correct chunk was ranked #1" from "it barely scraped into position #8" — both count as a hit equally. Reciprocal rank fixes that: 1.0 / rank — a hit at rank 1 scores 1.0 (perfect), rank 2 scores 0.5, rank 8 scores 0.125, a total miss scores 0. Averaged across all cases, this is MRR — a single number that rewards ranking the right answer near the top, not just including it somewhere in the results. enumerate(results, start=1) is what makes rank 1-indexed (rank 1 = the single most-similar chunk by cosine distance) instead of Python's normal 0-indexing.
  • bool(case.expected_symbols) and ... — a case with no expected_symbols specified in the golden YAML never scores a symbol_hit (short-circuits to False immediately, since bool([]) is False), avoiding a subtle bug where an empty expected_symbols list combined with a result whose symbol_name is also None could otherwise accidentally read as "expected None, got None, match!"

This is deliberate and important: the eval harness measures the pipeline exactly as a real user would experience it, not some simplified stand-in — if build_prompt's format ever changes, eval automatically measures the new format too, with zero eval-code changes needed.
  • The third metric — LLM-judge scoring: hit-rate and MRR only measure retrieval quality (did we find the right code), not whether the final generated answer was actually good. For that, this uses another LLM call (judge.chat(...), via get_generator(config) — a plain single generator, no fallback needed since this is an offline batch-scoring run, not a live user-facing request) with a small grading prompt: "compare the produced answer against a known-good reference answer, score 1-5, respond with ONLY the digit." This is the "LLM-as-judge" pattern — using a language model itself to grade another language model's output, useful because free-text answer quality is otherwise hard to score with simple string matching (two correct answers can be worded completely differently).

  • _parse_judge_score uses re.search(r"[1-5]", text) to pull the first digit 1-5 out of the judge's response text — a small defensive touch, since even with an explicit "respond with ONLY the digit" instruction, LLMs sometimes wrap the answer in extra text anyway ("I'd rate this a 4.") — a regex search rather than a strict int(text) tolerates that.
Reading the final table: run_eval returns a plain formatted text table (via _format_table) with one row per question — hit (True/False), rr (reciprocal rank, 0.00-1.00), judge (1-5 or -) — plus a final aggregate line: hit-rate@8: 0.XX MRR: 0.XX avg judge: X.X. Part 18 — Multi-language chunking: CSS, JSX/TSX, Vue, HTML

Extending the pipeline beyond Python/JS/TS to cover the rest of a real web stack — and two real bugs found and fixed along the way, not just new features bolted on.

Files: sleuth/ingest/css_chunker.py, sleuth/ingest/vue_chunker.py, sleuth/ingest/html_chunker.py, sleuth/ingest/markup_shared.py, sleuth/ingest/queries/javascript.scm, sleuth/ingest/queries/typescript.scm, vendor/tree-sitter-vue/

Concept — three different chunking shapes for three different kinds of language Python/JS/TS all share one shape: functions, classes, methods (Parts 5-6). Extending coverage meant recognizing that not every language has that shape at all, and forcing one onto it would be actively wrong, not just imprecise:
  • CSS has no functions — its natural unit is a rule (a selector plus its declaration block, or an at-rule like @media/@keyframes). Chunked structurally: walk the top-level nodes, one chunk per rule, no query needed at all.
  • HTML also has no functions — its natural unit is a markup section (an element and everything nested inside it). Chunked the same structural way, but with an extra wrinkle: HTML documents also embed other languages inline via <script>/ <style>, which need to be pulled out and handed to the JS/CSS chunkers, not chunked as raw markup themselves.
  • Vue single-file components (.vue) are the most different: literally three sub-languages in one file — a template (markup, not JS/CSS), a script (JS/TS), and a style block (CSS). Chunked by splitting the file at those three boundaries first, then handing the script/style content back into the exact same pipeline a standalone .js/.css file would go through.
This is why the fix effort for JSX/TSX and the fix effort for Vue/HTML look so different: JSX/TSX are still fundamentally JS/TS (Part 6's shape applies, something was just missing from the query patterns), whereas Vue/HTML needed genuinely new chunking logic, not a patch to the existing one.

CSS: structural chunking, one rule per chunk

    # ...leftover (comments, @import) becomes one "module" chunk, same
    # convention as the Python/JS chunker's junk bucket (Part 6)
  • No tree-sitter query here at all — just a plain loop over root.children checking each node's .type directly. This is the simplest possible chunker in the whole codebase, and deliberately so: CSS's top-level shape is flat (a stylesheet is just a sequence of rules, no nesting of one rule inside another the way a method nests inside a class), so there's no overlap/dedup problem to solve the way Part 6's query-based approach had to.
  • @media/@keyframes/@font-face are each kept as one chunk, not split into their inner rules — a @media screen { .a{...} .b{...} } block becomes a single chunk containing both inner rules, because the media query condition is part of what makes those rules meaningful (a rule inside a breakpoint means something different from the same selector outside one).
  • A real constraint discovered, not assumed: .scss is deliberately not registered to use this CSS grammar. Directly testing tscss's parser against real SCSS syntax ($variables, nested rule blocks, @mixin) produced has_error=True — the plain CSS grammar genuinely cannot parse SCSS-only syntax. Rather than silently mis-chunk `.scss` files, they fall through to the generic blank-line fallback chunker (same honest-degradation choice as any unsupported extension) until a real tree-sitter-scss grammar is added as its own task.

JSX/TSX: a real bug found by testing before assuming the fix would work

Concept — the arrow-function-component gap The original JS/TS query files (Part 6) only matched function_declaration/ class_declaration node types. Modern JS/TS — and virtually all React code — very often writes functions as const Foo = () => {...} instead. That's not a function_declaration in tree-sitter's grammar at all — it's a variable_declarator whose value happens to be an arrow_function. The old queries had no pattern for this shape, so every arrow-function component, every export const useThing = () => {...} hook, and every class-field arrow handler (handler = () => {...}) was silently falling into the "leftover module chunk" — exactly the same failure mode Part 6 already documents for undecorated wrapper nodes, just a different node type triggering it. This was found by directly parsing real React-shaped code and inspecting the tree before writing any fix, not guessed at.

HTML: the same recursion trick, plus a real design mistake caught before shipping

def _sectioning_roots(root: Node, source_bytes: bytes) -> list[Node]:
    html_element = next(
        (c for c in root.children if c.type == "element" and _tag_name(c, source_bytes) == "html"),
        None,
    )
    if html_element is None:
        return list(root.children)  # fragment file, no  wrapper

    sections: list[Node] = []
    for child in html_element.children:
        if child.type != "element":
            continue
        tag = _tag_name(child, source_bytes)
        if tag in ("head", "body"):
            sections.extend(child.children)
        else:
            sections.append(child)
    return sections
This function exists because the first version of the HTML chunker was wrong, and testing caught it before it shipped. The obvious first approach — chunk at document.children directly, same as CSS's flat rule list — was tried first. Directly running it against a realistic <!DOCTYPE html><html><head>...</head> <body>...</body></html> skeleton exposed the problem immediately: a full HTML document has exactly one top-level element (<html>), so "one chunk per document-root element" produced one giant chunk covering the entire page — the opposite of what chunking is for. _sectioning_roots is the fix: it looks specifically for an <html> wrapper, and if found, descends through it and its <head>/ <body> children specifically, returning their children as the actual chunk-worthy set. A fragment file with no <html> wrapper at all (common for partials/ includes rendered by a server-side template engine) falls through unchanged to the document's direct children, since there's no wrapper to descend through in the first place. 
_JS_SCRIPT_TYPES = {"text/javascript", "application/javascript", "module", "text/babel"}

def _is_chunkable_script(start_tag: Node, source_bytes: bytes) -> bool:
    script_type = attribute_value(start_tag, "type", source_bytes)
    return script_type is None or script_type.lower() in _JS_SCRIPT_TYPES
A second real distinction from Vue, found while implementing this: HTML overloads <script> for non-code payloads too — <script type="application/json"> (JSON-LD, embedded config data) and <script type="text/template"> (client-side templating libraries) are both completely legitimate, common HTML, and neither is JavaScript. Vue's <script lang="ts"> never has this ambiguity — a Vue SFC's script block is always code. Blindly feeding an HTML page's every <script> block through the JS chunker would produce actively wrong chunks (a JSON payload mis-tagged and mis-parsed as JavaScript, polluting search results with garbage). This check — verified with a direct test asserting the JSON payload text does not appear in any produced chunk — is what prevents that: only a script with no type attribute at all, or a recognized JS MIME type, gets routed through chunk_embedded_block; anything else is skipped outright.
Also worth knowing: <script>/<style> elements are explicitly excluded from the plain structural "element" chunking pass (_chunk_body_elements checks and skips any child tagged script/style). Without that exclusion, they'd be chunked twice — once as raw, unparsed markup text via the generic element pass, and again correctly parsed as JS/CSS via chunk_embedded_block — duplicating content and diluting search relevance, the same class of problem Part 6 already solved once for whole-class-vs-methods in Python/JS.

What's shared between Vue and HTML, and why it was factored out

Both grammars produce the identical node shapes for attributes (start_tag → attribute → attribute_name/quoted_attribute_value) and embedded blocks (script_element/style_element → raw_text) — confirmed by directly inspecting both parsers' trees side by side, not assumed just because they're both "HTML-flavored." Rather than writing (and maintaining, and re-testing) the attribute-reading and line-offset-correction logic twice, it was pulled into a new shared module, sleuth/ingest/markup_shared.py, used by both vue_chunker.py and html_chunker.py. This is the same instinct behind format_chunk_context being centralized back in Part 4 — logic genuinely shared between two callers belongs in one place, not copy-pasted and left to drift.

Part 21 — Auth: sessions, cookies, and per-user ownership

A CLI has one implicit user: whoever's running the terminal. A web app serving strangers over the internet needs to actually know who's asking.

Files: sleuth/api/routes/auth.py, sleuth/api/auth/session.py, sleuth/store.py

Concept — why a signed cookie, not just "remember the user server-side"? HTTP is stateless — every request arrives with no memory of any previous request. To know "this request is from the user who signed up as alice@example.com," the server needs some piece of evidence the browser sends back on every subsequent request. A session cookie is that evidence: a small piece of data the browser stores and automatically resends. The word signed is doing the real security work here — the cookie isn't just "the user's id in plain text" (which anyone could forge by typing a different id into their own cookie), it's cryptographically signed with a secret only the server knows, so the server can verify "this cookie's contents were genuinely produced by me, and haven't been tampered with," without needing a database lookup on every single request just to check session validity. 
from itsdangerous import URLSafeTimedSerializer

def create_session_cookie(user: dict, secret: str) -> str:
    serializer = URLSafeTimedSerializer(secret)
    return serializer.dumps({"id": user["id"], "email": user["email"], ...})

def read_session_cookie(cookie_value: str, secret: str) -> dict | None:
    serializer = URLSafeTimedSerializer(secret)
    try:
        return serializer.loads(cookie_value, max_age=SESSION_MAX_AGE_SECONDS)
    except (BadSignature, SignatureExpired):
        return None
  • URLSafeTimedSerializer(secret) — itsdangerous is a small, well-audited library purpose-built for exactly this: sign a small blob of data, embed an expiry timestamp, encode it into a URL/cookie-safe string. .dumps(...) serializes the dict and signs it; .loads(..., max_age=...) verifies the signature and checks it hasn't expired, raising a specific exception either way if something's wrong.
  • A tampered cookie (anyone editing the id field by hand, without knowing the secret) fails signature verification instantly — read_session_cookie returns None, and require_session (the FastAPI dependency every protected route uses) turns that into a 401, with zero database round trips needed to detect the forgery.

Part 22 — Connection pools and background tasks: serving many browsers at once

The CLI opens one database connection and uses it once. A web server has to juggle many browsers, all at once, all wanting a connection.

Files: sleuth/db.py, sleuth/api/main.py

Concept — why a pool instead of "open a connection per request"? Opening a fresh Postgres connection is a real, relatively slow operation — a TCP handshake, TLS negotiation, authentication — especially against a cross-region database like Supabase in production. Doing that inside an async def route handler blocks the entire event loop for that handshake, which means every other in-flight request — even completely unrelated ones, like a different browser tab's routine "list my repos" poll — visibly queues up behind it. A connection pool (psycopg_pool.ConnectionPool) opens a handful of connections once, up front, and hands existing ones out on a fast in-process borrow — no network handshake needed per request, just picking an already-open connection out of a small pile. 
def create_pool(database_url: str, *, min_size: int = 1, max_size: int = 10) -> ConnectionPool:
    return ConnectionPool(
        conninfo=database_url, min_size=min_size, max_size=max_size,
        kwargs={"autocommit": True}, configure=_configure_pooled_connection, open=True,
    )
  • max_size=10 — a hard cap on how many connections this one server process will ever hold open simultaneously. This number is exactly why how-chat-works.html Part 3 goes to the trouble of releasing its retrieval connection early, mid-stream — 10 is not a large number, and a handful of concurrent long-running chats holding a connection each for their entire streaming duration could genuinely exhaust it.
  • autocommit=True — every statement commits itself the instant it runs, rather than the psycopg default of implicitly opening a transaction on the first query that then has to be explicitly committed or rolled back. Before this, a read-only GET route that only ever queries (no writes, so never calls commit()) still left its connection in an open transaction when it went back to the pool — the pool then had to roll that transaction back before the next borrow could reuse it, a second hidden network round trip on top of the original query, for every single request. Measured impact against this project's actual Supabase instance: roughly 0.7-0.8s per request instead of ~0.2s.
  • configure=_configure_pooled_connection runs once per physical connection the pool opens (not once per borrow) — registering pgvector's type handler and setting lock_timeout only pays that setup cost min_size..max_size times total for the whole server's lifetime, not once per HTTP request.

Part 24 — Two real bugs found in production: doc-vs-code ranking & retry duplication

Both fixed. Both are exactly the kind of bug that only shows up once real users start actually using the thing.

Files: sleuth/chunking.py, sleuth/retrieve/search.py, sleuth/api/routes/repos.py

Bug 1: documentation crowding out real code

What happened: asking an architecture-flavored question against a repo containing both real source and hand-written architecture write-ups under a docs/ directory (e.g. docs/recruiter-authentication.html — a genuine, parseable HTML file, chunked and embedded exactly like real source) returned only documentation excerpts. The model correctly said it had no actual source code to cite — because none was ever retrieved into its context at all.

Root cause: prose about an architecture question can score a closer cosine match against that same question than the real implementation does — a write-up literally titled "how authentication works," phrased conversationally, can be semantically nearer to "how does auth work?" than the terse, jargon-dense actual code implementing it. Plain ORDER BY distance has no way to distinguish "real code" from "documentation about the code" — it just returns whichever wins on raw geometric distance. The fix touched four layers, each closing a different part of the gap: a new Chunk.is_doc property (true for anything under a docs/doc/ documentation directory at any depth), a new is_doc boolean column persisted alongside every chunk, search_chunks's ORDER BY is_doc, distance ranking real code strictly ahead of documentation (falling back to docs only once every code chunk is exhausted, so a genuinely doc-only question still gets answered), and an explicit [CODE]/[DOCUMENTATION] label on every excerpt in the prompt itself, with the system prompt telling the model to prefer citing code. Full code-level walkthrough: docs/how-chat-works.html Part 5.

Bug 2: retrying a failed index silently duplicated the repo

What happened: retrying a failed index used to just call POST /repos again with the exact same URL — and since create_repo has no uniqueness constraint on github_url (deliberately: nothing should stop two different users, or the same user twice, from legitimately indexing the same public repo), every retry silently inserted a second, brand-new repo row. The originally failed row just sat there forever, un-retried, un-watched, while a duplicate entry for the same repo piled up in the list on every subsequent attempt.

The fix: a dedicated POST /repos/{repo_id}/retry endpoint that always operates on the existing row (looked up by the id in the URL path, its github_url read back from that same row rather than trusted from the client), resetting its status and re-running the identical background ingest task against that one row. There is no code path in this endpoint capable of creating a second row for the same repo — the fix closes the ambiguity structurally rather than bolting a workaround onto the old endpoint. Full code-level walkthrough: docs/how-indexing-works.html Part 12.

Part 25 — Global/architecture-question retrieval: teaching the system to zoom out

Vector search finds fragments. Some questions need the whole picture.

Files: sleuth/summarize.py, sleuth/retrieve/routing.py, sleuth/retrieve/answer.py

Concept — why "rate my architecture" is structurally a different kind of question Every part of retrieval covered so far (Parts 10, 12, and how-chat-works.html Parts 4-5) is built around finding the k chunks nearest to a question. That's exactly the right tool for "where is X implemented" — the nearest chunk really is a good answer. But there is no single chunk, or any top-8 set of chunks, that is a good answer to "summarize this whole project" — broad questions need synthesis across most of the repo, not 8 arbitrary nearest neighbors. This was a real, reported production gap, closed with the smallest fix that actually addresses it: give the system one new artifact that does describe the whole repo, and a cheap way to know when to reach for it.

The mechanism is genuinely small — one new table, one new prompt, one regex. Full line-by-line treatment, including the deliberate "flat metadata listing instead of a full hierarchical summarization pass" scoping decision and its trade-offs, lives in docs/how-indexing-works.html Part 10 (the write side — generating and storing the summary during ingestion) and docs/how-chat-works.html Part 6 (the read side — the keyword classifier that decides when to use it). The short version, for context alongside everything else in this master document:

PieceWhat it does
repo_summaries tableOne row per repo — an LLM-written architecture summary, generated once per (re-)index from a cheap file/symbol/kind listing, not full source text
classify_question(question)A plain keyword regex (no LLM call) tagging a question "local" or "global" — both possible mistakes are harmless, so a free heuristic beats spending a model call classifying every question
build_prompt(..., summary=...)For a "global" question, the stored summary is prepended to the prompt, clearly labeled, ahead of the normal top-8 excerpts

Notice the pattern: this is the third time this document has shown "add one clearly-labeled block to the prompt, plus a cheap classifier to decide when it applies" as the fix for a retrieval gap (doc-vs-code labeling in Part 24 was the same shape of fix). That's not a coincidence — it's the natural shape of fixing "the model doesn't have the right context" problems in a system built around one shared build_prompt function: extend what goes into the prompt, gate it behind a cheap decision, and every caller (CLI and web app alike) benefits automatically, exactly the "one shared function, many callers" principle from Part 20.

Part 26 — The repo/chat lifecycle: retry, delete, and cascading foreign keys

A repo isn't just created and left alone forever — it can fail, get retried, or get deleted, and a chat can be deleted independently of its repo.

Files: sleuth/store.py, schema.sql, sleuth/api/routes/repos.py, sleuth/api/routes/chat.py

Concept — cascading deletes: letting the database enforce its own consistency Once chunks, repo_summaries, and chats all reference repos.id via a foreign key, a real question arises: what should happen to a repo's chunks and conversations when the repo itself is deleted? The naive answer is application code that remembers to manually DELETE FROM chunks WHERE repo_id = ..., then DELETE FROM chats WHERE repo_id = ..., then DELETE FROM messages WHERE chat_id IN (...), in the right order, every single place a repo might ever get deleted from. ON DELETE CASCADE moves that responsibility into the schema itself — declared once, on the foreign key, it becomes structurally impossible to forget: Postgres guarantees it, atomically, no matter which code path triggers the delete. 
CREATE TABLE IF NOT EXISTS chunks (
    ..., repo_id uuid NOT NULL REFERENCES repos(id) ON DELETE CASCADE, ...
);
CREATE TABLE IF NOT EXISTS repo_summaries (
    repo_id uuid PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE, ...
);
CREATE TABLE IF NOT EXISTS chats (
    ..., repo_id uuid NOT NULL REFERENCES repos(id) ON DELETE CASCADE, ...
);
CREATE TABLE IF NOT EXISTS messages (
    ..., chat_id uuid NOT NULL REFERENCES chats(id) ON DELETE CASCADE, ...
);

def delete_repo(conn, repo_id: str) -> None:
    conn.execute("DELETE FROM repos WHERE id = %s", (repo_id,))

One DELETE FROM repos statement is enough to remove the repo's chunks, its stored architecture summary, every chat about it, and (transitively, since messages cascades off chats which cascades off repos) every message in every one of those chats — all in one atomic operation. delete_chat is the same one-line pattern at a smaller scope: deleting a single chat row takes its messages with it, without touching the repo it belonged to at all.

Why this is a hard delete with no undo: the (not-yet-built) Repo Settings screen's own design copy already frames disconnecting a repo as destructive — "its index is deleted and past conversations about it become read-only" — so a hard cascading delete matches the feature's intended semantics, rather than adding a soft-delete/undo layer nothing in the design ever called for. The frontend gates both repo and chat deletion behind an inline click-to-confirm precisely because there's no way back.

Retry (covered fully in Part 24 above and how-indexing-works.html Part 12) is the other lifecycle event worth internalizing here: it reuses the exact same _run_ingest background task that a fresh POST /repos uses, just pointed at an existing row instead of a new one — one more example of this codebase preferring "reuse the same function with different inputs" over writing a parallel implementation for a closely related case.
