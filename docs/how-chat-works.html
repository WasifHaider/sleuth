Part 0 — The big picture

One sentence, then everything after this is just filling in how.

Concept — Retrieval-Augmented Generation, in one sentence Instead of asking an LLM a question and hoping it happens to already know the answer, SLEUTH first retrieves the handful of code chunks most relevant to your question (using the vector search built during indexing — see how-indexing-works.html), then generates an answer by handing the model your question plus those chunks as context, so it's answering from real evidence instead of guessing. Every part below is really just one of these two halves: Parts 4-6 are retrieval, Parts 7-8 are generation, and everything else is plumbing that makes those two halves usable from a real browser over a real network.

There are two completely separate code paths for "answer a question," and this document is almost entirely about the first one:

ModeWhen it's usedHow it finds relevant code
Indexed chat (this document, Parts 1-10) Asking about a repo you already added via the web app or sleuth add Pre-computed: vector search against chunks embedded during indexing
Agentic / live (Part 11, brief — has its own deep dive in pipeline-deep-dive.html Part 16) sleuth agentic against your current local directory, no upfront indexing No embeddings, no DB. The LLM itself decides to call grep/list_files/read_file in a loop

What actually leaves the browser the instant you press Enter.

Composer is a "dumb" component — it holds only the text you're currently typing (draft), and on submit it hands the trimmed text up to whatever function its parent (ChatScreen.jsx) gave it as onSend, then immediately clears the input. It has no idea what happens to that text next — that's ChatScreen's job, and specifically handleSend:

  • If this is the very first message in a fresh conversation, a chat row is created first (POST /chats) — a chat needs to exist before a message can be attached to it.

Part 2 — Server-Sent Events: how streaming actually works over HTTP

The mechanism that lets tokens appear on screen one at a time, like watching someone type, instead of the whole answer popping in at once.

Files: sleuth/api/routes/chat.py::_sse_frame, web/src/api.js::streamChat

Concept — why not just wait for the whole answer, then send it? An LLM generates text one token at a time internally regardless of how it's delivered — the only question is whether the server buffers all of that up before responding, or forwards each piece to the browser the moment it's produced. Buffering means staring at a blank screen for however many seconds the full answer takes to finish generating; forwarding each token immediately means the user sees progress right away, which feels dramatically faster even though the total time to finish is identical. Server-Sent Events (SSE) is a standard, simple HTTP mechanism for exactly this: a single long-lived HTTP response whose body is sent in small chunks over time, each one formatted as a tiny text protocol the browser (or, here, hand-rolled JavaScript) can parse incrementally as bytes arrive. 
def _sse_frame(event: str | None, data: str) -> str:
    prefix = f"event: {event}\n" if event else ""
    lines = "".join(f"data: {line}\n" for line in data.split("\n"))
    return f"{prefix}{lines}\n"

The SSE spec's format is: an optional event: <name> line, one or more data: <text> lines, then one blank line to mark "this event is complete." A plain token (event=None) has no event: line at all — that's the default, unnamed event type, what the frontend treats as "just append this text." A named frame like _sse_frame("sources", json.dumps(...)) lets the same one HTTP response carry multiple kinds of message: raw answer tokens, plus occasional structured events like "here are this answer's source citations" or "the chat's title just changed."

A real bug this exact function fixes: a single generated token can itself contain a raw "\n" — completely normal right after a code block's opening brace, say. But the SSE spec says a data: line cannot contain an embedded newline — it terminates the field the instant it hits one. The original code did yield f"data: {token}\n\n" directly; if token happened to be "{\n", that inner newline silently truncated the field and dropped everything after it, with no error anywhere — the bytes on the wire were still perfectly valid SSE, just wrong. _sse_frame's fix is to .split("\n") the data and emit one "data: "-prefixed line per physical line, exactly as the spec allows for multi-line payloads — and the frontend has a matching fix (Part 10) that rejoins them.

Part 3 — The route: POST /chat, guard checks, and connection lifetime

Where the actual request lands on the backend, and a genuinely tricky connection-management problem this route has to solve.

Files: sleuth/api/routes/chat.py, sleuth/api/schemas.py

class SendMessageIn(BaseModel):
    chat_id: str
    question: str = Field(max_length=8000)

Same Pydantic pattern as AddRepoIn in how-indexing-works.html Part 1: FastAPI validates the incoming JSON against this shape before the route body runs at all. max_length=8000 exists because this field was previously unbounded — a client could post an arbitrarily large question straight into both the database and the LLM prompt, which is both a storage-bloat and a cost-control concern. 8000 characters is far beyond anything reasonable to type by hand, while still bounding worst-case payload size per request. 

@router.post("/chat")
async def post_chat(body: SendMessageIn, request: Request, user: dict = Depends(require_session)) -> StreamingResponse:
    conn = request.state.conn

    create_message(conn, body.chat_id, "user", body.question)
    ...
  • Three guard checks, in order: does this chat even exist; does the repo it belongs to actually belong to this logged-in user (returning the exact same 404 either way — "doesn't exist" and "exists but isn't yours" are indistinguishable on purpose, so a caller can't use the response to probe whether some other user's chat id happens to exist); and is that repo actually "ready" yet (a repo still "indexing" has no chunks worth searching).
  • The user's own question is persisted to messages immediately, before any retrieval or generation happens — so even if the LLM call fails downstream, the question itself is never lost.
  • First message in a chat also triggers derive_chat_title(question) — a plain, truncated version of the question becomes the chat's title, exactly like how ChatGPT/Claude auto-name new conversations from your first message.

The tricky part: releasing the database connection mid-stream

Concept — a database connection is a scarce, shared resource The connection pool this whole app shares has a hard cap — max_size=10 — because a real Postgres server (especially a cross-region one like Supabase) can only sensibly serve so many concurrent connections at once. An LLM's answer can take many seconds to fully stream. If this route held onto its one borrowed connection for the entire duration of that stream just because it briefly touched the database at the very start (to embed the question and run the vector search), a handful of concurrent chats could exhaust the whole pool and starve every other request in the app — including something as unrelated as another browser tab's periodic "list my repos" poll. 
retrieval_conn = await asyncio.to_thread(pool.getconn)
retrieval_conn_released = False

def on_sources(results):
    nonlocal retrieval_conn_released
    collected_sources.extend([...])
    pending_frames.append(_sse_frame("sources", json.dumps(collected_sources)))
    pool.putconn(retrieval_conn)
    retrieval_conn_released = True

try:
    async for token in stream_answer(body.question, chat["repo_id"], retrieval_conn, config, on_sources=on_sources):
        ...
        yield _sse_frame(None, token)

    write_conn = await asyncio.to_thread(pool.getconn)   # borrow a FRESH connection just to persist the final answer
    try:
        create_message(write_conn, body.chat_id, "assistant", "".join(answer_parts), sources=collected_sources)
    finally:
        await asyncio.to_thread(pool.putconn, write_conn)
finally:
    if not retrieval_conn_released:
        await asyncio.to_thread(pool.putconn, retrieval_conn)
  • A connection is borrowed once, up front, purely for the retrieval half (the repo-status check plus the vector search inside stream_answer, Parts 4-6).
  • on_sources is a callback stream_answer calls exactly once, the instant retrieval finishes and before the generation loop starts producing its first token. Because an async generator function runs everything up to (and including) its first yield in one uninterrupted stretch — including any plain synchronous callback it calls along the way — this callback is guaranteed to have already run by the time the very first answer token comes back. That guarantee is exactly what makes it safe to release the connection right there, inside the callback, rather than needing some separate signal for "retrieval is done now."
  • Releasing the connection the instant retrieval finishes means it goes straight back into the shared pool for someone else to borrow, for the entire multi-second stretch the LLM is actually generating tokens — the part of this request that touches the database is now a tiny fraction of its total wall-clock time.
  • Once the whole answer has streamed, a completely fresh connection is borrowed just long enough to persist the finished message, then immediately returned.
  • The outer finally: if not retrieval_conn_released: ... exists because on_sources only fires on the happy path — if stream_answer raised before ever reaching retrieval (the ready-check race, an embedder throwing), the connection would otherwise never go back to the pool at all. This is the safety net for that case.

Part 4 — Embedding the question

The first real step of retrieval: turning your question into the exact same kind of vector the indexed code chunks already are.

Files: sleuth/retrieve/answer.py, sleuth/ingest/embed.py

embedder = VoyageEmbedder(api_key=config.voyage_api_key)
query_vector = (await embedder.embed_batch([question]))[0]

This is the exact same VoyageEmbedder class covered in full in how-indexing-works.html Part 8 — same model (voyage-code-3), same 1024-dimension output. That's not incidental: two texts can only be meaningfully compared by distance if they were both embedded by the same model into the same vector space — embedding the question with a different model than the one used to embed the stored chunks would produce vectors that simply aren't comparable at all, like trying to measure the distance between a point in inches and a point in kilometers. embed_batch always takes a list of texts and returns a list of vectors in the same order (Part 8 of the indexing doc explains why: it's designed for embedding hundreds of code chunks at once during ingestion) — here it's called with a list of exactly one question, and [0] just unwraps that single-element list back into one plain vector.

Part 5 — Vector search: finding the nearest chunks

The actual database query that turns "a vector" into "the 8 most relevant functions."

Files: sleuth/retrieve/search.py

@dataclass
class SearchResult:
    file_path: str
    symbol_name: str | None
    kind: str
    start_line: int
    end_line: int
    code_text: str
    distance: float
    is_doc: bool = False


def search_chunks(conn, repo_id: str, query_embedding: list[float], top_k: int = 8, prefer_code: bool = True) -> list[SearchResult]:
    order_by = "is_doc, distance" if prefer_code else "distance"
    rows = conn.execute(
        f"""
        SELECT file_path, symbol_name, kind, start_line, end_line, code_text,
               embedding <=> %(query)s::vector AS distance, is_doc
        FROM chunks
        WHERE repo_id = %(repo_id)s
        ORDER BY {order_by}
        LIMIT %(top_k)s
        """,
        {"query": query_embedding, "repo_id": repo_id, "top_k": top_k},
    ).fetchall()
    return [SearchResult(*row) for row in rows]
  • embedding <=> %(query)s::vector — <=> is pgvector's cosine distance operator (the extension adds this operator to Postgres itself; it's not a function call, it behaves like + or <). For every chunk row that belongs to this repo, this computes how far its stored embedding vector is from the question's vector, geometrically — a smaller number means "more similar in meaning."
  • ORDER BY distance LIMIT %(top_k)s is, in plain English, "give me the 8 closest matches." Postgres's query planner is what actually decides to route this through the HNSW index built during indexing (how-indexing-works.html Part 9) rather than computing the distance to every single row in the table — that's why this single, simple-looking SQL statement runs in milliseconds even against a repo with thousands of chunks.
  • WHERE repo_id = %(repo_id)s is what keeps one user's question from ever searching across a different repo's chunks — every search is always scoped to exactly the one repo the active chat belongs to.
  • %(query)s/%(repo_id)s/%(top_k)s — named parameter placeholders, the same parameterized-SQL pattern used everywhere in this codebase (see how-indexing-works.html Part 1's note on %s) — psycopg sends these values separately from the query text itself, which is the standard defense against SQL injection.

prefer_code: a real production bug, fixed with one ORDER BY clause

The bug: asking an architecture-flavored question against a repo that has both real source and hand-written architecture write-ups under a docs/ directory (e.g. docs/recruiter-authentication.html — a real, parseable HTML file that gets chunked and embedded exactly like genuine source) returned only the documentation excerpts. The model correctly reported it had no actual source code to cite — because none was ever in its context. Root cause: prose about an architecture question can score a closer cosine match against that question than the real implementation does, and plain ORDER BY distance has no way to tell "real code" and "documentation about the code" apart — it just returns whichever wins on raw distance.

ORDER BY is_doc, distance (the default, prefer_code=True) sorts by is_doc first — false sorts before true in SQL's ordering of booleans, so every real-code chunk (is_doc = false) ranks strictly ahead of every documentation chunk (is_doc = true), and only within each of those two groups does distance break ties. A genuinely doc-only question still gets an answer, because documentation chunks still surface — just only once every code chunk has been exhausted, never crowding out real code from a bounded top-8. This is belt-and-braces with a second fix in the prompt itself (Part 7): each excerpt is explicitly labeled [CODE] or [DOCUMENTATION], and the system prompt tells the LLM to prefer citing code — the ranking fix stops documentation from crowding code out of the top-8 at all; the labeling fix is what stops the model from treating an included doc excerpt as equally authoritative to real code once both are in front of it.

Part 6 — Local vs. global: the routing decision added post-launch

Why "rate my architecture" needs a completely different kind of context than "where is create_repo implemented."

Files: sleuth/retrieve/routing.py, sleuth/store.py::get_repo_summary

Concept — the gap vector search alone can't close Part 5's search_chunks is superb at "where is X implemented" — the nearest-neighbor chunks really are the answer. But there is no single chunk, or even any top-8 set of chunks, that is an answer to "summarize this whole project" — that question needs a bird's-eye view no 8 arbitrary functions can provide. how-indexing-works.html Part 10 covers the fix on the write side: one extra artifact, a whole-repo architecture summary, generated once during indexing and stored in repo_summaries. This part covers the read side: how a question gets classified as needing that summary in the first place. 
_GLOBAL_PATTERNS = [
    r"\barchitecture\b",
    r"\boverall\b",
    r"\bwhole (project|repo|repository|codebase)\b",
    r"\bsummarize (the )?(whole|everything|this repo|this project)\b",
    r"\brate (my|this) (architecture|codebase|project|design)\b",
    ...
]
_GLOBAL_RE = re.compile("|".join(_GLOBAL_PATTERNS), re.IGNORECASE)


def classify_question(question: str) -> str:
    return "global" if _GLOBAL_RE.search(question) else "local"
  • This is a plain regular expression check — deliberately not an LLM call. Classifying every single incoming question with its own separate model round trip would add real latency and cost to every question, just to decide which of two paths to take.
  • The key design insight is that both possible mistakes here are harmless. A false positive (a perfectly normal question happens to match, say, the word "architecture" in passing) just means the summary gets prepended to the prompt too — a little extra context, never wrong information. A false negative (a genuinely broad question doesn't match any pattern) just means it falls back to Part 5's plain top-8 search — today's pre-existing behavior, not a regression. Because neither failure mode is actually harmful, a fast, free, zero-latency heuristic is the right tool here — an LLM call would be solving a problem that doesn't need that much power.
summary = None
if classify_question(question) == "global":
    summary = get_repo_summary(conn, repo_id)
prompt = build_prompt(question, results, summary=summary)

This lives in stream_answer — the one shared function both the CLI and the web API funnel through — so the routing logic exists in exactly one place, not duplicated across two callers. get_repo_summary can return None (a repo indexed before this feature existed simply has no summary row yet — see how-indexing-works.html Part 10's caveat), and build_prompt (Part 7) handles that gracefully: no summary block is added at all, exactly as if this whole feature had never been built for that repo.

Part 7 — Building the prompt

Where the question, the retrieved code, and (sometimes) the whole-repo summary get glued into the single string the LLM actually receives.

Files: sleuth/retrieve/answer.py

SYSTEM_PROMPT = (
    "You are a code assistant. Answer the user's question about the repository "
    "using only the provided excerpts. Excerpts are labeled CODE or DOCUMENTATION: "
    "documentation is prose written by humans ABOUT the code, not the implementation "
    "itself, and may be incomplete, stale, or wrong — always prefer and cite CODE "
    "excerpts when answering questions about how something is actually implemented, "
    "and only fall back to DOCUMENTATION excerpts when no relevant code excerpt is "
    "present. If the excerpts don't contain the answer, say so explicitly rather "
    "than guessing."
)


def build_prompt(question: str, results: list[SearchResult], summary: str | None = None) -> str:
    blocks = []
    for r in results:
        symbol = r.symbol_name or "(module level)"
        label = "DOCUMENTATION" if r.is_doc else "CODE"
        blocks.append(
            f"# [{label}] File: {r.file_path}\n# {r.kind}: {symbol} (lines {r.start_line}-{r.end_line})\n\n{r.code_text}"
        )
    context = "\n\n---\n\n".join(blocks)
    prompt = f"Question: {question}\n\n"
    if summary:
        prompt += (
            "REPO SUMMARY (architecture-level overview, generated from the "
            "repo's file/symbol listing — use this for broad/whole-repo "
            "questions, and still ground specific implementation claims in "
            "the excerpts below):\n\n" + summary + "\n\n---\n\n"
        )
    prompt += f"Relevant excerpts:\n\n{context}"
    return prompt
  • SYSTEM_PROMPT is sent once, separately from the user's actual question, as a special {"role": "system", ...} message (Part 8) — this is how a chat LLM is told its behavior and constraints, distinct from the specific question being asked. Telling it explicitly to say "I don't know" rather than guess is a deliberate anti-hallucination instruction — without it, a model asked something the excerpts genuinely don't cover might confidently invent a plausible-sounding but wrong answer instead of admitting the gap.
  • Every retrieved chunk becomes one clearly delimited block: a comment-style header naming the file, the kind of construct, and its line range, then the chunk's actual source text. Line ranges matter — they're what let the model say "see lines 42-58 of auth.py" in its answer, something a human reading the response can go verify directly.
  • The [CODE]/[DOCUMENTATION] label on every single block is the prompt-level half of the doc-vs-code fix from Part 5 — belt-and-braces with the ranking fix, since even a correctly-ranked-lower doc chunk that still makes it into the top-8 needs to be visibly distinguishable from real code once it's sitting in front of the model.
  • The optional REPO SUMMARY block (Part 6) is inserted before the per-chunk excerpts, with its own explicit instruction about when to use it — broad questions should lean on it, but specific implementation claims should still be grounded in the actual excerpts below it, not just the summary's own (necessarily higher-level, less precise) prose.
  • Blocks are joined with "\n\n---\n\n" — a plain visual separator that has no special meaning to the LLM API itself; it's purely there so the model (and a human reading a captured prompt while debugging) can clearly tell where one excerpt ends and the next begins.

Part 8 — Generation: streaming tokens with a fallback chain

Where the assembled prompt actually goes to a real language model, and what happens if that model is down.

Files: sleuth/llm/generate.py

class Generator(ABC):
    model_name: str
    timeout: float = DEFAULT_TIMEOUT

    async def chat(self, messages: list[dict], stream: bool = True):
        async with httpx.AsyncClient(timeout=self.timeout) as client:
            if stream:
                async for token in self._stream_chat(client, messages):
                    yield token
            else:
                yield await self._chat_once(client, messages)

    @abstractmethod
    def _url(self) -> str: ...


class GroqGenerator(Generator):
    model_name = "openai/gpt-oss-120b"
    def _url(self) -> str: return GROQ_URL


class NimGenerator(Generator):
    model_name = "meta/llama-3.2-90b-vision-instruct"
    timeout = 120
    def _url(self) -> str: return NIM_URL
A real, still-open reliability gap: the original NIM fallback default, meta/llama-3.1-70b-instruct, was retired from NVIDIA's catalog — real calls to it started returning 410 Gone even though the model ID isn't listed at all anymore in GET /v1/models. Checking the current catalog by hand (2026-09-01) turned up several candidates, and every one had a problem: three different models 404'd or 500'd on the generic chat completions endpoint despite being listed, one reasoning/"thinking" model hung for 60-150+ seconds even on a trivial "say OK" prompt, and another answered short prompts fine but hung indefinitely on a real multi-turn agentic question. meta/llama-3.2-90b-vision-instruct is what's configured now — a real, currently-invocable model, unlike the retired default — but its practical reliability as an actual fallback is unverified for this project's agentic tool loop specifically (see docs/how-repl-and-agent-session-works.html). In practice, Groq is the sole generator agentic mode actually exercises today.
  • Generator is an Abstract Base Class — the same pattern as Embedder in how-indexing-works.html Part 8: shared logic (chat, the streaming/non-streaming branching) lives once on the base class, and each concrete subclass only supplies what's genuinely different — its model name and its API URL. Groq and NIM speak a nearly identical OpenAI-style chat completions API, so almost nothing needs to be reimplemented per provider.
  • stream=True (used for real user-facing chat) delegates to _stream_chat — an async generator that reads Server-Sent Events off the LLM provider's own streaming response and yields just the text token from each event, exactly the same generator pattern _sse_frame's output gets read back with on the frontend (Part 10). stream=False (used by the eval harness, and for the whole-repo summarization step in how-indexing-works.html Part 10, where nobody is watching tokens arrive live) waits for the complete response and yields it once.

The fallback chain

def get_fallback_chain(config: Config) -> list[Generator]:
    chain = [get_generator(config)]
    if config.generation_provider == "groq" and config.nim_api_key:
        chain.append(NimGenerator(api_key=config.nim_api_key))
    return chain


async def chat_with_fallback(chain: list[Generator], messages: list[dict], stream: bool = True):
    last_error = None
    for generator in chain:
        try:
            async for token in generator.chat(messages, stream=stream):
                yield token
            return
        except (httpx.HTTPStatusError, httpx.TransportError) as exc:
            last_error = exc
            continue
    raise RuntimeError(f"All generators in fallback chain failed: {last_error}")
Concept — why have a fallback provider at all? Any single external API can have an outage, a rate limit, or a transient network blip — and generation is the one part of this whole pipeline with no local fallback (unlike, say, a retried HTTP call for a single request). If Groq is the default provider and it's briefly unavailable, SLEUTH doesn't have to fail the whole question — if a NIM API key is configured, it tries that provider next, automatically, with no user action needed.
  • The chain is just an ordered list: Groq first (if that's the configured default), NIM appended only if an NIM key is actually set — no key, no fallback attempt, since there'd be nothing to call.
  • The loop tries each generator in order; the moment one succeeds (its async for loop finishes without raising), the function returns immediately, never touching the rest of the chain.
  • Only httpx.HTTPStatusError/httpx.TransportError — actual HTTP/network-level failures — trigger a fallback attempt; anything else (a bug, an unexpected response shape) propagates immediately rather than being silently swallowed and retried against a different provider that would likely just fail the exact same way.
A known, documented gap: if the first provider fails partway through streaming — after it has already yielded several real tokens to the caller — the fallback to the next provider starts completely over from the beginning of the answer. A caller that's already displayed those partial tokens (exactly what the chat UI does, appending each token as it arrives) would end up showing the first provider's partial answer immediately followed by the second provider's full answer, visibly duplicated on screen. This is flagged rather than silently accepted: the actual fix would need the caller to track and discard already-yielded tokens on a fallback, which isn't built yet.

Part 9 — Persisting the conversation

Making sure the question and the finished answer both survive after the browser tab closes.

Files: sleuth/store.py, schema.sql

CREATE TABLE IF NOT EXISTS messages (
    id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    chat_id    uuid NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    role       text NOT NULL CHECK (role IN ('user', 'assistant')),
    content    text NOT NULL,
    sources    jsonb,
    created_at timestamptz NOT NULL DEFAULT now()
);
  • Two rows get written per exchange: the user's question (persisted immediately in Part 3, before retrieval even starts) and, once the full answer has finished streaming, the assistant's message — with a sources column recording exactly which chunks were retrieved for it, as JSON.
  • sources jsonb is what lets the chat UI show "this answer cited these 8 files/lines" even after a page reload, days later — without sources, re-opening an old conversation would only show the text of past answers, with no way to see what evidence they were actually grounded in.
  • CHECK (role IN ('user', 'assistant')) is a database-level constraint — Postgres itself refuses any row with a different value in that column, an extra layer of correctness that doesn't depend on every single application code path remembering to validate it first.

Part 10 — Back on the frontend: reassembling the stream

Closing the loop: how the raw SSE bytes from Part 2 turn back into the live, token-by-token chat UI.

Files: web/src/api.js::streamChat

const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  let frameEnd;
  while ((frameEnd = buffer.indexOf('\n\n')) !== -1) {
    const frame = buffer.slice(0, frameEnd);
    buffer = buffer.slice(frameEnd + 2);
    const lines = frame.split('\n');
    const eventLine = lines.find((l) => l.startsWith('event: '));
    const eventType = eventLine ? eventLine.slice('event: '.length) : 'message';
    const data = lines
      .filter((l) => l.startsWith('data: '))
      .map((l) => l.slice('data: '.length))
      .join('\n');

    if (eventType === 'sources') { onSources(JSON.parse(data)); }
    else if (eventType === 'title') { onTitle?.(JSON.parse(data).title); }
    else if (eventType === 'done') onDone();
    else onToken(data);
  }
}
  • res.body.getReader() is the browser's native streaming Fetch API — it hands back chunks of bytes as they arrive over the network, rather than waiting for the entire response body to finish downloading before any of it is accessible to JavaScript at all. Without this API, streaming server-side would be pointless — the browser would just buffer the whole thing anyway before handing it over.
  • buffer exists because network chunks don't respect message boundaries — a single chunk of bytes from reader.read() might contain half of one SSE frame and half of the next, or several complete frames at once. Everything gets appended to one running buffer, and the code repeatedly looks for the next "\n\n" (the blank-line frame terminator from Part 2's _sse_frame) — extracting and processing one complete frame at a time, and leaving whatever's left (a partial frame, if the chunk boundary landed mid-frame) in the buffer for the next read to complete.
  • The multi-line data: rejoin (.filter(...).map(...).join('\n')) is the exact frontend half of the newline-in-a-token fix from Part 2 — reversing _sse_frame's split to recover the token's original text, embedded newline intact.
  • Dispatching by eventType is what lets one single HTTP stream carry several different kinds of update — plain tokens append to the visible answer text live (onToken), a sources event populates the citation cards shown under the finished answer, a title event live-updates the sidebar the moment the backend renames a fresh chat, and done is what finally moves the accumulated streamed text out of "still streaming" state and into the permanent message list.

Part 11 — The other mode: agentic/live chat now also an interactive session

Briefly — this mode skips almost everything above entirely. Full treatment lives in its own companion, docs/how-repl-and-agent-session-works.html.

Files: sleuth/retrieve/agent_session.py, sleuth/retrieve/agentic.py, sleuth/repl.py

sleuth agentic <path> <question> (one-shot) and bare sleuth with no subcommand (a persistent multi-turn REPL) both answer questions about a local directory, with zero upfront indexing wait — no cloning, no chunking, no embeddings, no Postgres involvement at all. Instead of Part 4-5's "embed the question, vector-search pre-computed chunks," the LLM itself is given three tools — grep, list_files, read_file — and runs in a loop: it can request a tool call (a small structured text protocol, TOOL: <name> {json}), get the tool's real output fed back to it, and decide whether it now has enough to answer or needs to look at something else, capped at 6 iterations per question. This is the same fundamental RAG idea (find relevant evidence, then answer from it) but with the LLM doing its own retrieval decisions turn by turn, like a human exploring an unfamiliar repo, rather than one fixed vector-search step. Trade-off: nothing to wait for up front, but no incremental re-indexing benefit and a hard iteration cap on how much it can look at per question.

This tool loop was extracted into a reusable AgentSession class specifically so it could back three different callers without three different implementations: the one-shot CLI command, the interactive REPL (where a session's messages persist across many questions in one run, so a later question can build on an earlier tool call's findings), and — covered in Part 10 of how-indexing-works.html — the repo-summarization step that now runs during ingestion itself. The full mechanics (why ripgrep/sed instead of hand-rolled Python, the path-traversal sandboxing guard, the message-trimming policy for a long-running session, the full-screen terminal UI built on prompt_toolkit) are covered end to end, import by import, in docs/how-repl-and-agent-session-works.html — read that if you're extending or debugging this mode specifically.

Closing — the whole journey, one diagram

Browser: type a question, press Enter │ ▼ (Part 1) Composer/ChatScreen — question pushed into local UI state instantly, no network wait │ ▼ (Part 1/2) streamChat() — POST /chat, body = {chat_id, question}, response read as a byte stream │ ▼ (Part 3) POST /chat route — 404/409 guard checks, user's question persisted to `messages` immediately │ ONE connection borrowed just for retrieval, released the instant it's done (Part 3 detail) │ ▼ (Part 4) VoyageEmbedder.embed_batch([question]) — same model/vector-space as indexed chunks │ ▼ (Part 5) search_chunks() — cosine distance ORDER BY (is_doc, distance) LIMIT 8, HNSW does the work │ ▼ (Part 6) classify_question() — "local" (top-8 only) or "global" (also fetch the stored repo summary) │ ▼ (Part 7) build_prompt() — question + [optional REPO SUMMARY] + labeled [CODE]/[DOCUMENTATION] excerpts │ ▼ (Part 8) chat_with_fallback() — Groq streams tokens; NIM is tried automatically if Groq fails │ each token: yield _sse_frame(None, token) ── sent over the wire AS IT'S GENERATED │ ▼ (Part 9) once the full answer is done: a FRESH connection persists the assistant message + sources │ ▼ (Part 10) browser's streamChat() reassembles frames byte-by-byte, dispatches onToken/onSources/onDone │ ▼ ChatScreen appends each token to the visible bubble live, then finalizes it into the permanent message list once the `done` event arrives

That's the entire request lifecycle. Notice how little of it is actually "AI magic" — most of the real engineering is in the plumbing around the two genuinely intelligent steps (embedding and generation): connection lifetime management, a wire protocol for streaming partial results, a fallback chain for when a provider goes down, and a cheap heuristic for routing between two different kinds of question. That's a deliberate reflection of this project's whole philosophy: no vendor RAG SDK doing any of this invisibly — every one of these steps is a plain function you've now seen in full.
