Part 0 — The big picture

What problem does "indexing" actually solve, and why can't SLEUTH just answer questions directly from a raw GitHub URL?

Concept — why does anything need to be "indexed" at all? An LLM like Groq's model has never seen your repository. It knows general programming knowledge from its training data, but it has zero specific knowledge of your auth.py or your retry logic. If you just paste a question into a chat box, the model can only guess or hallucinate. The fix is to hand the model the actual relevant source code as part of the prompt, every single time you ask a question — but a real repository can be tens of thousands of lines, far too much to paste in wholesale (prompts have hard size limits, and even where they don't, the model gets worse at ignoring irrelevant text as the prompt grows). So the problem is really a search problem: given a question, find the handful of functions/classes that are actually relevant, and only send those. Indexing is the up-front, one-time (well — re-runnable) work of preparing a repo so that search is fast at question-time: break it into small labeled pieces, and pre-compute something you can search over instantly.

Concretely, indexing means: clone the repo, cut it into function/class-sized pieces ("chunks"), convert each chunk's text into a list of numbers ("an embedding vector") that captures its meaning geometrically, and store all of that in Postgres. Once that's done once, answering a question is cheap: embed the question the same way, and ask Postgres "which stored vectors are closest to this one?" — that query runs in milliseconds even against thousands of chunks, because of an index structure explained in Part 9. This document is entirely about the "prepare a repo" half; the question-answering half has its own companion document, docs/how-chat-works.html.

The five states a repo passes through

Every repo row in the repos table has a status column, and the whole indexing story is really the story of that one column changing value over time. Here's every value it can hold, in the order a healthy repo passes through them:

pending → indexing → ready

...or, if something goes wrong at any point along the way:

pending → indexing → failed

This document walks through exactly what code runs during that middle "indexing" phase — every function call, in the order it actually executes, with the real source underneath each step.

Part 1 — The click: POST /repos

What happens the instant you paste a URL into the Repos screen and hit Add.

Files: web/src/components/AddRepoForm.jsx, sleuth/api/routes/repos.py, sleuth/api/schemas.py

On the frontend, AddRepoForm.jsx is a plain HTML form with one text input. Submitting it calls addRepo(trimmed) (web/src/api.js), which is just fetch(BASE_URL + "/repos", { method: "POST", body: JSON.stringify({ github_url }) }) — a standard HTTP POST with a JSON body, using the browser's credentials: "include" option so the signed session cookie rides along and the backend knows which user is adding this repo.

Validating the URL before anything expensive happens

Concept — fail fast, fail cheap A malformed URL (a typo, a non-GitHub host, an empty string) is the cheapest possible failure to catch — it costs nothing to notice immediately. If SLEUTH let it through, the failure would instead surface minutes later as a cryptic git clone error, deep inside a background task the user isn't even watching. Catching it at the API boundary, before a database row is even created, means the user gets an instant, clear 400 response instead of a repo that silently sits at failed with a confusing message. 
class AddRepoIn(BaseModel):
    github_url: str

    @field_validator("github_url")
    @classmethod
    def _must_be_a_github_https_url(cls, value: str) -> str:
        parsed = urlparse(value)
        if parsed.scheme != "https" or parsed.netloc.lower() != "github.com" or not parsed.path.strip("/"):
            raise ValueError("github_url must be an https://github.com/<owner>/<repo> URL")
        return value

This is a Pydantic model — FastAPI's way of describing "the shape of a request body." Before your route function ever runs, FastAPI parses the incoming JSON against this class; if github_url is missing, isn't a string, or (thanks to the @field_validator) isn't a well-formed https://github.com/... URL, the request is rejected with a 422 automatically — your route's body never even executes for a bad request.

The route itself

@router.post("/repos", response_model=RepoOut)
def add_repo(
    body: AddRepoIn, request: Request, background_tasks: BackgroundTasks,
    user: dict = Depends(require_session),
) -> RepoOut:
    conn = request.state.conn
    config = request.state.config
    repo_id = create_repo(conn, body.github_url, user_id=user["id"])
    conn.commit()
    background_tasks.add_task(_run_ingest, repo_id, body.github_url, request.app.state.pool, config)
    return RepoOut(**get_repo(conn, repo_id, user_id=user["id"]))
  • Depends(require_session) is FastAPI's dependency injection — before this function body runs, require_session reads the signed cookie, decodes which user it belongs to, and loads that user's row. If there's no valid session, FastAPI returns 401 and this function's body never runs at all. Every route in this router (APIRouter(dependencies= [Depends(require_session)])) gets this check for free.
  • create_repo(conn, body.github_url, user_id=user["id"]) is one plain INSERT ... RETURNING id (in sleuth/store.py). Its status column defaults to 'pending' at the database level — nobody has to explicitly set that. user_id is what makes this repo belong to the logged-in user: every later lookup of this repo (list, get, chat against it) is scoped by user_id, so one user can never see or touch another user's repos just by guessing an id.
  • conn.commit() — this row must actually land in Postgres before the background task starts, because that task borrows a completely different connection out of the pool and needs to see this row.
  • background_tasks.add_task(_run_ingest, ...) is the single most important line in this function, covered fully in Part 2: it schedules the actual heavy lifting to run after this HTTP response is sent back to the browser, not before.
  • The function returns immediately — RepoOut(**get_repo(...)) — with the repo's current state, which at this instant is just status: "pending". The browser gets this response in milliseconds, long before any cloning or embedding has happened.

Part 2 — Background tasks: why the API responds instantly

The mechanism that lets "add a repo" feel instant even though indexing a real repo can take minutes.

Files: sleuth/api/routes/repos.py

Concept — request/response vs. fire-and-continue An HTTP request is supposed to get a response back promptly — a user staring at a spinner for two minutes while a repo clones, gets parsed, and gets embedded chunk-by-chunk would be a terrible experience, and many HTTP clients/load balancers will simply time out a request that takes that long anyway. FastAPI's BackgroundTasks solves this by letting a route return its response immediately, and only then — after the response bytes are already on their way to the browser — run a function you queued up. The browser gets an instant "yes, I created your repo, here's its id, status is pending" and can immediately start polling a separate progress endpoint (Part 11) to watch it work. 
async def _run_ingest(repo_id: str, github_url: str, pool, config) -> None:
    conn = await asyncio.to_thread(pool.getconn)
    try:
        progress_store.start(repo_id)
        try:
            await ingest_repo(
                github_url, conn, config, repo_id=repo_id,
                on_event=lambda step, detail: progress_store.record(repo_id, step, **detail),
            )
        except Exception as exc:
            update_repo_status(conn, repo_id, "failed", str(exc))
            progress_store.record(repo_id, "failed", error=str(exc))
    finally:
        await asyncio.to_thread(pool.putconn, conn)
  • This function borrows its own connection from the shared pool (pool.getconn) — it cannot reuse the connection the original request used, because by the time this runs, that request is long finished and its connection has already gone back to the pool for some other request to borrow.
  • asyncio.to_thread(pool.getconn) — getconn/putconn are plain blocking calls (they're not async def themselves), so running them directly inside this async def function would freeze the entire event loop for that moment. Wrapping them in to_thread hands them off to a background OS thread so the event loop stays free to serve other requests while this borrow/return happens.
  • progress_store.start(repo_id) initializes an in-memory progress record — explained fully in Part 11 — that the frontend's polling loop reads from.
  • The call to ingest_repo is wrapped in its own try/except as a second, narrower safety net. ingest_repo itself already promises to never raise (Part 12 covers exactly how) — but this outer catch exists in case something goes wrong outside that promise, such as progress_store itself misbehaving. BackgroundTasks has no supervisor of its own: an uncaught exception here would be silently swallowed by FastAPI's internals, leaving the repo stuck at "indexing" forever with absolutely no explanation visible anywhere in the UI. This except block is what guarantees that never happens.
  • on_event=lambda step, detail: progress_store.record(...) — this is how ingest_repo, a function that otherwise has no idea a web frontend even exists, reports its progress back out. It's handed a plain callback function; every time it reaches a new stage internally, it calls this callback with a short string name and whatever details it has. This is the same pattern used for the CLI, which passes no callback at all (Part 11 explains why that's safe).
Retry uses the exact same background-task mechanism. POST /repos/{id}/retry (Part 12) calls the identical _run_ingest function, just with the existing repo_id instead of a freshly created one — which is the whole fix for a real bug this project shipped and later caught: retrying a failed index used to just call POST /repos again with the same URL, and because create_repo has no uniqueness constraint on github_url, every retry silently created a brand-new duplicate row. A dedicated retry endpoint that always operates on the one existing repo_id makes that bug structurally impossible now.

Part 3 — Cloning the repo

Getting the repo's actual files onto disk, where tree-sitter can read them.

Files: sleuth/ingest/clone.py, sleuth/ingest/pipeline.py

Concept — why clone at all, why not read files over the GitHub API? GitHub's REST API can fetch individual file contents, but fetching an entire repo file-by-file over HTTP would mean one API call per file (rate-limited, slow, and GitHub's API has its own request quotas). A git clone gets every file in one operation, using git's own efficient transfer protocol, and leaves you with a completely normal local directory that every other tool in this pipeline (tree-sitter, plain file I/O) already knows how to read. 
def clone_repo(url: str, dest_dir: str, retries: int = 2, backoff_seconds: float = 2.0) -> Path:
    dest = Path(dest_dir)
    attempt = 0
    while True:
        result = subprocess.run(
            ["git", "clone", "--depth", "1", url, str(dest)],
            capture_output=True, text=True,
        )
        if result.returncode == 0:
            return dest

        stderr = result.stderr.strip()
        is_transient = any(pattern in stderr.lower() for pattern in TRANSIENT_CLONE_ERROR_PATTERNS)
        if is_transient and attempt < retries:
            if dest.exists():
                shutil.rmtree(dest, ignore_errors=True)
            time.sleep(backoff_seconds)
            attempt += 1
            continue

        raise CloneError(stderr)
  • --depth 1 is a shallow clone — it fetches only the latest commit's snapshot of every file, not the entire commit history. SLEUTH only ever needs to read the current state of the code, never git log or diff against an old commit, so downloading the full history (which can be enormous for old, active repos) would be pure waste.
  • subprocess.run(["git", "clone", ...]) literally shells out to the real git binary installed on the machine — this project deliberately doesn't use a Python git library, since the actual git CLI is the one thing guaranteed to handle every protocol/auth edge case correctly.
  • capture_output=True, text=True captures stdout/stderr as decoded strings instead of letting them print to the terminal — result.returncode and result.stderr are then inspected in code instead of a human reading console output.
  • The retry loop exists because of a real, confirmed-live bug: git-for-windows can fail a clone with "getaddrinfo() thread failed to start" — a WinSock thread-pool exhaustion glitch — that succeeds immediately if you just try again. TRANSIENT_CLONE_ERROR_PATTERNS is a list of substrings ("getaddrinfo", "connection reset", etc.) that identify this class of "try again, it'll probably work" failure, as opposed to "this repo genuinely doesn't exist or you don't have access," which should fail immediately and clearly instead of being retried.
  • On a genuine (non-transient) failure, this raises CloneError(stderr) — carrying git's own human-readable error text straight through, so a real error like "fatal: could not read Username for 'https://github.com'" (a private repo with no credentials) ends up verbatim in the repo's error_message column for the user to see.

Back in the pipeline, this is called from inside a try/except that's the very first "never raise" exit point:

try:
    repo_path = clone_repo(github_url, workdir)
except CloneError as exc:
    update_repo_status(conn, repo_id, "failed", str(exc))
    conn.commit()
    emit("failed", error=str(exc))
    return repo_id

If cloning fails, indexing stops right here — there's no code to parse yet, so nothing downstream can run anyway. The repo goes straight to status = "failed" with git's real error message attached, and the function returns cleanly instead of letting the exception propagate.

Part 4 — Walking the file tree

Deciding which of the repo's files are even worth looking at.

Files: sleuth/ingest/clone.py::list_source_files, sleuth/ingest/parse.py

def list_source_files(repo_path: Path, extensions: set[str]) -> list[Path]:
    files = []
    for path in Path(repo_path).rglob("*"):
        if ".git" in path.parts:
            continue
        if path.is_file() and path.suffix in extensions:
            files.append(path)
    return files
  • Path(repo_path).rglob("*") — recursive glob: walks every file and directory under repo_path, at every depth, matching everything (*).
  • if ".git" in path.parts: continue — every clone has a .git/ folder full of git's own internal bookkeeping (object database, refs, etc.). None of that is source code, so it's explicitly skipped rather than accidentally chunked as if it were.
  • path.suffix in extensions — only files whose extension is in the supported set get kept. That set (SUPPORTED_EXTENSIONS in pipeline.py) is built directly from the language registry in sleuth/ingest/parse.py: .py, .js, .ts, .jsx, .tsx, .vue, .html, .css — every language SLEUTH has a tree-sitter grammar for (Parts 5-6, and pipeline-deep-dive.html Part 18 for the multi-language chunkers specifically). Anything else — images, lockfiles, markdown, compiled binaries — is silently never looked at.
Why this list is built from the registry, not hardcoded here: if a new language chunker gets added later, this function needs zero changes — it automatically starts including that extension the moment a LanguageSpec for it exists in the registry. One source of truth for "what languages does SLEUTH understand," read from everywhere else that needs the answer.

Part 5 — Parsing: turning text into a tree

The first real structural step: making the computer understand code as syntax, not just text.

Files: sleuth/ingest/parse.py

Concept — why not just split files by blank lines, or every N characters? The naive approach to "chunking" a document is splitting it into fixed-size windows — every 500 characters, say. That's fine for prose, but it's actively bad for code: a fixed window can slice a function in half, separate a function's signature from its body, or bundle three unrelated functions into one chunk purely because they happened to land in the same character range. What you actually want are chunks aligned to meaningful boundaries — "this is one whole function," "this is one whole class" — and the only way to know where those boundaries are is to actually understand the code's grammar. tree-sitter is a parser generator that, for dozens of languages, turns a file's raw text into a syntax tree: a nested structure where every node is labeled with what kind of language construct it is (function_definition, class_definition, if_statement, and so on), and every node knows exactly which byte range of the original text it spans.

Concretely: parse_source(source_bytes, language_key) hands raw bytes to the tree-sitter parser for that language and gets back a tree object whose .root_node is the top of the whole file's syntax tree. Every node under it — nested arbitrarily deep — represents one syntactic construct, and crucially, every node exposes .start_byte/.end_byte, so once SLEUTH decides "this node is a chunk," it can slice the exact original text back out with source_bytes[node.start_byte:node.end_byte] — no re-formatting, no risk of subtly rewriting the user's code.

Why bytes, not strings: tree-sitter's node byte offsets are counted in raw bytes, not Python Unicode characters — a multi-byte UTF-8 character (an emoji in a comment, say) would make string-index-based slicing land in the wrong place. Reading the file as bytes and slicing with byte offsets keeps everything consistent with what tree-sitter itself is counting.

Part 6 — Chunking: turning a tree into Chunk objects

Walking the syntax tree and deciding "this is one unit of retrievable code."

Files: sleuth/ingest/chunk.py, sleuth/chunking.py

@dataclass
class Chunk:
    file_path: str
    symbol_name: str | None
    kind: str  # 'function' | 'method' | 'class' | 'module'
    start_line: int
    end_line: int
    code_text: str

    @property
    def content_hash(self) -> str:
        return hashlib.sha256(self.code_text.encode("utf-8")).hexdigest()

    @property
    def is_doc(self) -> bool:
        return is_doc_path(self.file_path)
  • @dataclass generates __init__/__repr__/__eq__ automatically from the field list — every one of the six fields above is set once at construction and never mutated afterward.
  • content_hash is a computed property — it's not stored, it's derived fresh every time you ask for it, from a SHA-256 hash of the chunk's actual text. This one field is the entire mechanism behind incremental re-indexing, covered fully in Part 7.
  • is_doc flags any chunk that lives under a docs/, doc/, or documentation/ directory at any depth — hand-written architecture write-ups get chunked and embedded exactly like real source (a docs/architecture.html file is a perfectly valid, parseable HTML file), but retrieval needs to be able to tell "prose about the code" apart from "the code itself" (see how-chat-works.html Part on ranking).

The actual walking-the-tree logic lives in a tree-sitter query — a small declarative pattern-matching language (not Python) that says "find me every node shaped like a function definition, or a class definition, or a method inside a class." The chunker runs this query against the parsed tree, and for each match it constructs a Chunk: the matched node's start/end lines, the symbol's name (pulled from a child identifier node within the match), a kind label, and the exact source text for that byte range.

A real bug this caught: the original chunker walked node types directly (if node.type == "function_definition") instead of using a query. That missed wrapped nodes — export class Foo {} in JS/TS wraps the class inside an export_statement node, and @app.get(...) decorators in Python wrap the function inside a decorated_definition node — so decorated/exported functions were silently dropped, and the line spans for the "everything else" leftover chunk came out wrong. The fix was a query-based chunker that unwraps decorators/exports before classifying a node, while still keeping the outer node's full byte span so the exported/decorated wrapper text isn't lost.

Part 7 — The incremental re-index check

The single idea that makes re-running indexing on a mostly-unchanged repo nearly free.

Files: sleuth/ingest/pipeline.py, sleuth/store.py

Concept — why does this matter so much? Embedding calls cost real money and real time (Part 8) — every chunk sent to Voyage's API is a network round trip and a billable request. If someone re-indexes a repo they already indexed yesterday, and only one function actually changed since then, re-embedding all 2,000 chunks in that repo to update one of them would be enormously wasteful. The fix is to give every chunk a fingerprint of its own content, and only pay the embedding cost for chunks whose fingerprint actually changed. 
current_keys = {(c.file_path, c.symbol_name) for c in all_chunks}
existing_hashes = get_existing_hashes(conn, repo_id)

to_embed = [
    c for c in all_chunks
    if existing_hashes.get((c.file_path, c.symbol_name)) != c.content_hash
]
  • Every chunk is identified by the pair (file_path, symbol_name) — e.g. ("sleuth/auth.py", "login"). This is the chunk's identity: as long as the function stays in the same file with the same name, it's considered "the same chunk," even if its body changes completely.
  • current_keys is every identity that exists in the repo right now, from this fresh clone.
  • existing_hashes is a dict pulled straight from Postgres — for every chunk already stored for this repo_id, what content_hash did it have last time this repo was indexed?
  • The list comprehension keeps only chunks whose current hash doesn't match the previously stored hash for that same identity. .get(...) returns None for a brand-new chunk that has no previous entry at all — and None never equals a real hash string, so new chunks are automatically included too. If a function's body hasn't changed a single character since last time, its hash is bit-for-bit identical, it's excluded from to_embed, and it costs zero embedding calls this run.

The other half of "incremental" is noticing when code has been deleted: 

delete_stale_chunks(conn, repo_id, current_keys)

If a function was removed (or a whole file was deleted) since the last index, its identity simply won't appear in current_keys this time, but a row for it still exists in Postgres from before. delete_stale_chunks (sleuth/store.py) diffs "what's stored" against "what currently exists" and deletes exactly the leftover rows — otherwise a deleted function would keep haunting every future search result forever, as a chunk that no longer corresponds to any real code.

Part 8 — Embedding: turning code into vectors

The step that actually makes "search by meaning" possible.

Files: sleuth/ingest/embed.py, sleuth/http_retry.py, sleuth/chunking.py::format_chunk_context

Concept — what is an embedding, actually? An embedding model is a neural network trained specifically to turn text into a fixed-length list of numbers — a vector — such that texts with similar meaning end up as vectors that are geometrically close together in that (very high-dimensional) space. This project uses Voyage AI's voyage-code-3 model, which was specifically trained on code, and it always produces a vector of exactly 1024 numbers, no matter how long or short the input text is. "Geometrically close" here means cosine distance — literally the angle between two vectors — which is exactly the metric SLEUTH's search query uses later (Part 9, and how-chat-works.html). The entire premise of RAG rests on this one idea: if two pieces of text mean similar things, their embedding vectors will land near each other, so "find code relevant to this question" becomes "find the nearest vectors to this question's vector" — a purely geometric operation a database can do extremely fast.

Formatting a chunk before embedding it

def format_chunk_context(chunk: Chunk, language: str) -> str:
    symbol = chunk.symbol_name or "(module level)"
    header = (
        f"# File: {chunk.file_path}\n"
        f"# {chunk.kind}: {symbol}\n"
        f"# Language: {language}\n\n"
    )
    return header + chunk.code_text

The embedding model never sees just the bare function body — it sees a small header naming the file, the kind of construct, and the language, prepended in front of the real code. A function called process could mean radically different things in payments/process.py versus images/process.py; giving the embedding model that context lets it produce a vector that actually reflects the surrounding meaning, not just the isolated code text in a vacuum.

Sending it to Voyage, with pacing and concurrency limits

async def embed_batch(self, texts: list[str], on_batch_done=None) -> list[list[float]]:
    batches = [texts[i : i + self.batch_size] for i in range(0, len(texts), self.batch_size)]
    semaphore = asyncio.Semaphore(self.max_concurrency)
    ...
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(*(run_one(client, batch) for batch in batches))
  • texts (potentially hundreds of chunks) is sliced into batch_size-sized groups — Voyage's API accepts many texts per HTTP call, so batching turns e.g. 500 individual network round trips into a handful.
  • asyncio.Semaphore(max_concurrency) caps how many batches are "in flight" to Voyage at once — a counter that lets at most max_concurrency coroutines proceed simultaneously, everyone else waits their turn. This is what prevents SLEUTH from firing every batch at Voyage all at once and getting instantly rate-limited.
  • asyncio.gather(*(...)) runs every batch's coroutine concurrently (not one after another) and waits for all of them to finish, returning results in the same order they were given — the actual mechanism that makes "many slow network calls" take roughly as long as the slowest one, instead of the sum of all of them.
  • on_batch_done(completed, total) fires after every batch finishes — this is exactly what powers the Indexing screen's live "Embedded: 340/612" counter (Part 11).
The free tier's real, confirmed limit: a Voyage API key with no billing method attached is hard-capped at 3 requests/minute and 10K tokens/minute (confirmed directly against the live API — it comes back in an x-api-warning response header). FREE_TIER_BATCH_SIZE = 10, FREE_TIER_MAX_CONCURRENCY = 1, and FREE_TIER_REQUESTS_PER_MINUTE = 3 are tuned specifically to stay under that cap: small batches keep any single request's token count well under 10K, and a request pacer (a separate mechanism from the semaphore — it spaces out when requests start, not just how many run at once) guarantees consecutive requests are never closer than 20 seconds apart, regardless of how fast responses actually come back. Retrying a 429 alone can't fix a request pattern that's structurally over the limit — the pacer is what actually keeps you under it in the first place.

Retrying transient failures

Every HTTP call to Voyage/Groq/NIM goes through one shared helper, post_with_retry (sleuth/http_retry.py): on a 429 or 5xx or network-level error, it waits briefly and retries once, then gives up and lets the real exception propagate. One centralized retry policy means every provider gets the same resilience without each embedder/generator re-implementing its own backoff logic — and it means there's exactly one place to look if retry behavior is ever wrong.

Part 9 — Writing to Postgres: upsert and stale-chunk cleanup

Getting the (chunk, vector) pairs durably stored, ready for millisecond search later.

Files: sleuth/store.py, schema.sql

INSERT INTO chunks
    (repo_id, file_path, symbol_name, kind, start_line, end_line, code_text, content_hash, embedding, is_doc)
VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s)
ON CONFLICT (repo_id, file_path, COALESCE(symbol_name, ''))
DO UPDATE SET
    kind = EXCLUDED.kind, start_line = EXCLUDED.start_line, end_line = EXCLUDED.end_line,
    code_text = EXCLUDED.code_text, content_hash = EXCLUDED.content_hash,
    embedding = EXCLUDED.embedding, is_doc = EXCLUDED.is_doc
Concept — what "upsert" means, and why ON CONFLICT matters here An upsert ("update or insert") is a single SQL statement that inserts a new row, unless a row already exists that would collide with a uniqueness rule — in which case it updates that existing row instead. Without this, re-indexing a changed function would either need a manual "does this already exist? if so update, else insert" round trip (two queries, and a race condition if two processes run it at the same moment), or would insert a second row for the same chunk, silently duplicating it forever. The chunks_identity_idx unique index on (repo_id, file_path, COALESCE(symbol_name, '')) is what defines "this is the same chunk as before" at the database level — COALESCE(symbol_name, '') treats a module-level chunk's NULL symbol name as an empty string for uniqueness purposes, since Postgres's uniqueness rules otherwise treat every NULL as distinct from every other NULL.

Why a vector column, and why HNSW

embedding     vector(1024) NOT NULL
...
CREATE INDEX IF NOT EXISTS chunks_embedding_idx
    ON chunks USING hnsw (embedding vector_cosine_ops);

vector(1024) is a column type from the pgvector Postgres extension — it stores a fixed-length array of floats natively, with its own comparison operators (<=> for cosine distance, used constantly in how-chat-works.html). Without an index, finding the nearest vectors to a query would mean computing the distance to every single row and sorting — correct, but linear in the number of chunks, which gets slow once a repo has thousands of them. HNSW ("Hierarchical Navigable Small World") is an approximate-nearest-neighbor index structure — instead of checking every vector, it builds a multi-layer graph where each vector is connected to its rough neighbors, so a search can "hop" toward the closest match in roughly logarithmic time instead of linear time. It trades a small amount of exactness (it might occasionally miss the single mathematically closest chunk) for a dramatic speedup — the right trade for "find roughly the 8 most relevant functions," where being off by one rank almost never matters to a human reading the answer.

Doc-vs-code, a real production bug fixed here: the is_doc column exists because a hand-written architecture write-up under docs/ — a real, parseable .html file — got chunked and embedded exactly like genuine source, and prose about an architecture question can score a closer cosine match than the actual implementation against that same question. Confirmed live: asking an architecture question against a repo with both real source and docs/*.html write-ups returned only doc excerpts, with the model correctly reporting it had no actual code to cite. how-chat-works.html covers exactly how retrieval uses this column to rank real code strictly ahead of documentation.

Part 10 — The new step: summarizing the whole repo added post-launch, since rebuilt

Why per-chunk search alone can't answer "rate my architecture," what was added to fix it, and a real payload-size bug that forced a rebuild of how it works.

Files: sleuth/summarize.py, sleuth/retrieve/agent_session.py, sleuth/ingest/pipeline.py, sleuth/store.py

Concept — the gap this closes Everything in Parts 5-9 produces chunks that are excellent answers to local questions — "where is the retry logic," "what does this function do." But a question like "rate my overall architecture" or "summarize this whole project" has no single chunk that is the answer — the top-8 nearest-neighbor chunks are just 8 arbitrary functions, not a coherent picture of the whole system. This was a real, reported gap in production use, and the fix is to produce one more artifact during indexing that does describe the whole repo: a short, LLM-written architecture summary.
The original approach's real bug: a linearly growing prompt. The first version of this feature (build_repo_map/summarize_repo, no longer in the codebase — see git history if curious) built one giant flat string of every chunk's file: kind symbol and sent it as a single chat completion. That prompt's size scales linearly with repo size — fine for a small repo, but a large enough one blows straight past Groq's request size limit and the whole summarization step fails with a 413 Payload Too Large. The fix wasn't a bigger limit or truncation — it was to stop sending the whole listing upfront at all. 
SUMMARY_QUESTION = (
    "Explore this codebase using your tools (list_files, grep, read_file) and then "
    "write a concise architecture summary: what the project is, its major "
    "components/modules and what each does, and how they likely fit together. "
    "Ground this in what you actually find — don't invent implementation details "
    "you haven't seen. 3-6 short paragraphs, no preamble."
)


async def summarize_repo_agentic(
    path: str, config: Config, generator: Generator | None = None,
    fallback_chain: list[Generator] | None = None,
) -> str | None:
    session = AgentSession(path, config=config, generator=generator, fallback_chain=fallback_chain)
    try:
        async for event in session.ask(SUMMARY_QUESTION):
            if isinstance(event, AnswerEvent):
                if event.text == UNAVAILABLE_MESSAGE:
                    return None
                return event.text
    except Exception:
        return None
    return None
  • This reuses the exact same AgentSession tool loop that backs the interactive REPL and the one-shot sleuth agentic command (its own companion document, docs/how-repl-and-agent-session-works.html, covers this class fully) — instead of one unbounded prompt, the model is handed list_files/grep/read_file tools and decides for itself what's worth looking at (a README, the top-level directory structure, a handful of entry-point files), converging on an answer within AgentSession.MAX_ITERATIONS (6) round trips — a fixed, bounded cost regardless of whether the repo has 50 files or 5,000, because the model is never handed the entire file/symbol listing at once.
  • The trade-off runs the other way from before: the old version's summary was fast and cheap (one call) but strictly metadata-only; this version costs up to 6 model round trips per repo but the resulting summary can be grounded in real file contents the model chose to actually open, not just file/symbol names.
  • event.text == UNAVAILABLE_MESSAGE — AgentSession already turns a fully failed fallback chain into a friendly, user-facing sentence rather than raising (so a live chat question never crashes on a provider outage). That text is exactly right to show a human, but wrong to silently store as if it were a real architecture summary — this check is what keeps the two concerns separate.

Wired into the pipeline, right after chunking finishes — note it now runs against the cloned repo directory on disk, not the in-memory chunk list:

try:
    summary = await summarize_repo_agentic(str(repo_path), config)
    if summary:
        upsert_repo_summary(conn, repo_id, summary)
        conn.commit()
        emit("summarized")
except Exception as exc:
    emit("summary_failed", error=str(exc))
Still deliberately non-fatal, on two levels now. summarize_repo_agentic has its own internal try/except that swallows anything unexpected and returns None instead of raising — belt-and-braces underneath AgentSession's own error handling, not a replacement for it. This outer try/except in the pipeline is a second, narrower safety net for anything that still slips through. Either way, a flaky or rate-limited Groq call here must not block the rest of indexing (embedding, storing chunks, marking the repo ready) from succeeding — summarization is additive, its failure mode is "skip storing a summary and keep going," never "fail the whole repo." repo_summaries is a table, one row per repo (repo_id uuid PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE), overwritten wholesale on every re-index rather than versioned or appended to.
Caveat that matters in practice: a repo that was indexed before this feature existed has no summary row at all until it's re-indexed — asking it an architecture question today simply gets no summary block prepended (the same as if this feature had never been built for that repo), not an error. Same backfill caveat the is_doc column has.

Part 11 — Watching it happen: progress events end to end

How the Indexing screen's live "Clone → Parse → Chunk → Embed → Store" tracker actually gets its data.

Files: sleuth/api/progress_store.py, sleuth/api/routes/repos.py, web/src/components/IndexingScreen.jsx

Concept — how does a browser see progress happening inside a background task it can't touch? The browser has no direct connection to the background task running inside the server process — it can only make new HTTP requests. The pattern used here is polling: the frontend asks "what's the latest status?" over and over on a short timer, and the backend keeps an in-memory record of "the most recent thing that happened for this repo_id" that each poll can read. This is deliberately simpler than something like WebSockets (a truly live, pushed connection) — polling every 1.5 seconds is plenty responsive for something that takes tens of seconds to minutes, and it needs zero new infrastructure: it's the exact same plain HTTP GET the rest of this app already uses everywhere. 
def record(repo_id: str, step: str, **detail) -> None:
    with _lock:
        entry = _progress.setdefault(
            repo_id, {"step": step, "detail": {}, "log": [], "started_at": time.monotonic()}
        )
        entry["step"] = step
        entry["detail"] = detail
        entry["log"].append({"step": step, **detail})
        entry["log"] = entry["log"][-20:]
        _progress.move_to_end(repo_id)
        _evict_oldest_if_over_cap()
  • _progress is a plain in-process Python dict (an OrderedDict, specifically) keyed by repo_id — this lives only in server memory, not in Postgres. It doesn't need to survive a server restart; it only needs to answer "what's happening right now."
  • with _lock: — a plain threading.Lock. Multiple ingest tasks for different repos could be running "concurrently" (interleaved, on the event loop) at once, all writing into this same shared dict; the lock ensures one write finishes cleanly before another starts, so entries never get corrupted by two writes interleaving mid-update.
  • entry["log"] = entry["log"][-20:] caps the kept history at the last 20 events per repo — the Indexing screen only shows a short scrolling log, so nothing is gained by keeping every event forever, and this bounds memory per repo.
  • _evict_oldest_if_over_cap()/_MAX_TRACKED_REPOS = 500 — a simple insertion-order LRU across all repos: once 500 repos have an entry, the oldest one is dropped to make room. Without this, a long-running server ingesting many repos over its lifetime would leak a little memory forever, one entry at a time, never freed.

The frontend side is a plain polling loop, widening/narrowing its interval based on whether anything's actually still in flight:

const interval = setInterval(() => {
  if (repoRef.current && (repoRef.current.status === 'ready' || repoRef.current.status === 'failed')) {
    clearInterval(interval);
    return;
  }
  poll();
}, 1500);

Once a repo reaches a terminal status — ready or failed — there is nothing left to observe, so the interval clears itself rather than polling forever for no reason. A retry (Part 12) bumps a pollGeneration React state value, which the surrounding effect is watching — that re-runs the whole effect and starts a fresh interval, since the previous one already permanently stopped itself when the repo first reached failed.

Why the CLI never needs any of this: the CLI (sleuth add <url>) calls ingest_repo with no on_event callback at all — it just awaits the whole function and prints a final result when it's done, because there's no separate browser process watching; the same terminal that started the command is still attached and will simply show the command as "running" the whole time. on_event defaulting to None (and every internal emit(...) call checking if on_event: before calling it) is what makes this one function serve both the CLI and the web app without needing two separate implementations.

Part 12 — When things go wrong: failure, retry, delete

The three ways a repo's story can deviate from the happy path, and exactly what code handles each.

Files: sleuth/ingest/pipeline.py, sleuth/api/routes/repos.py, sleuth/store.py, web/src/components/RepoList.jsx, IndexingScreen.jsx

Failure: the outer safety net

async def ingest_repo(github_url: str, conn, config: Config, on_event=None, repo_id: str | None = None) -> str:
    def emit(step: str, **detail) -> None:
        if on_event:
            on_event(step, detail)

    if repo_id is None:
        repo_id = _find_or_create_repo(conn, github_url)
    update_repo_status(conn, repo_id, "indexing")
    conn.commit()
    emit("cloning")

    try:
        return await _run_ingest_steps(github_url, conn, config, repo_id, emit)
    except Exception as exc:
        update_repo_status(conn, repo_id, "failed", str(exc))
        conn.commit()
        emit("failed", error=str(exc))
        return repo_id
  • Every real step (clone, parse, chunk, embed, upsert) lives inside _run_ingest_steps, and ingest_repo wraps the entire call in one try/except Exception. This is the literal implementation of the documented contract "ingest_repo never raises" — whatever actually goes wrong (Voyage rejects the API key, Postgres refuses a write, a bug in the chunker), the repo ends up at status = "failed" with that exception's message attached, and the function returns normally instead of an unhandled exception propagating up into whatever called it (a background task with no supervisor of its own, or a CLI command).
  • The clone-specific except CloneError seen in Part 3 is a narrower, earlier catch inside _run_ingest_steps — it exists so a clone failure can be reported with git's exact error text specifically. This outer except Exception is the last-resort net underneath that, catching literally anything else that wasn't specifically anticipated.

Retry: same row, not a new one

@router.post("/repos/{repo_id}/retry", response_model=RepoOut)
def retry_repo(repo_id: str, request: Request, background_tasks: BackgroundTasks, user: dict = Depends(require_session)) -> RepoOut:
    conn = request.state.conn
    config = request.state.config
    repo = get_repo(conn, repo_id, user_id=user["id"])
    if repo is None:
        raise HTTPException(status_code=404, detail="repo not found")
    update_repo_status(conn, repo_id, "pending")
    conn.commit()
    background_tasks.add_task(_run_ingest, repo_id, repo["github_url"], request.app.state.pool, config)
    return RepoOut(**get_repo(conn, repo_id, user_id=user["id"]))

This route takes the existing repo_id from the URL path itself, looks up its github_url from the row already in the database (never trusting a URL the client might send), and re-runs the exact same _run_ingest background task from Part 2 against that same row. Structurally, there is no code path here that creates a second row for the same repo — which is the actual fix for the duplicate-row bug mentioned back in Part 2.

Delete: a hard, cascading removal

def delete_repo(conn: psycopg.Connection, repo_id: str) -> None:
    conn.execute("DELETE FROM repos WHERE id = %s", (repo_id,))

One statement. Every table that references repos.id — chunks, repo_summaries, chats (and messages, which itself cascades off chats) — was declared with REFERENCES repos(id) ON DELETE CASCADE in schema.sql. That's a foreign-key constraint telling Postgres itself "if the parent row goes away, automatically delete every row that points at it, in every table, transitively." So one DELETE FROM repos takes the repo's chunks, its architecture summary, and every conversation ever had about it, all in one atomic operation — no application code has to remember to clean up each table by hand, and there's no window where an orphaned chat could be left pointing at a repo_id that no longer resolves to anything.

Why this is destructive with no undo: the (not-yet-built) Repo Settings screen's own design copy already frames this action as destructive — "its index is deleted and past conversations about it become read-only" — so a hard cascading delete matches the intended semantics rather than adding a soft-delete/undo layer the design never called for. The frontend gates this behind an inline click-to-confirm precisely because it's irreversible.
