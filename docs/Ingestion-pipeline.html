1. The big picture

One function, ingest_repo(github_url, conn, config), does the whole job. It is async (because embedding calls go over the network) and it takes a GitHub URL, a live database connection, and a Config object holding API keys. It returns the repo's database id, and — this is the important design rule — it never raises. Every failure mode ends with the repo's status column set to 'failed' plus an error message, not a Python exception bubbling up. That matters because ingestion will eventually run as a background job; nothing should be sitting there ready to crash a worker process over a bad clone URL.

Flow: find/create repo row → mark "indexing" → clone repo to a temp dir → walk every source file → parse + chunk each one with tree-sitter → hash each chunk's code and compare against what's already stored → embed only the chunks that changed → upsert those into Postgres → delete chunks for code that no longer exists → mark "ready" → delete the temp clone.

The single idea that shapes almost every line in this file is incremental re-indexing: re-running ingestion on a repo that's mostly unchanged should re-embed almost nothing. Embedding calls cost money and time; a content hash per chunk is the cheap check that avoids paying for it twice.

_find_or_create_repo

23def _find_or_create_repo(conn, github_url: str) -> str:
24    row = conn.execute("SELECT id FROM repos WHERE github_url = %s", (github_url,)).fetchone()
25    if row is not None:
26        return str(row[0])
27    repo_id = create_repo(conn, github_url)
28    conn.commit()
29    return repo_id

This is what makes re-indexing the same repo find the same row instead of creating duplicates. It queries repos by github_url first; if a row already exists it returns that row's id (cast to str because Postgres hands back a UUID object, and the rest of the codebase treats repo ids as plain strings). Only if nothing was found does it call create_repo — a one-line INSERT ... RETURNING id in store.py — and commit that insert immediately so the new row is visible to any other query on the same connection right away.

The %s placeholder with a tuple argument, (github_url,), is parameterized SQL — psycopg sends the value separately from the query text, so a URL containing a stray quote character can never be interpreted as SQL. This is the standard defense against SQL injection, and every query in this codebase uses it instead of string-formatting values into the query.

This is the incremental re-index check — the heart of the whole design. Mark ready, return the id, then always clean up the clone. The finally block runs whether the function returned normally on line 85 or exited early on line 46 after a clone failure — shutil.rmtree(..., ignore_errors=True) deletes the temp directory tree without raising even if something about the cleanup itself goes wrong. Nothing about the outcome of ingestion depends on this step succeeding, which is why errors here are deliberately swallowed.

Notice what's absent: there is no top-level try/except around the whole function body. A truly unexpected exception (a bug in chunk_source, a dropped DB connection mid-run) would still propagate out of ingest_repo today. The "never raises" guarantee currently covers the one failure mode that's expected to happen routinely in practice — a bad clone URL — not every conceivable exception. Worth keeping in mind if this is ever wrapped in a background job queue.

4. Deep dive: cloning & file listing

sleuth/ingest/clone.py
9def clone_repo(url: str, dest_dir: str) -> Path:
10    dest = Path(dest_dir)
11    result = subprocess.run(
12        ["git", "clone", "--depth", "1", url, str(dest)],
13        capture_output=True,
14        text=True,
15    )
16    if result.returncode != 0:
17        raise CloneError(result.stderr.strip())
18    return dest

subprocess.run with a list of arguments (not a shell string) is used deliberately — passing ["git", "clone", ..., url, ...] as a list means the OS invokes git directly with each argument as its own value, so there's no shell interpreting the URL string. If url contained something like ; rm -rf ~, it would just be treated as a literal (invalid) URL argument to git, not executed as a shell command. This is the subprocess equivalent of the parameterized-SQL protection used everywhere else in this codebase.

--depth 1 is a shallow clone — only the latest commit's file tree, no history. Ingestion only ever reads the current state of files, so pulling the entire commit history would be pure waste of bandwidth and disk. result.returncode != 0 is how you detect failure from a subprocess.run call (it doesn't raise by default); git's own explanation of what went wrong is on stderr, which gets wrapped into CloneError and is exactly the string that ends up in repos.error_message when this bubbles up through ingest_repo. 

21def list_source_files(repo_path: Path, extensions: set[str]) -> list[Path]:
22    files = []
23    for path in Path(repo_path).rglob("*"):
24        if ".git" in path.parts:
25            continue
26        if path.is_file() and path.suffix in extensions:
27            files.append(path)
28    return files

rglob("*") recursively walks every entry — files and directories — under repo_path. ".git" in path.parts checks whether any path segment is literally named .git (catches the whole .git/ internals folder, not just a file called .git). The final filter keeps only real files (not directories) whose suffix — .py, .js, .ts — is in the caller-supplied extensions set. This function doesn't hardcode which extensions matter; ingest_repo passes in SUPPORTED_EXTENSIONS, keeping the language list defined in exactly one place (parse.py's LANGUAGES registry).

5. Deep dive: parsing & chunking

sleuth/ingest/parse.py · sleuth/ingest/chunk.py

parse_source — turning bytes into a syntax tree

30def parse_source(source_bytes: bytes, extension: str) -> tuple[Tree, LanguageSpec]:
31    spec = LANGUAGES.get(extension)
32    if spec is None:
33        raise UnsupportedFileType(extension)
34
35    parser = Parser(spec.ts_language)
36    tree = parser.parse(source_bytes)
37    return tree, spec

Tree-sitter is a real parser, not a regex hack — it builds a full concrete syntax tree (every paren, every keyword, every block gets a node) for the language matching the file's extension. It parses bytes directly rather than a decoded string, because tree-sitter's own node positions are byte offsets — feeding it a Python str would create an offset mismatch the moment the file contains any non-ASCII character (a byte-string in a docstring, a name with an accent). LANGUAGES is the single lookup table from file extension → compiled tree-sitter grammar (Python/JS/TS), built once at import time from the tree_sitter_python/tree_sitter_javascript/tree_sitter_typescript packages.

chunk_source — the tree becomes a list of Chunks

20def chunk_source(source_bytes: bytes, file_path: str, extension: str) -> list[Chunk]:
21    try:
22        tree, spec = parse_source(source_bytes, extension)
23    except UnsupportedFileType:
24        chunks = _fallback_chunk(source_bytes, file_path)
25    else:
26        query = _load_query(spec.key, spec.ts_language)
27        chunks = run_query(query, tree.root_node, source_bytes, file_path)
28
29    return _cap_chunk_sizes(chunks)

Two ways a file gets chunked: structural for supported languages, via a tree-sitter query — a small pattern-matching language (loaded from a .scm file per language in sleuth/ingest/queries/) that finds function/class/method definitions in the syntax tree and returns each as a Chunk with the right symbol name, kind, and line span. Or fallback, for any extension not in LANGUAGES — blank-line-delimited blocks of text, no symbol awareness. Every chunk, from either path, then goes through _cap_chunk_sizes before being returned.

Design history worth knowing: the query-based approach replaced an earlier per-node-type walker after it was found to silently drop decorated/exported definitions — @app.get(...) in Python, export class Foo {} in TS — because those wrap the real definition node inside a decorated_definition/export_statement wrapper the old walker didn't unwrap. See the Task 5 entry in docs/progress.html for the full story.

_fallback_chunk — for unsupported extensions

32def _fallback_chunk(source_bytes: bytes, file_path: str) -> list[Chunk]:
33    text = source_bytes.decode("utf-8", errors="replace")
34    lines = text.splitlines()
35
36    blocks: list[tuple[int, int, list[str]]] = []
37    current: list[str] = []
38    start = 1
39    for lineno, line in enumerate(lines, start=1):
40        if line.strip() == "":
41            if current:
42                blocks.append((start, lineno - 1, current))
43                current = []
44            continue
45        if not current:
46            start = lineno
47        current.append(line)
48    if current:
49        blocks.append((start, len(lines), current))

Note this path is currently unreachable from ingest_repo in practice — SUPPORTED_EXTENSIONS is derived from LANGUAGES.keys(), so only .py/.js/.ts files ever get listed by list_source_files in the first place. It exists as a safety net inside chunk_source itself (used directly by its own tests) and would matter the day the supported-extension list grows without every new extension getting a tree-sitter query. The algorithm: walk lines, accumulate non-blank runs into current, and whenever a blank line closes a run, record it as one block (start_line, end_line, lines). errors="replace" on the decode means a file with invalid UTF-8 bytes doesn't crash this function — bad bytes become the � replacement character instead.

_cap_chunk_sizes — splitting oversized chunks

64def _cap_chunk_sizes(chunks: list[Chunk]) -> list[Chunk]:
65    capped: list[Chunk] = []
66    for chunk in chunks:
67        if len(chunk.code_text) <= MAX_CHUNK_CHARS:
68            capped.append(chunk)
69            continue

MAX_CHUNK_CHARS = 4000. Most chunks (a typical function) pass straight through unchanged on line 68. For the rare giant function or class that blows past 4000 characters, the rest of the function (not reproduced line-by-line here — see the file directly) walks its lines and greedily packs them into sub-chunks that each stay under the limit, naming them symbol#1, symbol#2, etc. via a flush() closure that captures part_lines/part_index/part_start from the enclosing scope using nonlocal. This exists because embedding models have an input token limit, and a single giant chunk would either get truncated silently by the API or blow the budget disproportionately for one oversized function versus every other normal-sized chunk.

6. Deep dive: the Chunk model & hashing

sleuth/chunking.py
5@dataclass
6class Chunk:
7    file_path: str
8    symbol_name: str | None
9    kind: str  # 'function' | 'method' | 'class' | 'module'
10    start_line: int
11    end_line: int
12    code_text: str
13
14    @property
15    def content_hash(self) -> str:
16        return hashlib.sha256(self.code_text.encode("utf-8")).hexdigest()

A dataclass is just a plain container — @dataclass auto-generates __init__, __repr__, and __eq__ from the field list, so no boilerplate constructor is hand-written. symbol_name: str | None is deliberately nullable — module-level fallback chunks and top-of-file code don't belong to any named function/class, so they're stored with symbol_name = None.

content_hash is a @property, not a stored field — it's computed on demand from code_text every time it's accessed, using SHA-256. This is the entire mechanism incremental re-indexing is built on: two chunks with byte-for-byte identical code produce the identical hash, deterministically, every time, regardless of when or where it's computed. Comparing hashes instead of comparing full code strings is faster (32-byte hash vs. potentially thousands of characters of code) and is exactly what get_existing_hashes/to_embed in pipeline.py line 65 relies on. 

19def format_chunk_context(chunk: Chunk, language: str) -> str:
20    symbol = chunk.symbol_name or "(module level)"
21    header = (
22        f"# File: {chunk.file_path}\n"
23        f"# {chunk.kind}: {symbol}\n"
24        f"# Language: {language}\n\n"
25    )
26    return header + chunk.code_text

This is what actually gets sent to the embedding API — not the raw code alone. A three-line comment header is prepended: which file, what kind of symbol and its name, and what language. Why bother? Because embedding models produce better, more discriminating vectors when given a little surrounding context — a function named login in auth.py means something different from one named login in a test fixture file, and the embedding should reflect that. This function is called from pipeline.py line 70, once per chunk in to_embed, right before the batch goes to embed_batch.

29    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
30        batches = [texts[i : i + self.batch_size] for i in range(0, len(texts), self.batch_size)]
31        semaphore = asyncio.Semaphore(self.max_concurrency)
32
33        async with httpx.AsyncClient() as client:
34            results = await asyncio.gather(
35                *(self._embed_one_batch(client, semaphore, batch) for batch in batches)
36            )

This is where "embedding calls sent concurrently (bounded)" — a stated project requirement — actually gets implemented. Line 30 chops the (possibly huge) list of texts into chunks of at most 128 — Voyage's API accepts a batch of texts per request, so this is the largest slice sent in one HTTP call. Line 31 creates a semaphore capped at 5: a counter that at most 5 concurrent tasks can "hold" at once — the concurrency bound, so a repo with 40 batches doesn't fire 40 simultaneous HTTP requests at Voyage and get rate limited. Line 34's asyncio.gather(*(...)) starts all the per-batch coroutines at once, but each one immediately blocks on the semaphore inside _embed_one_batch until a slot frees up — so at most 5 are actually in flight against the network at any moment, and gather waits for every one to finish before returning, preserving order. 

43    async def _embed_one_batch(self, client, semaphore, batch: list[str]) -> list[list[float]]:
44        async with semaphore:
45            response = await post_with_retry(
46                client, VOYAGE_EMBEDDINGS_URL,
47                headers={"Authorization": f"Bearer {self.api_key}"},
48                json={"input": batch, "model": self.model_name},
49            )
50        data = response.json()["data"]
51        data.sort(key=lambda item: item["index"])
52        return [item["embedding"] for item in data]

async with semaphore: is what actually enforces the bound described above — it acquires a slot on entry and releases it on exit (even if the request raises). The Voyage API's response doesn't strictly guarantee its data array comes back in the same order as the input texts, so each item carries its own index; line 51 sorts by that index before extracting embeddings, which is what makes the ordering contract embed_batch relies on (matching vectors back up to chunks via zip in pipeline.py line 74) actually safe.

post_with_retry — one shared retry policy for every HTTP call

8async def post_with_retry(client, url, *, retries: int = 1, backoff_seconds: float = 1.0, **kwargs):
9    attempt = 0
10    while True:
11        try:
12            response = await client.post(url, **kwargs)
13        except httpx.TransportError:
14            if attempt < retries:
15                attempt += 1
16                await asyncio.sleep(backoff_seconds)
17                continue
18            raise
19
20        if response.status_code in TRANSIENT_STATUS_CODES and attempt < retries:
21            attempt += 1
22            await asyncio.sleep(backoff_seconds)
23            continue
24        response.raise_for_status()
25        return response

Lives in sleuth/http_retry.py, shared by every provider call in the codebase (Voyage here; Groq/NIM later for generation). Two distinct failure shapes get one retry each, by default: a transport-level failure (httpx.TransportError — DNS failure, connection reset, timeout — the request never got a response at all) and a transient HTTP status (429 too-many-requests, or 500/502/503/504 server-side errors — TRANSIENT_STATUS_CODES). Both retry exactly once (retries=1 by default) after a fixed one-second sleep, then give up — a permanent 4xx like 401 (bad API key) or 400 (malformed request) is never retried, since retrying an unauthorized request five times wastes time and won't ever succeed. response.raise_for_status() on line 24 converts any remaining non-2xx status into an httpx.HTTPStatusError exception, which — since nothing in ingest_repo catches it — would currently propagate all the way up and violate the "never raises" goal for anything other than a clone failure (see the callout at the end of section 3).

8. Deep dive: the store layer (SQL)

sleuth/store.py

Every function here takes a live psycopg.Connection and issues one raw parameterized SQL statement — no ORM, per the project's core constraint. None of these functions call conn.commit() themselves; committing is always the caller's job (visible throughout pipeline.py), which keeps the store layer honest about not deciding transaction boundaries on the orchestrator's behalf.

get_existing_hashes

29def get_existing_hashes(conn, repo_id: str) -> dict[tuple[str, str | None], str]:

Pulls every chunk currently stored for this repo and reshapes the rows into a dict keyed by (file_path, symbol_name) mapping to content_hash — exactly the shape ingest_repo needs for the O(1) hash lookup on line 65, instead of scanning a list.

57        )

ON CONFLICT (...) DO UPDATE is Postgres's upsert: try the INSERT; if it would violate the unique index on (repo_id, file_path, COALESCE(symbol_name, '')) (defined in schema.sql, section 9), instead run the UPDATE clause on the row that's already there. EXCLUDED is special upsert syntax referring to the row values that would have been inserted. This single statement is what makes re-indexing a changed function overwrite its old row in place rather than erroring on the duplicate key or leaving two rows for the same symbol.

The COALESCE(symbol_name, '') in the conflict target matters because SQL's NULL is never equal to another NULL — two rows both having symbol_name = NULL would not collide under a plain unique index on (repo_id, file_path, symbol_name), silently producing duplicate rows for module-level chunks every re-index. Coalescing NULL to empty string first makes "no symbol" collide with itself correctly.

Called once per (chunk, embedding) pair from a loop in upsert_chunks — one row at a time, not a single bulk statement; fine at the scale this pipeline currently runs at, but worth knowing if a very large repo ever makes per-row round-trips a bottleneck.

delete_stale_chunks

70def delete_stale_chunks(conn, repo_id: str, current_keys: set[tuple[str, str | None]]) -> None:
71    existing = get_existing_hashes(conn, repo_id)
72    stale_keys = existing.keys() - current_keys
73    for file_path, symbol_name in stale_keys:
74        conn.execute(
75            "DELETE FROM chunks WHERE repo_id = %s AND file_path = %s AND COALESCE(symbol_name, '') = COALESCE(%s, '')",
76            (repo_id, file_path, symbol_name),
77        )

existing.keys() - current_keys is plain Python set difference — every key that's in the database but not in this run's fresh chunk list. That's exactly "code that used to exist and doesn't anymore." The same COALESCE(..., '') trick from the upsert query reappears in the DELETE's WHERE clause, for the same NULL-equality reason — without it, a stale module-level chunk (symbol_name IS NULL) would never match and would never get deleted.

9. Deep dive: the database schema

schema.sql
17CREATE TABLE IF NOT EXISTS chunks (
18    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
19    repo_id       uuid NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
20    file_path     text NOT NULL,
21    symbol_name   text,
22    kind          text NOT NULL,
23    start_line    int NOT NULL,
24    end_line      int NOT NULL,
25    code_text     text NOT NULL,
26    content_hash  text NOT NULL,
27    embedding     vector(1024) NOT NULL
28);
29
30CREATE UNIQUE INDEX IF NOT EXISTS chunks_identity_idx
31    ON chunks (repo_id, file_path, COALESCE(symbol_name, ''));
32
33CREATE INDEX IF NOT EXISTS chunks_embedding_idx
34    ON chunks USING hnsw (embedding vector_cosine_ops);

embedding vector(1024) is a pgvector column type — a fixed-width array of 1024 floats, matching VoyageEmbedder.dim exactly. Fixed-width is why the project design notes chunk tables per dimension (chunks_1024/chunks_2048) for a future multi-provider setup — pgvector can't store a variable-length vector in one column, so a NIM embedder (2048-dim) couldn't share this table as-is. Today's schema is the narrowed Voyage-only version: one chunks table, hardcoded vector(1024).

REFERENCES repos(id) ON DELETE CASCADE means deleting a row from repos automatically deletes every chunk that belongs to it — no orphaned chunk rows left behind pointing at a repo that no longer exists.

chunks_identity_idx is the unique index that upsert_chunks's ON CONFLICT clause (section 8) targets — it's what turns a duplicate insert into an update instead of a Postgres uniqueness error. It's the schema-level enforcement of "one row per (repo, file, symbol)," with the exact same COALESCE trick applied here at index-definition time as well.

chunks_embedding_idx is an HNSW (Hierarchical Navigable Small World) index — an approximate-nearest-neighbor index structure that makes "find the chunks whose embedding is closest to this query vector" fast even with many thousands of rows, instead of comparing the query against every single vector in the table. vector_cosine_ops tells pgvector to measure closeness by cosine similarity (the angle between vectors) rather than raw Euclidean distance — the standard choice for text/code embeddings, where direction matters more than magnitude. This index isn't used by anything in the ingestion pipeline itself; it's what the not-yet-built retrieval step (Task 10+) will query against.

11. Glossary of concepts used

async / await
Python's syntax for cooperative concurrency. An async def function returns a coroutine that doesn't run until awaited (or scheduled via asyncio.gather); while one coroutine is waiting on I/O (a network response), the event loop can run other coroutines. Used here so embedding batches can be in flight concurrently instead of one at a time.
Semaphore
A counter-based concurrency limiter. asyncio.Semaphore(5) lets at most 5 concurrent async with semaphore: blocks proceed at once; the 6th caller blocks until one of the first 5 finishes and releases its slot.
Shallow clone
git clone --depth 1 — fetches only the latest commit's tree, not the repo's full history. Much faster and smaller when only the current file contents matter.
Content hash
A deterministic fingerprint (here, SHA-256) of a piece of content. Identical content always produces the identical hash, so comparing hashes is a cheap stand-in for comparing full content — the basis of the incremental re-index skip.
Upsert (INSERT ... ON CONFLICT ... DO UPDATE)
A single SQL statement that inserts a new row, or updates the existing one in place if it would collide with a unique constraint — avoids the insert-then-check-then-update race and boilerplate.
COALESCE
SQL function returning its first non-NULL argument. COALESCE(symbol_name, '') turns NULL into '' so two NULLs can be compared/indexed as equal — plain SQL NULL = NULL is never true.
HNSW index
Hierarchical Navigable Small World — an approximate-nearest-neighbor graph index. Lets a vector similarity search return "close enough" nearest matches in roughly logarithmic time instead of scanning every row.
Cosine similarity
Similarity measured by the angle between two vectors, ignoring their magnitude. The standard distance metric for comparing text/code embeddings.
Parameterized SQL / argument-list subprocess calls
Passing values separately from the query/command template (%s placeholders in SQL, a list of args instead of a shell string for subprocess.run) so user-controlled data can never be misinterpreted as code — the general defense against injection attacks.
respx
A test library that intercepts outgoing httpx requests and returns programmed fake responses, so tests never touch the real network.
